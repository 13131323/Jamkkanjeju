# 방명록 작성 비즈니스 규칙

## 1. 요청과 현재 사용자 확인

- 요청·응답·오류 계약은 [방명록 작성 API 명세](./API_SPEC.md#방명록-작성-api)를 따른다.
- 작성자는 인증된 현재 사용자다. 요청으로 다른 사용자 ID를 받지 않는다.
- 일반 필드와 실제 이미지·오디오 파일을 multipart로 받고 유형별 조건부 필드는 요청 DTO에서 검증한다.
- `GENERAL`은 장소를, `ROAD`는 장소 별칭과 좌표를 사용한다. 유형에서 사용하지 않는 장소·좌표·미션 값은 무시하여 저장하지 않고 요청 검증 단계에서 거절한다.
- 이미지·오디오 모두 미첨부를 허용한다. 같은 파일 필드로 여러 파일을 보내는 요청과 첨부한 빈 파일은 요청 검증 실패로 처리한다.
- 날짜·문자열 길이·기온·좌표는 명세의 제약을 Bean Validation으로 검증한다. 기존 좌표 범위 검증과 중복되는 별도 유한성 메서드는 추가하지 않는다.
- 사용자 인증이나 요청 필드 검증에 실패하면 방명록 생성·Blob 업로드를 진행하지 않는다.

## 2. 처리 순서

1. 요청의 유형·조건부 필드·파일 개수와 인증된 현재 사용자를 확인한다.
2. 일반 방명록이면 장소 존재와 본인의 방문 이력을 확인한다.
3. 일반 방명록에 미션 ID가 있으면 미션 존재·활성 상태·현재 사용자 완료 여부를 순서대로 확인하고 연결할 미션을 결정한다.
4. 방명록 공통 기록과 유형별 기록을 만들고 방명록 ID를 확보한다.
5. 첨부 파일을 크기·실제 형식·디코딩 기준으로 검증하고 오디오 재생 시간이 제한 이내인지 확인한 뒤 유형·방명록 ID별 Blob 경로로 업로드한다.
6. 업로드된 단일 URL과 사용자 입력 오디오 제목을 공통 기록에 반영한다.
7. DB 저장·커밋까지 성공하면 실제 저장값으로 작성 응답을 구성한다. 중간 실패나 커밋 실패 시 DB 변경과 이번 요청의 Blob을 정리한다.

장소·방문·미션 검증 전에 Blob을 업로드하지 않는다. 파일이 없는 요청도 같은 DB 트랜잭션으로 처리하되 파일 검증·스토리지 호출은 생략한다.

## 3. 일반 방명록의 장소와 방문 이력

- `locationId`로 장소를 조회한다. 장소가 없으면 방문·미션 조회와 파일 처리를 진행하지 않는다.
- 장소가 있으면 현재 사용자와 해당 장소가 모두 일치하는 `VISITED_LOCATION`을 조회한다. 다른 사용자의 방문 기록은 인정하지 않는다.
- 현재 스키마는 사용자·장소 조합당 방문 기록 한 건을 유지한다. 기존 FastAPI처럼 여러 방문 행 중 최신 행을 고르는 조회는 추가하지 않는다.
- 방문 기록이 없으면 일반 방명록을 생성하지 않는다. 존재하면 해당 방문 기록을 새 `LOCATION_GUESTBOOK.visited_location_id`에 연결한다.
- 요청의 `visitedAt`은 방명록에 기록할 날짜다. 방문 기록의 `last_visited_at` 날짜와 비교하거나 서버 날짜로 덮어쓰지 않는다.
- 기존 방명록 유무와 작성 횟수는 검사하지 않는다. 같은 장소·사용자·방문 날짜로 여러 번 작성할 수 있다.
- 방명록 작성을 이유로 방문 기록을 생성하거나 `last_visited_at`을 갱신하지 않는다. 좌표·장소 반경으로 방문 여부를 다시 판정하지 않는다.

## 4. 일반 방명록의 미션 연결

- `missionId`는 공통 `MISSION.id`다. 세부 미션 ID나 진행도 ID로 해석하지 않는다.
- 미션 ID가 없으면 미션·진행도·보상 상태를 조회하지 않고 연결 없이 저장한다.
- 미션 ID가 있으면 공통 미션과 유형별 상세를 기준으로 존재와 활성 상태를 확인한다.
- 존재하지 않거나 유형별 미션 상세가 없는 대상은 미션 없음으로 처리한다. 비활성 미션은 완료 이력이 있어도 거절하며 완료 여부를 먼저 조회하여 우회하지 않는다.
- 활성 미션이면 현재 사용자의 완료 이력을 확인한다. 완료했다면 해당 미션을 `LOCATION_GUESTBOOK.mission_id`에 연결하고, 미완료이면 방명록 작성은 허용하되 연결은 비운다.
- 완료 기준은 보상 지급 상태가 아닌 진행도의 `mission_status`다. 보상 상태 존재·지급 여부로 완료를 대체하지 않는다.
- 문화 미션은 해당 사용자·미션 진행도가 완료인지 확인한다.
- 보물찾기 미션은 기존 `MissionCompletionChecker`의 완료 판정 기준을 재사용한다.
- 협동 미션은 현재 사용자가 `ACCEPTED`로 참가한 팀의 진행도가 완료인 이력이 하나라도 있으면 완료로 본다. `PENDING`은 완료로 인정하지 않으며 현재 진행 중인 다른 팀이 있다는 이유로 과거 완료 이력을 무시하지 않는다. 기존 공통 완료 판정을 재사용한다.
- 현재 스키마에 없는 FastAPI의 `deleted_at` 조건이나 별도 세부 미션 PK를 그대로 옮기지 않는다.
- 장소 ID와 미션 ID는 기존처럼 각각 검증한다. 미션이 해당 장소에 속해야 한다는 추가 연결 제약은 만들지 않는다.
- 이 연결은 방명록 조회의 미션 정보와 지도 조회의 미션별 방명록 작성 여부에 사용한다. 미션 진행도나 보상을 변경하지 않는다.

## 5. 길바닥 방명록

- 장소·방문 기록·미션·완료 이력은 조회하지 않는다.
- 공통 방명록과 PK를 공유하는 `ROAD_GUESTBOOK`에 요청의 장소 별칭과 위도·경도를 저장한다.
- 장소에 자동으로 귀속시키거나 가까운 장소를 검색하여 방문 기록을 생성하지 않는다.
- 같은 사용자·별칭·좌표에 기존 길바닥 방명록이 있어도 새로 작성할 수 있다.

## 6. 공통 내용과 오디오 제목

- `GUESTBOOK`에 작성자, 방문 날짜, 글·사진 URL·음성 URL·오디오 제목·날씨·기온·색상, 서버 저장 시각과 `ACTIVE` 상태를 저장한다.
- 일반 방명록은 공통 기록과 `LOCATION_GUESTBOOK`, 길바닥 방명록은 공통 기록과 `ROAD_GUESTBOOK`을 함께 생성한다. 별도의 유형별 방명록 ID를 만들지 않는다.
- 사진·음성 URL은 기존 VARCHAR 컬럼에 각각 단일 문자열로 저장한다. URL 배열·JSON 문자열·쉼표로 결합한 여러 URL을 저장하지 않는다.
- 오디오 제목은 사용자 입력만 사용하며 요청 검증에서 최대 스무 자를 적용한다. DB 컬럼의 기존 길이가 더 길어도 요청 제한을 늘리지 않는다.
- 오디오 파일이 있으면 전달된 제목을 저장한다. 제목은 선택이므로 미전송이면 null이며, 오디오가 없으면 제목만 전달되더라도 제목은 저장하지 않는다.
- OpenAI 전사·제목 생성 호출과 관련 설정·실패 처리는 가져오지 않는다. 파일명이나 음성 내용을 제목으로 자동 대체하지 않는다.
- 글·날씨·기온·색상과 모든 파일이 없어도 공통 기록과 유형별 기록을 생성한다.
- `saved_at`은 주입받은 `Clock`과 기존 KST 시간 정책으로 구한 서버 시각이다. 클라이언트 날짜·파일 메타데이터·EXIF로 대체하지 않는다.

## 7. 이미지 검증

- 기존 공통 `ImageValidator`를 재사용하고 방명록 도메인의 오류 코드를 전달한다. 형식·크기·손상 오류 메시지는 기존 사진 저장 API와 일치시킨다.
- 파일을 제한된 크기로 읽으며 multipart 크기 정보만 신뢰하지 않는다. 허용 형식과 바이트 제한은 API 명세를 따른다.
- 파일명·요청 Content-Type 대신 실제 바이트 시그니처로 형식을 판별하고 디코딩까지 확인한다. 손상된 이미지는 Blob에 저장하지 않는다.
- 검증 후 원본 데이터를 저장한다. 리사이징·압축·임의 형식 변환은 추가하지 않는다.
- 실제 JPEG는 `.jpg`와 `image/jpeg`, PNG는 `.png`와 `image/png`, WebP는 `.webp`와 `image/webp`로 저장한다.

## 8. 오디오 검증과 요청 크기

- 오디오 읽기·크기 제한·실제 형식 판별은 다른 도메인에서도 재사용할 수 있는 공통 검증 컴포넌트로 분리한다. 서비스에 바이트 시그니처 판별 코드를 직접 넣지 않는다.
- 파일을 읽는 동안에도 명세의 바이트 상한을 적용하고, 파일 시그니처·컨테이너 헤더로 실제 허용 형식인지 판별한다. 확장자와 multipart Content-Type만으로 통과시키지 않는다.
- 이미지와 오디오 모두 최대 10MB로 제한한다. 판별할 수 없거나 허용 형식이 아니면 형식 오류, 크기 초과는 해당 파일의 용량 오류로 구분한다.
- 오디오는 FFmpeg로 실제 디코딩한다. 헤더만 정상이고 내용이 잘렸거나 디코더가 오류를 보고하는 파일, 오디오 스트림이 없거나 재생 가능한 샘플이 없는 파일은 오디오 손상 오류로 거절한다. 파일명이나 메타데이터에 적힌 길이만 신뢰하지 않는다.
- Docker 실행 이미지에 FFmpeg를 설치한다. 로컬 실행은 PATH의 `ffmpeg`를 사용하고, 다른 위치에 설치했으면 `FFMPEG_PATH`에 실행 파일 경로를 지정한다. YAML의 `app.audio.ffmpeg-path`로 주입한다.
- 디코딩한 샘플 수로 재생 시간을 구해 30초를 초과하면 재생 시간 초과 오류로 처리한다. 정확히 30초까지 허용한다. 제한 이내 파일은 끝까지 디코딩하며, 초과 파일은 초과를 확인하는 데 필요한 부분까지만 디코딩해 거절한다. 음성 인식이나 내용 판정은 하지 않는다.
- 검증용 입력과 디코딩 결과는 임시 파일로 처리하고 성공·실패 모두 정리한다. 디코더 미설치·실행 실패 등 서버 설정 문제는 손상된 파일로 오인하지 않고 공통 서버 오류로 전달한다.
- 실제 형식에 맞는 `.mp3`, `.m4a`, `.aac`, `.wav`, `.ogg`, `.webm` 확장자와 Content-Type을 지정한다. 검증한 원본 데이터를 업로드하며 다른 포맷으로 변환하지 않는다.
- 서블릿 기본 크기 제한이 개별 검증보다 먼저 요청을 거절하지 않도록 multipart의 파일·전체 요청 상한을 해제한다. 이미지·오디오 검증 컴포넌트가 각각 10MB 제한과 개별 오류를 적용하며, 임의의 전체 요청 용량 상한을 추가하지 않는다. 기존 다른 사진 업로드 API의 개별 이미지 제한과 오류 계약은 유지한다.
- 파싱된 이미지·오디오의 개별 상한 초과는 각 파일의 용량 오류로 처리하며 내부 파서 예외를 응답에 노출하지 않는다.

## 9. Blob 경로와 저장

- 공통 방명록 ID를 확보한 뒤 방명록 유형에 맞는 경로를 사용한다. Blob 이름은 서버에서 만든 UUID와 실제 형식의 확장자로 구성하고 원본 파일명은 사용하지 않는다.

```text
guestbook/general/{guestbookId}/images/{uuid}.{extension}
guestbook/general/{guestbookId}/audios/{uuid}.{extension}
guestbook/road/{guestbookId}/images/{uuid}.{extension}
guestbook/road/{guestbookId}/audios/{uuid}.{extension}
```

- 업로드와 삭제는 기존 공통 `BlobStorageClient`를 재사용한다. 저장된 Blob의 URL만 공통 방명록에 반영한다.
- 이미지·오디오 중 뒤에 처리한 파일이 실패할 수 있으므로 이번 요청에서 업로드에 성공한 모든 Blob에 대해 롤백 정리를 등록한다.
- 파일이 없으면 해당 URL은 null이며 스토리지에 빈 파일을 생성하지 않는다.

## 10. 트랜잭션과 실패 처리

- 공통 기록·유형별 기록·URL과 제목 반영은 하나의 쓰기 트랜잭션에서 처리한다. 방명록 ID 확보를 위한 flush는 최종 커밋으로 취급하지 않는다.
- 파일 검증·업로드·DB 저장 또는 커밋이 실패하면 방명록 DB 변경을 모두 롤백한다. 먼저 업로드된 이번 요청의 Blob은 기존 `BlobRollbackCleanup` 방식으로 보상 삭제한다.
- DB 롤백만으로 Blob이 삭제된다고 가정하지 않는다. 파일 업로드 뒤 커밋이 실패하는 경우도 포함한다.
- 정리 중 Blob 삭제가 실패해도 최초 오류를 바꾸거나 정상 응답으로 바꾸지 않는다. 방명록 ID·Blob 식별자와 정리 실패를 로그에 남긴다. 스토리지 비밀값과 파일 내용을 로그에 남기지 않는다.
- 기존 공통 정리 정책처럼 트랜잭션 결과가 불명확하면 정상 행이 참조할 수 있는 Blob을 임의 삭제하지 않고 확인이 필요한 식별자를 로그로 남긴다.
- 내부 스토리지·DB 오류는 공통 서버 오류 처리에 전달한다. 응답에 내부 예외 메시지를 노출하지 않는다.
- 기존 방명록·방문·미션 진행도·지급 상태·포인트·쿠폰·캐릭터 획득 기록을 변경하지 않는다. 정리 대상도 이번 요청의 Blob에 한정한다.

## 11. 반복 요청과 응답

- 성공한 요청마다 새 공통 방명록과 유형별 기록을 생성한다. 같은 콘텐츠나 좌표를 비교해 중복을 제거하거나 기존 기록을 갱신하지 않는다.
- 네트워크 재시도로 동일 요청이 두 번 정상 처리되면 두 건이 생성될 수 있다. 별도 멱등 키 정책을 추가하지 않는다.
- 실제 저장된 단일 URL·제목·방문 날짜·서버 저장 시각과 연결 미션으로 응답을 구성한다. 미완료 미션이 요청되었더라도 응답에 요청 ID를 그대로 넣지 않는다.
- 일반 방명록은 장소 정보를 방문 기록을 통해 구성하고 길바닥 전용 필드는 비운다. 길바닥은 장소 ID·미션 ID를 비운다.
- 응답은 공통 래퍼 없이 DTO를 반환하며 nullable 필드는 생략하지 않는다.
