# 협동 미션 시작/이어하기 API 테스트 계획

- 상태: **실행 완료**
- 실행일: 2026-10-19
- 결과: **협동 미션 32개 전부 통과, 기존 테스트 포함 전체 513개 전부 통과** (실패·오류·건너뜀 0개)
- 대상 API: `POST /api/v2/cooperative-missions/{missionId}/progress`
- 기준 문서: `API_SPEC.md`, `BUISNESS_RULE.md`

## 진행 방식

| 구분 | 방법 |
| --- | --- |
| 단위 테스트 | Spring과 DB 없이 JUnit 5, AssertJ, Mockito로 응답 구성, 검증 순서, 서비스 분기와 저장 호출을 검증한다. 시각은 `Clock.fixed`로 고정하고 난수는 특정 값 대신 형식·길이를 검증한다. |
| 통합 테스트 | `MySqlIntegrationTestSupport`의 실행별 임시 MySQL DB에서 실제 JWT, MockMvc, JPA와 트랜잭션을 연결한다. 일반 테스트는 롤백하며 실제 커밋·롤백·동시 요청 검증은 테스트 트랜잭션 없이 실행하고 준비 데이터를 직접 정리한다. |

개발용 자동 로그인은 끈다. 개발 DB와 볼륨은 변경하지 않고, 테스트 종료 시 임시 DB와 접근 권한이 제거되는지 확인한다.

## 단위 테스트 계획

### `StartCooperativeMissionResponseTest`

| 구분 | 검증 내용 |
| --- | --- |
| 응답 구성 | 팀 진행도 ID와 내부 신규 생성 여부를 유지하고, 팀 토큰 문자열과 `null`이 각각 JSON의 `teamToken`으로 노출되는지 확인한다. |

### `StartCooperativeMissionServiceTest`

| 구분 | 검증 내용 |
| --- | --- |
| 검증 순서 | 사용자 잠금 조회 → 미션 검증 → 본인 참가 기록 조회 순서를 지키며, 사용자 없음·미션 없음·비활성에서는 올바른 오류와 함께 후속 조회·저장을 중단한다. |
| 신규 시작 | 첫 단계·진행 중·완료 시각 null인 팀을 저장한 뒤 현재 사용자를 HOST·ACCEPTED·고정 합류 시각으로 연결한다. 팀 토큰은 32바이트 URL-safe Base64이며 패딩 없이 컬럼 길이 안에 들어가고 응답에도 포함된다. |
| 이어하기 | HOST·MEMBER 및 PENDING·ACCEPTED 조합 모두 기존 진행도 ID를 반환하고, `HOST + ACCEPTED`에만 기존 팀 토큰을 반환한다. 나머지는 `teamToken=null`이며 팀·참가자 상태와 합류 시각을 변경하거나 추가 저장하지 않는다. |
| 완료 이력 | 완료 기록만 있으면 과거 기록을 유지하고 새 팀을 만들며, 완료 기록과 진행 중 기록이 섞여 있으면 진행 중 팀만 이어간다. |
| 저장 실패 | 진행도 저장 실패 시 참가자를 저장하지 않고, 참가자 저장 실패는 원래 예외를 전파한다. 실제 롤백은 통합 테스트에서 확인한다. |

## 통합 테스트 계획

### `StartCooperativeMissionApiIntegrationTest`

| 구분 | 요청 및 검증 내용 |
| --- | --- |
| 최초·반복 | 장소 없는 미션도 201로 시작하고 진행도와 본인 방장만 생성한다. 신규·반복 모두 동일 ID와 팀 토큰을 반환하며 저장된 토큰·시각·행 수를 유지한다. |
| 이어하기 | HOST·MEMBER 및 PENDING·ACCEPTED 조합을 실제 DB에 준비해 200을 확인한다. `HOST + ACCEPTED`만 기존 토큰을 받고 나머지는 `null`을 받으며, 팀 단계·상태·토큰, 모든 참가자와 기존 역할 수행 기록을 유지하고 PENDING은 자동 수락하지 않는다. |
| 완료 후 시작 | 완료된 팀·참가자·역할 수행 기록과 기존 보상 지급 상태를 그대로 두고 새 팀 ID를 생성한다. 역할 수행 기록과 보상 이력을 새로 만들거나 초기화하지 않는다. |
| 사용자·미션 격리 | 같은 미션의 타인 팀에 합류하지 않으며, 본인의 다른 미션 참가·대기 기록은 새 시작을 막지 않는다. 타인·다른 미션 데이터는 유지한다. |
| 오류 | 비정수 경로는 공통 400, 미인증·없는 사용자 토큰은 공통 401, 미션 없음·다른 유형 ID·비활성 신규/이어하기는 각각 명세의 404이며 기존 데이터를 유지한다. 토큰 변조·만료 세부 분기는 기존 인증 테스트로 회귀 확인한다. |
| Swagger | 인증 필요 POST 경로와 응답 스키마를 확인하고 내부 `created`는 공개하지 않는다. |
| 실제 롤백 | 참가자 저장 후 강제로 실패시켜 500과 신규 팀·참가자 전체 롤백, 기존 이력·보상 보존을 확인한다. 실패 후 재요청은 정상 생성되어 잠금이 해제되었는지 확인한다. |

### `StartCooperativeMissionConcurrencyIntegrationTest`

| 구분 | 요청 및 검증 내용 |
| --- | --- |
| 같은 사용자·같은 미션 | 독립 HTTP 요청을 동시에 시작해 201 한 건·나머지 200, 동일 진행도 ID, 팀·본인 참가자 각 한 건만 커밋되는지 확인한다. |
| 같은 사용자·다른 미션 | 동시에 요청해 각 미션에 새 팀을 만들 수 있고 충돌 오류를 내지 않는지 확인한다. |
| 다른 사용자·같은 미션 | 동시에 요청해 각자의 새 팀과 방장 참가자를 만들며 서로의 팀에 자동 합류하지 않는지 확인한다. |

동시 테스트는 시작 장벽과 제한 시간 있는 Future를 사용하며 임의 sleep이나 특정 생성 ID·난수에 의존하지 않는다.

## 실행 순서

1. DTO와 서비스 단위 테스트를 작성하고 실행한다.
2. API와 동시 요청 통합 테스트를 작성하고 실행한다.
3. 기존 테스트를 포함한 전체 테스트를 실행해 회귀 오류를 확인한다.
4. 실제 실행 결과와 임시 DB 정리 결과를 기록한다.

## 완료 조건

- 단위·통합 테스트가 모두 통과하고 기존 테스트에 회귀 오류가 없다.
- 신규·이어하기, 상태 보존, 사용자·미션 격리, 오류 응답과 롤백이 검증된다.
- 실제 MySQL에서 동시 중복 생성 방지가 검증된다.
- 개발 DB를 사용하지 않고 임시 DB·접근 권한이 정리된다.

## 발견하고 수정한 점

- 응답에 `teamToken`을 추가했다. 신규 시작과 기존 `HOST + ACCEPTED` 이어하기는 저장된 토큰을 반환하고, `HOST + PENDING`, `MEMBER + ACCEPTED`, `MEMBER + PENDING`은 `null`을 반환한다.
- Swagger 테스트는 개별 API에 `security`가 있는 것으로 잘못 가정했던 부분을 수정해 기존 OpenAPI 전역 `bearerAuth` 설정을 확인한다.
- 전체 회귀 실행에서 캐시된 테스트 컨텍스트의 연결 풀이 누적되어 MySQL `Too many connections`가 발생했다. 새 협동 미션 통합 테스트 기반에 `@DirtiesContext(AFTER_CLASS)`를 적용해 각 클래스 종료 후 컨텍스트·연결 풀을 닫도록 수정했다. 서버 연결 제한이나 기존 테스트·운영 설정은 변경하지 않았다.
- 상태·역할 조합은 매개변수 테스트로, 없는 미션·다른 유형 ID와 미인증·없는 사용자 토큰은 각각 한 테스트 안에서 함께 검증했다. 계획에서 제외한 정책이나 추가한 정책은 없다.
- 참가자 저장 실패는 실제 참가자를 저장·flush한 뒤 예외를 발생시켰으며, 테스트 트랜잭션 없이 호출해 팀·참가자 전체 롤백과 기존 데이터 보존을 확인했다. 이후 정상 재요청으로 잠금 해제도 확인했다.
- 같은 사용자·같은 미션의 독립 요청 4개에서 201 한 건·200 세 건, 동일 진행도 ID, 팀·본인 참가자 각 한 건을 확인했다. 서로 다른 미션 또는 사용자 요청은 각각 새 팀을 생성했다.
- Java 21에서 단위 테스트 → 통합 테스트 → 전체 회귀 테스트 순서로 다시 실행했다. 최종 전체 실행은 2026-10-19 15:07:23(KST)에 성공했다.
- 종료 후 MySQL을 조회해 `tour_test_<UUID>` 임시 DB 0개·해당 접근 권한 0개를 확인했다. 개발 DB·볼륨은 변경하지 않았다.
