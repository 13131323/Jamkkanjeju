# 협동 미션 시작/이어하기 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져오며 요청에서 별도로 받지 않는다.
- 요청의 `missionId`는 공통 `MISSION.id`이자 `COOPERATIVE_MISSION.mission_id`이며 팀 진행도 ID와 구분한다.
- 인증 정보에 해당하는 사용자가 존재하지 않으면 `UNAUTHORIZED`로 처리한다.
- 같은 사용자의 중복 생성을 막기 위해 현재 사용자 행을 비관적 쓰기 잠금으로 조회하고, 해당 트랜잭션이 종료될 때까지 잠금을 유지한다.
- 이어하기 조회와 신규 시작 판단은 사용자 잠금을 획득한 뒤 수행한다.
- 이 잠금은 같은 사용자·같은 협동 미션의 중복 생성을 막기 위한 것이며 문화·보물찾기의 기존 사용자 조회 방식은 변경하지 않는다.

## 2. 협동 미션 확인

- 요청한 공통 미션 ID에 해당하는 협동 미션을 조회한다.
- 해당 협동 미션이 없으면 `COOPERATIVE_MISSION_NOT_FOUND`로 처리한다. 다른 유형의 미션 ID도 동일하게 처리한다.
- 협동 미션 상태가 `INACTIVE`이면 `COOPERATIVE_MISSION_INACTIVE`로 처리한다.
- 미션 존재 여부와 활성 상태는 신규 시작과 이어하기 모두 검증한다.
- 미션 검증이 끝나기 전에는 진행도·참가자·팀 토큰을 생성하거나 변경하지 않는다.
- 미션의 장소는 시작 조건이나 응답 구성에 사용하지 않으며 연결된 장소가 없어도 시작·이어하기를 허용한다.

## 3. 본인이 참가 중인 팀 이어하기

- 현재 사용자와 요청 미션에 대해 다음 조건을 모두 만족하는 팀 진행도를 찾는다.
  - 진행도의 협동 미션 ID가 요청한 `missionId`와 같다.
  - 팀 진행 상태가 `IN_PROGRESS`이다.
  - 해당 팀에 현재 사용자의 참가자 기록이 있고 참가 상태가 `PENDING` 또는 `ACCEPTED`이다.
- `participant_role`은 이어하기 조건에 넣지 않는다. `HOST`와 `MEMBER` 모두 동일하게 이어갈 수 있다.
- 팀원 전체를 조회해 애플리케이션에서 순회하지 않고 현재 사용자의 참가 기록과 연결된 팀을 조건으로 조회한다.
- 조건을 만족하는 팀이 있으면 새 진행도를 생성하지 않고 해당 팀의 기존 진행도 ID를 반환한다.
- 기존 팀의 진행 단계·진행 상태·팀 토큰·완료 시각과 모든 참가자의 상태·역할·합류 시각을 변경하지 않는다.
- 역할 진행도나 보상 이력도 변경하지 않는다.
- `PENDING` 참가 기록도 이어하기 대상으로 사용하되 기존 대기 상태와 합류 시각을 그대로 유지한다. 이 API에서 참가를 자동 수락하지 않는다.
- 본인이 등록되지 않은 다른 팀이 같은 미션을 진행 중이어도 그 팀을 반환하거나 본인을 합류시키지 않는다.

## 4. 신규 시작 판단 범위

- 신규 시작 여부는 현재 사용자와 요청한 협동 미션의 진행 중인 참가·대기 기록만으로 판단한다.
- 해당 미션에서 이어갈 팀이 없으면 신규 시작으로 처리한다.
- 다른 협동 미션의 `PENDING` 또는 `ACCEPTED` 참가 기록이 있어도 새 팀 생성을 막지 않는다. 사용자당 전체 협동 미션 팀 수를 하나로 제한하지 않는다.
- 같은 사용자·같은 미션에 대해서만 진행 중인 참가·대기 팀을 최대 하나로 유지한다. 기존 팀이 있으면 이어하기로 처리하므로 참가 중·대기를 이유로 한 충돌 오류를 반환하지 않는다.
- `COMPLETED` 팀의 참가 이력은 이어하기 대상으로 사용하지 않으며 신규 시작도 제한하지 않는다.
- 다른 미션의 팀과 참가 기록은 수락·삭제하거나 완료 처리하지 않는다.

## 5. 새 진행도와 본인 참가자 생성

- 요청한 미션에서 이어갈 팀이 없으면 해당 협동 미션으로 새 팀 진행도를 생성한다.
- 진행도의 `current_step`은 1, `mission_status`는 `IN_PROGRESS`, `completed_at`은 `null`로 설정한다.
- `team_token`은 서버에서 생성한 새 팀 토큰으로 설정한다.
- 팀 토큰은 기존 FastAPI처럼 암호학적으로 안전한 난수를 URL-safe 문자열로 만들어 생성한다. `SecureRandom`으로 생성한 32바이트 난수를 URL-safe Base64로 인코딩하며 패딩은 제외한다.
- 팀 토큰은 `team_token`의 컬럼 길이 안에서 생성하고 DB 유일성 제약을 유지한다.
- 팀 토큰 원문은 로그에 출력하지 않으며 완성된 초대 URL은 저장하지 않는다.
- 진행도 ID를 확보한 뒤 본인 참가자 한 건을 생성하고 해당 진행도와 현재 사용자를 연결한다.
- 본인 참가자의 `participant_role`은 `HOST`, `participant_status`는 `ACCEPTED`로 설정한다.
- `joined_at`은 주입받은 `Clock`으로 구한 현재 시각을 사용한다.
- 신규 생성 시 다른 사용자의 참가자 기록은 만들지 않는다.
- 역할 카드나 역할 진행도를 생성·배정하지 않는다. 역할 선택·배정은 별도 기능에서 처리한다.
- 완료된 과거 진행도·참가자·역할 진행도는 그대로 유지하며 초기화하거나 삭제하지 않는다.
- 보상 지급과 `MISSION_REWARD_STATUS` 생성·초기화, 포인트·캐릭터·쿠폰 획득 기록 변경은 수행하지 않는다.

## 6. 응답 구성

- 신규 시작과 이어하기 모두 사용할 팀의 `COOPERATIVE_MISSION_PROGRESS.id`를 `cooperativeMissionProgressId`로 구성한다.
- 생성한 참가자 ID나 공통 미션 ID를 진행도 ID 대신 반환하지 않는다.
- 현재 사용자의 참가 역할이 `HOST`이고 참가 상태가 `ACCEPTED`인 경우에만 진행도에 저장된 팀 토큰을 `teamToken`으로 반환한다.
- 신규 시작에서는 현재 사용자를 `HOST + ACCEPTED`로 생성하므로 새 팀 토큰을 반환한다.
- 이어하기에서는 기존 참가자의 역할과 상태를 기준으로 판단하며, `HOST + ACCEPTED`이면 기존 팀 토큰을 반환한다.
- `HOST + PENDING`, `MEMBER + ACCEPTED`, `MEMBER + PENDING`이면 `teamToken`은 `null`로 반환한다.
- 토큰 반환 여부를 판단하기 위해 참가자의 상태·역할을 변경하지 않는다.
- 팀 상태·참가자 목록·역할 카드·역할 진행도·보상 정보는 응답에 포함하지 않는다.
- 기존 FastAPI의 전체 팀 상태 응답 구성은 가져오지 않는다. 해당 데이터는 별도의 상태 조회 기능에서 제공한다.
- 신규 생성 여부는 응답 상태를 구분하기 위한 내부 정보로만 사용하고 공개 JSON 필드로 노출하지 않는다.
- 성공·오류 응답 형식과 신규·이어하기의 응답 상태 구분은 API 명세를 따른다.

## 7. 반복 요청 및 동시 중복 생성 방지

- 같은 사용자가 같은 미션을 다시 요청하면 본인의 `PENDING` 또는 `ACCEPTED` 참가 기록으로 기존 팀을 이어서 반환한다.
- 조회 결과가 없었다는 이유만으로 잠금 획득 전의 판단을 사용해 새 팀을 만들지 않는다.
- 같은 사용자의 동시 요청은 사용자 행 잠금으로 순서대로 처리하고, 대기한 요청은 앞선 트랜잭션이 반영한 최신 참가·진행 상태를 기준으로 판단한다.
- 같은 미션의 동시 요청에서는 한 요청만 팀을 생성하고 나머지는 생성된 팀의 기존 진행도 ID를 반환한다.
- 같은 사용자가 서로 다른 미션을 동시에 시작하면 사용자 잠금으로 순서대로 처리하되 각 미션에서 이어갈 팀이 없다면 각각 새 팀을 생성할 수 있다.
- 앞선 요청이 실패해 롤백되면 이후 요청은 롤백된 미완성 데이터를 참가 중인 팀으로 판단하지 않는다.
- 다른 사용자끼리는 사용자 잠금을 공유하지 않으며 같은 미션에서 각자의 팀을 생성할 수 있다.
- 팀 토큰과 팀·사용자 조합의 유일성 제약만으로는 같은 사용자·같은 미션의 중복 참가를 막을 수 없으므로 이어하기 조회와 생성까지 같은 잠금 범위에서 처리한다.
- 향후 참가 요청 기능에서도 같은 사용자·같은 미션에 대한 참가·대기 팀 한 개 기준과 사용자 잠금을 적용해야 시작 요청과 참가 요청 사이의 중복을 막을 수 있다. 다른 미션의 참가·대기는 제한하지 않는다.

## 8. 트랜잭션 및 실패 시 보존

- 사용자 잠금, 미션 검증, 이어하기 조회와 신규 시작 판단, 진행도·본인 참가자 생성과 응답 구성을 하나의 트랜잭션으로 처리한다.
- 진행도와 본인 참가자 모두 정상 저장된 경우에만 커밋한다.
- 참가자 저장 등에 실패하면 새 진행도와 이번 요청의 참가 기록을 함께 롤백한다. 방장 없는 진행도가 남지 않아야 한다.
- 검증 실패·저장 실패에서 기존 팀과 참가자·역할 진행도, 과거 완료 기록과 보상 관련 데이터는 유지한다.
- 예상하지 못한 DB 오류를 미션 없음으로 바꾸지 않고 공통 서버 오류로 처리한다.
- 성공·실패와 관계없이 트랜잭션이 끝나면 사용자 잠금을 해제한다.

# URL로 참여 요청 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져오며 요청에서 별도로 받지 않는다.
- 요청 Body의 `teamToken`으로 참여할 협동 미션 팀을 식별한다.
- 인증 정보에 해당하는 사용자가 존재하지 않으면 `UNAUTHORIZED`로 처리한다.
- 시작/이어하기 요청과 참여 요청이 동시에 처리되더라도 같은 사용자·같은 미션의 진행 중인 팀이 중복되지 않도록 현재 사용자 행을 비관적 쓰기 잠금으로 조회한다.
- 잠금 순서는 현재 사용자 행, 대상 협동 미션 진행도 행 순서로 통일하고 트랜잭션이 종료될 때까지 유지한다.

## 2. 팀 진행도와 협동 미션 확인

- `teamToken`이 일치하고 진행 상태가 `IN_PROGRESS`인 협동 미션 진행도를 조회한다.
- 일치하는 진행도가 없거나 토큰에 해당하는 진행도가 이미 `COMPLETED`이면 `INVALID_INVITE_TOKEN`으로 처리한다.
- 조회한 진행도 행을 비관적 쓰기 잠금으로 조회하여 참가자 확인부터 신규 참가자 저장까지 대상 팀의 참가자 구성이 동시에 변경되지 않도록 한다.
- 진행도에 연결된 협동 미션의 상태가 `INACTIVE`이면 `COOPERATIVE_MISSION_INACTIVE`로 처리한다.
- 비활성 상태 검증은 기존 참가자 반환보다 먼저 수행하므로 대상 팀에 이미 참가한 사용자도 비활성화된 미션에는 참여 요청을 이어갈 수 없다.
- 팀 토큰과 미션 검증이 끝나기 전에는 참가자 상태나 진행도를 변경하지 않는다.

## 3. 대상 팀의 기존 참가자 확인

- 대상 진행도 ID와 현재 사용자 ID로 기존 참가자를 조회한다.
- 기존 참가자의 상태가 `PENDING`이면 새 참가자를 만들지 않고 기존 참가자 정보를 반환한다.
- 기존 참가자의 상태가 `ACCEPTED`이면 참가자 상태나 역할을 변경하지 않고 기존 참가자 정보를 반환한다.
- 방장이 자신의 초대 URL을 열면 대상 팀의 `HOST + ACCEPTED` 참가자이므로 같은 기존 참가자 반환 규칙을 적용한다.
- 기존 참가자를 반환할 때는 팀이 6명이거나 `current_step`이 2 이상이어도 정원 초과나 참여 마감 오류로 처리하지 않는다.
- 기존 참가자 반환은 새로운 참여 요청이 아니므로 참가 역할, 참가 상태와 합류 시각을 변경하지 않는다.

## 4. 동일 미션의 다른 팀 중복 참가 방지

- 대상 팀에 현재 사용자의 참가자 기록이 없으면, 대상 팀과 같은 협동 미션의 다른 진행 중인 팀에 현재 사용자가 참가하고 있는지 확인한다.
- 다른 팀의 참가 상태가 `PENDING` 또는 `ACCEPTED`이면 `COOPERATIVE_MISSION_ALREADY_PARTICIPATING`으로 처리한다.
- 다른 협동 미션의 참가·대기 기록은 현재 참여 요청을 제한하지 않는다.
- `COMPLETED` 팀의 과거 참가 이력도 현재 참여 요청을 제한하지 않는다.
- 다른 팀의 참가 기록을 대상 팀으로 옮기거나 삭제하지 않으며, 대상 팀에 새 참가자도 생성하지 않는다.
- 이 검증으로 시작/이어하기와 URL 참여 요청 모두에서 같은 사용자·같은 협동 미션의 진행 중인 참가·대기 팀을 최대 하나로 유지한다.

## 5. 새로운 참여 요청 검증

- 대상 팀과 같은 미션의 다른 팀 어디에도 현재 사용자의 진행 중인 참가 기록이 없을 때만 새로운 참여 요청을 검증한다.
- 새로운 참여 요청은 대상 진행도의 `current_step`이 1인 경우에만 허용한다.
- `current_step`이 2 또는 3이면 `COOPERATIVE_MISSION_JOIN_CLOSED`로 처리한다.
- 협동 미션의 최대 참가 인원은 방장을 포함하여 6명으로 고정한다.
- 현재 인원에는 대상 진행도의 `PENDING`과 `ACCEPTED` 참가자를 모두 포함한다.
- 현재 인원이 6명 이상이면 `COOPERATIVE_MISSION_FULL`로 처리한다.
- 참여 단계 검증을 먼저 수행하고, 통과한 경우에만 현재 인원을 검증한다.
- 검증 실패 시 기존 진행도와 참가자 정보를 변경하지 않는다.

## 6. 참가자 생성

- 모든 검증을 통과하면 현재 사용자를 대상 진행도의 새 참가자로 생성한다.
- 참가 역할은 `MEMBER`, 참가 상태는 `PENDING`으로 설정한다.
- 아직 방장이 참여 요청을 수락하지 않았으므로 `joined_at`은 `null`로 설정한다.
- 역할 카드와 역할 진행도는 이 API에서 생성하거나 배정하지 않는다.
- 진행도의 현재 단계, 진행 상태, 팀 토큰과 완료 시각은 변경하지 않는다.
- 참가자 생성에 성공하면 신규 참여 요청으로 처리한다.

## 7. 응답 구성

- `cooperativeMissionProgressId`는 팀 토큰으로 조회한 `COOPERATIVE_MISSION_PROGRESS.id`로 구성한다.
- `participantId`와 `participantStatus`는 신규 생성했거나 기존에 존재하던 현재 사용자의 참가자 정보로 구성한다.
- 신규 참가자를 생성한 경우 참가 상태는 `PENDING`이다.
- 기존 참가자를 반환하는 경우 저장된 `PENDING` 또는 `ACCEPTED` 상태를 그대로 반환한다.
- 신규 생성 여부는 정상 응답 상태를 구분하기 위한 내부 정보로만 사용하고 공개 JSON 필드로 노출하지 않는다.
- 성공 응답 상태와 응답 구조는 API 명세를 따른다.

## 8. 반복 요청 및 동시 요청 방지

- 같은 사용자가 같은 팀 토큰으로 요청을 반복하면 최초 요청에서만 참가자를 생성하고 이후 요청에는 기존 참가자 정보를 반환한다.
- 현재 사용자 행 잠금을 획득한 뒤 대상 팀과 동일 미션의 다른 팀 참가 여부를 최신 상태로 다시 확인한다.
- 대상 진행도 행 잠금을 획득한 뒤 대상 팀의 기존 참가자와 현재 인원을 최신 상태로 다시 확인한다.
- 여러 사용자가 같은 팀에 동시에 참여를 요청하면 진행도 행 잠금으로 순서대로 처리하여 전체 참가자가 6명을 초과하지 않도록 한다.
- 같은 사용자가 시작/이어하기 API와 URL 참여 요청 API를 동시에 호출하면 사용자 행 잠금으로 순서대로 처리하고, 먼저 커밋된 진행 중인 참가 기록을 나중 요청이 확인한다.
- 동일한 진행도와 동일한 사용자에 대한 참가자는 하나만 유지하며 DB의 팀·사용자 유일성 제약도 함께 적용한다.
- 앞선 요청이 실패해 롤백되면 이후 요청은 롤백된 참가자를 기존 참가자로 판단하지 않는다.

## 9. 트랜잭션 및 실패 시 보존

- 사용자 잠금, 진행도와 미션 확인, 기존 참가자와 다른 팀 참가 여부 확인, 단계·정원 검증, 참가자 생성과 응답 구성을 하나의 트랜잭션으로 처리한다.
- 신규 참가자 저장과 응답 구성이 모두 성공한 경우에만 변경을 커밋한다.
- 검증 실패나 저장 실패가 발생하면 이번 요청에서 생성한 참가자를 남기지 않는다.
- 실패 시 기존 진행도의 단계·상태·팀 토큰·완료 시각과 모든 기존 참가자의 상태·역할·합류 시각을 유지한다.
- 예상하지 못한 DB 오류를 초대 토큰 오류나 충돌 오류로 바꾸지 않고 공통 서버 오류로 처리한다.
- 성공·실패와 관계없이 트랜잭션이 끝나면 사용자와 진행도 잠금을 해제한다.
