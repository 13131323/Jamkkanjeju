# 협동 미션 상태 조회 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC_2.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져오며 요청에서 참가자 ID·역할·참가 상태를 별도로 받지 않는다.
- 요청의 진행도 ID는 팀 단위 `COOPERATIVE_MISSION_PROGRESS.id`이며 공통 미션 ID와 구분한다.
- 사용자 좌표는 완료 단계의 다음 장소 추천과 거리 계산에 사용한다.
- 조회 단계와 관계없이 요청 좌표 검증은 동일하게 적용한다.

## 2. 진행도와 미션 확인

- 요청 ID에 해당하는 팀 진행도와 연결된 협동 미션을 조회한다.
- 진행도가 없으면 `COOPERATIVE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 진행 중인 팀뿐 아니라 완료된 팀도 조회하므로 진행 상태를 `IN_PROGRESS`로 제한하지 않는다.
- 연결된 협동 미션이 비활성 상태이면 `COOPERATIVE_MISSION_INACTIVE`로 처리한다.
- 협동 미션의 장소가 없어도 상태 조회를 허용한다.
- 조회 과정에서 진행도를 생성·초기화하거나 단계를 변경하지 않는다.

## 3. 현재 참가자 확인

- 진행도 ID와 현재 사용자 ID가 모두 일치하는 참가자를 조회한다.
- 참가자가 없으면 `COOPERATIVE_MISSION_PARTICIPANT_NOT_FOUND`로 처리한다.
- 참여 요청 거절로 행이 삭제된 경우도 참가자 없음으로 처리한다.
- 방장·팀원과 대기·수락 상태 모두 조회할 수 있다. 대기 참가자를 조회 과정에서 자동 수락하지 않는다.
- 완료 단계에서도 참가자 확인을 먼저 수행한다. 완료 응답에서 현재 참가자 정보를 숨긴다는 이유로 권한 확인을 생략하지 않는다.
- 요청에 포함된 다른 사용자의 참가자 ID를 신뢰하거나 다른 팀 상태를 반환하지 않는다.

## 4. 단계와 응답 구성 범위

| 단계 | 의미 | 진행 상태 |
| --- | --- | --- |
| 1 | 초대·역할 배정 | `IN_PROGRESS` |
| 2 | 미션 수행 및 사진 인증 | `IN_PROGRESS` |
| 3 | 미션 완료 | `COMPLETED` |

- 별도의 역할 배정 단계를 두지 않고 초대와 역할 배정을 같은 첫 단계에서 진행한다.
- 모든 단계에서 팀 진행도 ID, 공통 미션 ID, 연결된 미션 제목, 저장된 진행 상태와 현재 단계를 반환한다.
- 첫 단계와 수행 단계에서는 현재 참가자·전체 참가자·역할 카드·역할 수행 목록과 역할 집계를 구성한다.
- 완료 단계에서는 참가자·역할 관련 필드를 사용하지 않고 완료 장소·현재 사용자 보상 정보·다음 장소를 구성한다.
- 현재 단계에 사용하지 않는 필드는 생략하지 않고 명세에 따라 null로 구성한다.
- 역할이 모두 인증되었다는 이유만으로 조회 API에서 완료 상태로 전환하지 않는다. 저장된 팀 상태를 기준으로 응답한다.
- 완료 시 단계·진행 상태·완료 시각을 변경하는 책임은 진행도 저장 API에 있다.

## 5. 참가자 목록 구성

- 해당 팀에 등록된 방장과 대기·수락된 팀원을 모두 조회한다.
- 방장을 먼저 배치하고 그 외 참가자는 생성 시각 오름차순으로 정렬한다.
- 참가자 ID·닉네임·팀 내 역할·참가 상태는 각 참가자와 연결된 사용자 정보를 기준으로 구성한다.
- 현재 참가자 정보는 앞서 조회한 현재 사용자의 참가자 행을 기준으로 구성한다.
- 거절되어 삭제된 참가자는 목록에 포함하지 않는다.
- 참가자 조회를 위해 합류 시각이나 참가 상태를 갱신하지 않는다.

## 6. 역할 카드와 역할 수행 목록

- 첫 단계부터 공통 역할 카드 전체와 현재 저장된 배정·수행 기록을 반환한다.
- 역할 카드는 카드 ID 오름차순으로 정렬한다.
- 역할 수행 기록은 대상 팀 참가자와 연결된 기록만 조회하며 다른 팀의 같은 카드 수행 기록을 포함하지 않는다.
- 현재 스키마에서 역할 수행 기록은 참가자 ID와 역할 카드 ID의 복합키로 식별한다.
- 응답에는 참가자 ID와 역할 카드 ID가 이미 있으므로 별도의 단일 `roleProgressId`를 만들거나 가상 ID로 대체하지 않는다.
- 역할 수행 목록은 참가자 ID, 역할 카드 ID 오름차순으로 정렬한다.
- 각 수행 기록은 담당 참가자 ID·닉네임, 역할 카드 ID·이름, 인증 진행 상태와 이미지 URL로 구성한다.
- 아직 저장된 역할 배정이 없으면 빈 목록을 반환한다.
- 역할 카드 하나는 같은 팀에서 최대 한 명에게 배정하고 한 참가자는 서로 다른 여러 카드를 맡을 수 있다는 기존 배정 규칙을 유지한다.
- 미배정 카드는 역할 카드 목록에는 포함하지만 수행 목록에는 포함하지 않는다.
- 역할 배정 저장 이후의 조회에는 커밋된 배정 결과를 반영한다.
- 이 API는 역할 카드를 배정하거나 역할 수행 기록을 생성·변경하지 않는다.

## 7. 역할 집계

- 전체 역할 수는 해당 팀에 실제 생성된 역할 수행 기록 수로 계산한다.
- 완료 역할 수는 그중 인증 진행 상태가 완료인 기록 수로 계산한다.
- 참가자 수나 공통 역할 카드 전체 개수를 전체 역할 수로 대신 사용하지 않는다.
- 배정이 없으면 전체·완료 역할 수는 모두 0이다.
- 첫 단계와 수행 단계에서 집계값을 반환하며 완료 단계에서는 사용하지 않는다.
- 집계 결과만으로 인증 상태·팀 진행 상태를 변경하거나 보상을 지급하지 않는다.

## 8. 완료 장소 구성

- 완료 단계에서 해당 협동 미션에 연결된 장소의 ID와 장소명을 구성한다.
- 연결된 장소가 없으면 완료 장소는 null로 구성한다.
- 완료 장소는 방금 완료한 미션의 장소이며 다음 추천 장소와 구분한다.
- 첫 단계와 수행 단계에서는 완료 장소를 구성하지 않는다.

## 9. 완료 보상 조회

- 보상 정산과 지급은 진행도 저장 API에서 팀을 완료 처리할 때 수행한다.
- 협동 미션 보상은 완료 역할 수·사진 인증 성공 여부와 관계없이 사용자별 해당 미션 최초 완료 시 한 번만 지급한다.
- 지급 대상은 완료 시점의 `ACCEPTED` 참가자이며 방장·팀원 역할을 구분하지 않는다. `PENDING` 참가자에게는 지급하지 않는다.
- 참가자마다 사용자와 공통 미션 조합의 `MISSION_REWARD_STATUS` 및 기존 완료 참가 이력을 확인한다. 현재 진행 중인 팀의 참가 기록이 있다는 이유만으로 재도전으로 판단하지 않는다.
- 기존 완료·지급 이력이 없는 참가자에게 미션에 설정된 AR 캐릭터·포인트·쿠폰을 모두 지급하고 지급 상태를 갱신한다. 미션에 설정되지 않은 보상은 지급하지 않는다.
- 기존에 같은 미션의 보상을 지급받은 참가자에게는 아무 보상도 지급하지 않는다. 일부 항목만 남아 있다고 재도전에서 나누어 지급하는 방식은 사용하지 않는다.
- 같은 팀에 최초 완료 사용자와 재도전 사용자가 섞여 있으면 각 사용자의 이력에 따라 지급 여부를 따로 결정한다.
- 진행도 저장에서는 완료 상태·완료 시각 변경과 참가자 보상 지급을 하나의 트랜잭션으로 처리한다. 지급 실패 시 완료 처리와 보상 변경을 함께 롤백한다.
- 기존 FastAPI처럼 완료 상태를 처음 조회할 때 보상을 정산하는 처리는 가져오지 않는다.
- 이 API는 현재 사용자가 수락된 참가자로 완료한 동일 미션의 팀 이력을 조회하여 최초 완료 팀을 찾는다.
- 최초 완료 팀은 완료 시각이 가장 이른 팀이며, 완료 시각이 같으면 진행도 ID가 작은 팀을 선택한다. 최초 완료 판단은 전체 팀이나 방장 기준이 아니라 현재 사용자 기준으로 수행한다.
- 조회 중인 팀이 현재 사용자의 최초 완료 팀이면 해당 팀에서 지급된 미션의 보상 정보를 구성한다. 보상 구성은 완료 역할 수에 따라 줄이지 않는다.
- 조회 중인 팀이 이후 재도전 팀이면 `reward` 객체의 모든 항목을 null로 구성한다. 사용자·미션의 누적 지급 상태가 true여도 과거 팀의 보상을 현재 팀의 보상처럼 반환하지 않는다.
- 최초 완료 팀을 나중에 다시 조회하더라도 해당 최초 완료 보상 정보를 동일하게 반환한다. 이후 팀이 생겼다는 이유로 최초 팀의 보상 표시를 바꾸지 않는다.
- 최초 완료 팀의 보상 항목은 미션에 설정된 보상과 현재 사용자의 지급 상태를 함께 확인하여 구성한다. 설정되지 않았거나 지급되지 않은 항목은 null이다.
- 이 방식으로 보상 지급 결과를 재구성할 수 있도록 완료된 진행도와 참가자 이력은 유지한다. Redis·서버 메모리 등에 별도의 지급 결과를 보관하지 않는다.
- 반복 폴링이나 여러 참가자의 동시 조회로 포인트·AR 캐릭터·쿠폰을 추가 지급하지 않는다.
- `MISSION_REWARD_STATUS`는 사용자와 공통 미션 조합의 지급 관리 데이터이며, 조회 과정에서 생성·초기화하거나 지급 여부를 변경하지 않는다.
- 완료 보상이 하나도 없어도 완료 응답의 보상 객체는 유지하고 각 항목을 null로 구성한다.
- 첫 단계와 수행 단계에서는 보상 정보를 구성하지 않는다.
- 아직 지급되지 않은 보상이 보이더라도 이 조회를 복구·재지급 작업으로 사용하지 않는다.

## 10. 다음 장소 구성

- 완료 단계에서 현재 사용자의 요청 좌표를 기준으로 다음 장소를 추천한다.
- 사용자 좌표에서 직선거리가 가장 가까운 장소를 선택하고 거리가 같으면 장소 ID가 작은 장소를 선택한다.
- 완료한 협동 미션에 장소가 연결되어 있으면 그 장소는 추천 후보에서 제외한다. 연결된 장소가 없으면 제외할 장소도 없다.
- 기존 장소 추천 공통 컴포넌트를 재사용하며 이 서비스에 거리·추천 로직을 중복 구현하지 않는다.
- 공통 추천 구현에 `// TODO: 추후 사용자 개인화된 추천 로직을 적용한다.` 주석을 유지한다.
- 사용자마다 좌표가 다르므로 추천 결과가 다를 수 있고 폴링 사이에 같은 장소를 유지할 의무는 없다.
- 기존 FastAPI 상태 조회와 동일하게 추천 후보가 없으면 다음 장소를 null로 구성한다.
- 추천 장소 이미지 조회에 실패하거나 이미지가 없으면 이미지 URL은 null로 구성한다.
- 추천 장소에 연결된 미션이 없으면 다음 미션은 null로 구성한다. 연결된 미션이 있으면 기존 공통 추천 규칙으로 미션 ID와 유형을 구성한다.
- 거리 정보는 요청 좌표에서 추천 장소까지의 직선거리를 미터 단위로 구성한다.
- 첫 단계와 수행 단계에서는 장소 추천과 이미지 조회를 실행하지 않는다.
- 추천 결과를 저장하거나 추천 실패를 이유로 기존 완료 상태·보상 결과를 변경하지 않는다.

## 11. 폴링과 반복 조회

- 첫 단계에서는 현재 참가 상태로 대기·수락 여부를 확인하고 역할 배정 변경을 반영한다.
- 수행 단계에서는 역할별 인증 상태와 집계값을 반영한다.
- 완료 단계의 응답을 받은 프론트는 폴링을 중단하고 완료 화면을 표시한다.
- 대기 중이던 사용자의 참가자 행이 삭제되어 참가자 없음 오류가 반환되면 프론트는 거절로 처리하고 폴링을 중단한다.
- 비활성 미션이나 진행도 없음 오류를 받은 경우에도 폴링을 중단한다.
- 동일 조건의 반복 조회는 팀·참가자·역할·보상 데이터를 변경하지 않는다.
- 보상·상태 변경이 커밋된 뒤의 새 조회는 변경 결과를 읽어야 한다.

## 12. 조회 트랜잭션과 실패 시 보존

- 진행도·미션 검증, 현재 참가자 확인과 단계별 데이터 조회를 읽기 전용 트랜잭션으로 처리한다.
- 보상 정산을 위한 비관적 쓰기 잠금은 사용하지 않는다.
- 같은 응답의 팀 단계와 참가자·역할 집계가 서로 다른 시점의 변경을 섞지 않도록 같은 조회 트랜잭션에서 구성한다.
- 첫 단계부터 완료 단계까지 DB 쓰기 작업을 수행하지 않는다.

- 예상하지 못한 조회 오류를 진행도 없음이나 참가자 없음으로 바꾸지 않고 공통 서버 오류로 처리한다.
