# 지도 홈 조회 비즈니스 규칙

## 1. 요청과 현재 사용자 확인

- 요청 형식과 응답·오류 계약은 [API 명세](./API_SPEC.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져오며 요청으로 사용자 ID를 받지 않는다.
- 인증 정보에 해당하는 사용자가 존재하는지 확인하고, 없으면 기존 공통 인증 오류로 처리한다.
- 회전·기울기가 없는 지도 화면만 대상으로 한다. 화면 좌상단·우하단 좌표와 실제 사용자 좌표는 구분한다.
- 필수값·숫자 및 boolean 형식·좌표 범위·화면 방향을 검증한 뒤 콘텐츠를 조회한다.
- 잘못된 좌표를 임의로 교환하거나 지도 중심을 사용자 위치로 대체하지 않는다.

## 2. 처리 순서

1. 요청값과 현재 사용자를 확인한다.
2. 좌상단·우하단으로 원래 화면 영역을 구성하고 사방으로 확장한 공통 조회 범위를 계산한다.
3. 확장 범위 안의 장소와 길바닥 방명록을 조회한다.
4. 조회한 장소에 연결된 활성 보물찾기·협동 미션을 모아 장소별 중복 여부를 확인한다.
5. 간소 응답이면 장소·길바닥 방명록 식별자와 좌표, 장소의 공통 미션 ID·유형만 구성한다.
6. 상세 응답이면 현재 사용자의 미션 완료·방명록 작성 여부, 장소별 방명록 수와 실제 수령 쿠폰을 조회한다.
7. 상세 응답의 장소별 거리·예상 시간과 TourAPI 대표 이미지, 길바닥 방명록 첨부 이미지를 구성한다.
8. 선택된 응답 형식으로 반환하며 조회 과정에서 상태를 변경하지 않는다.

## 3. 화면 영역 계산과 확장

- 화면의 북쪽 경계는 좌상단 위도, 남쪽 경계는 우하단 위도, 서쪽 경계는 좌상단 경도, 동쪽 경계는 우하단 경도이다.
- 나머지 꼭짓점은 우상단을 좌상단 위도·우하단 경도, 좌하단을 우하단 위도·좌상단 경도로 구성할 수 있다. 프론트에서 추가 꼭짓점을 받지 않는다.
- 원래 화면의 위도 차이를 높이, 경도 차이를 너비로 사용한다. 높이와 너비가 모두 양수여야 한다.
- 북쪽 경계에 높이의 20%를 더하고 남쪽 경계에서 높이의 20%를 뺀다.
- 동쪽 경계에 너비의 20%를 더하고 서쪽 경계에서 너비의 20%를 뺀다.
- 확장 전후 중심은 같으며 전체 위도 폭·경도 폭은 각각 원래의 1.4배이다. 전체 20% 증가나 면적 20% 증가로 해석하지 않는다.
- 예를 들어 원래 위도 범위가 33.43~33.47, 경도 범위가 126.91~126.95이면 확장 범위는 위도 33.422~33.478, 경도 126.902~126.958이다.
- 확장 계산은 한 곳에 모아 장소와 길바닥 방명록, 상세·간소 응답에 동일한 결과를 재사용한다.
- 좌표가 확장 경계 안에 있거나 경계와 같으면 포함한다. 원래 화면 밖이더라도 확장 범위 안이면 제외하지 않는다.
- 거리나 원형 반경으로 화면 포함 여부를 판단하지 않는다.
- 사용자 좌표가 화면이나 확장 범위 밖이어도 조회 영역을 옮기거나 요청을 거부하지 않는다.

## 4. 장소와 길바닥 방명록 조회

- 장소는 확장 범위 안에 좌표가 있는 LOCATION 전체를 대상으로 한다.
- 미션·방명록·쿠폰 존재 여부나 현재 사용자의 완료·방문 여부로 장소를 제외하지 않는다.
- 길바닥 방명록은 ROAD_GUESTBOOK 자체 좌표에 같은 확장 범위를 적용한다. 장소 좌표나 사용자 방문 기록 좌표로 대체하지 않는다.
- 현재 스키마에서는 장소 방명록과 길바닥 방명록이 공통 GUESTBOOK과 PK를 공유한다. 응답 ID는 해당 guestbook_id를 사용한다.
- 조회 결과가 없는 종류는 빈 목록으로 구성한다. 한 종류가 비어 있어도 다른 종류의 조회 결과는 반환한다.
- 기존 FastAPI의 deleted_at 컬럼을 현재 테이블에 있는 것처럼 사용하지 않는다.
- 길바닥 방명록은 공통 GUESTBOOK.status가 ACTIVE인 기록만 상세·간소 응답에 포함한다.
- 장소별 방명록 수와 본인의 미션 방명록 작성 여부에도 동일하게 ACTIVE 조건을 적용한다. 비활성 방명록만 있어도 장소 자체는 제외하지 않는다.

## 5. 활성 미션 연결과 데이터 정합성

- 장소와 연결된 TREASURE_MISSION 및 COOPERATIVE_MISSION을 장소 ID 기준으로 조회하며 활성 미션만 응답 후보에 포함한다.
- 문화 미션은 장소를 참조하지 않으므로 지도 장소의 미션 후보에 포함하지 않는다.
- 장소당 활성 미션은 유형을 합쳐 최대 한 건이어야 한다. 같은 유형의 두 건도 중복에 해당한다.
- 활성 미션이 없으면 상세 응답의 미션을 비우고, 간소 응답의 미션 ID·유형도 함께 비운다. 비활성 미션만 있어도 장소 자체는 유지한다.
- 연결된 활성 미션이 두 건 이상이면 하나를 임의로 선택하거나 덮어쓰지 않는다. 해당 요청 전체를 실패시킨다.
- 중복이 발견되면 장소 ID, 충돌한 공통 미션 ID 목록과 유형을 오류 로그에 남긴다. 인증 토큰이나 외부 API 키는 로그에 남기지 않는다.
- 데이터 정합성 실패는 기존 공통 서버 예외 처리로 전달하고 별도 도메인 오류를 만들지 않는다. 구체적인 내부 원인은 응답에 노출하지 않는다.
- 상세·간소 응답 모두 같은 중복 검증을 거친다. 후보를 단일 값 맵으로 덮어쓰기 전에 중복을 확인한다.
- 미션 식별자는 MISSION.id이며 세부 미션의 mission_id와 동일하다. 장소 ID나 팀·개인 진행도 ID를 사용하지 않는다.
- 미션 유형·제목은 연결된 MISSION_TYPE의 type·title을 사용한다.

## 6. 사용자별 미션 완료와 방명록 작성 여부

- 이 항목은 상세 응답에서만 계산한다.
- 완료 여부는 기존 공통 MissionCompletionChecker와 동일한 기준을 재사용한다.
- 보물찾기는 현재 사용자의 해당 미션 진행도가 완료인 경우 완료로 판단한다.
- 협동 미션은 현재 사용자의 수락된 참가 기록에 완료된 해당 미션 팀 진행도가 연결되어 있는 경우 완료로 판단한다.
- 진행 기록이 없거나 진행 중인 이력만 있으면 미완료이며, 반복 진행 중이어도 과거 완료 이력이 하나 이상 있으면 완료이다.
- 협동 참가자·진행도에 현재 없는 삭제 플래그 조건을 추가하지 않는다. 실제로 남아 있는 기록을 기준으로 판단한다.
- 미션 미완료이면 방명록 작성 여부는 판정하지 않고 비운다.
- 미션 완료이면 현재 사용자가 해당 장소와 공통 미션을 참조하여 작성한 활성 장소 방명록이 존재하는지 확인한다. 비활성 방명록은 작성 이력에 포함하지 않는다.
- 현재 스키마에서는 LOCATION_GUESTBOOK.mission_id, visited_location으로 연결된 장소 ID, 공통 GUESTBOOK.user_id를 함께 사용한다.
- 같은 장소의 다른 미션 방명록, 다른 사용자의 방명록, 길바닥 방명록을 본인의 해당 미션 작성 이력으로 보지 않는다.
- 장소 참조가 없는 장소 방명록은 특정 장소의 작성 이력으로 추정하여 연결하지 않는다.

## 7. 장소별 방명록 수와 길바닥 방명록 이미지

- 장소별 방명록 수는 LOCATION_GUESTBOOK의 visited_location으로 연결된 장소 ID를 기준으로 집계한다.
- 해당 장소에 연결된 모든 사용자의 활성 장소 방명록을 집계하며 미션 연결 여부는 구분하지 않는다. 비활성 방명록과 길바닥 방명록은 장소 집계에 포함하지 않는다.
- 장소 참조가 없는 방명록은 임의의 장소에 집계하지 않는다. 해당 장소의 결과가 없으면 개수는 영으로 구성한다.
- 길바닥 방명록의 위치 별칭은 ROAD_GUESTBOOK에서, 첨부 이미지 URL은 연결된 공통 GUESTBOOK에서 가져온다.
- 현재 content_img_url은 URL 문자열 컬럼이므로 기존 FastAPI의 이미지 배열로 해석하지 않는다. 저장된 URL을 대표 첨부 이미지로 사용하고 없으면 비운다.
- 길바닥 방명록 이미지에 TourAPI 장소 이미지를 대신 사용하지 않는다. 업로드·URL 변경도 수행하지 않는다.

## 8. 현재 사용자의 수령 쿠폰

- 이 항목은 상세 응답에서만 조회한다.
- 현재 사용자의 ACQUIRED_COUPON과 연결된 COUPON을 기준으로 실제 획득한 쿠폰만 조회한다.
- 쿠폰의 location_id가 이번 응답 대상 장소의 ID와 일치할 때만 해당 장소에 연결한다. 장소명 일치나 유사 문자열로 연결하지 않는다.
- 쿠폰이 장소에 정의되어 있어도 현재 사용자의 획득 기록이 없으면 반환하지 않는다.
- 다른 사용자의 쿠폰이나 사용처 장소가 없는 쿠폰을 임의의 장소에 붙이지 않는다.
- 기존 FastAPI의 reward_detail이나 진행도별 쿠폰 지급 플래그를 조합하여 획득 이력을 복원하지 않는다.
- 현재 획득 테이블의 쿠폰·사용자 복합키 한 건을 실제 수령 한 건으로 취급한다. 같은 획득 기록이 조인으로 중복되지 않도록 한다.
- 서로 다른 쿠폰을 같은 장소에서 사용할 수 있으면 각각 반환하며 금액이 같다는 이유로 합치지 않는다. 같은 쿠폰을 여러 미션이 참조한다는 이유로 획득 기록을 늘려 반환하지 않는다.
- 금액은 연결된 쿠폰에서, 사용처 주소는 해당 장소에서 가져온다.
- 해당 장소에서 사용할 수 있는 수령 쿠폰이 없으면 필드를 생략하거나 빈 배열로 바꾸지 않고 비운다.

## 9. 거리·예상 소요 시간과 TourAPI 대표 이미지

- 상세 응답에서 각 장소의 거리·시간은 요청의 실제 사용자 좌표와 장소 좌표로 기존 공통 TravelEstimator를 호출한다.
- 지도 중심·좌상단·우하단·확장 경계를 거리 계산의 출발점으로 쓰지 않는다.
- 기존 공통 로직의 직선거리·도보 시간 추정·정수 반올림 기준을 그대로 사용하고 지도 서비스에 공식을 복제하지 않는다.
- 공통 거리·시간 계산에 남아 있는 추후 계산 방식 교체 TODO를 유지한다. 별도의 지도 전용 계산 정책을 추가하지 않는다.
- 대표 이미지는 장소의 content_id로 기존 TourApiClient를 호출하여 구한다. 장소 방명록 수·이미지 유무와는 무관하다.
- 기존 공통 이미지 로직처럼 원본 firstimage를 우선하고 없으면 축소 이미지 firstimage2를 사용한다.
- 이미지가 없거나 TourAPI 조회가 실패하면 해당 장소의 이미지 URL만 비우고 나머지 지도 조회는 정상 처리한다.
- 같은 요청의 같은 content_id를 불필요하게 반복 호출하지 않는다. 기존 공통 클라이언트를 사용하며 지도에 외부 HTTP 호출 코드를 중복 구현하지 않는다.

## 10. 간소 응답과 조회 범위의 일관성

- 간소 응답에서는 같은 장소·길바닥 방명록과 검증된 활성 미션 연결 결과를 식별자·좌표 중심으로 변환한다.
- 상세 응답의 공통 미션 ID·유형과 간소 응답의 공통 미션 ID·유형은 같은 장소에 대해 일치해야 한다.
- 클러스터링 플래그는 서버의 군집 생성이나 조회 반경 변경을 의미하지 않는다. 항목을 합치거나 임의의 대표 좌표·새 클러스터 ID를 만들지 않는다.
- 간소 응답에서는 거리·시간, 사용자 완료 이력·작성 여부, 방명록 수·상세 콘텐츠, 수령 쿠폰, TourAPI 이미지를 조회·계산하지 않는다.
- 상세 전용 필드를 단순히 비운 객체로 나열하지 않고 간소 응답에 정의된 항목만 반환한다.
- 간소 응답에서도 현재 사용자 존재 확인·요청 검증·활성 미션 중복 검증은 생략하지 않는다.

## 11. 조회 조합과 데이터 보존

- 장소 ID 목록을 기준으로 미션·완료 이력·방명록 집계·작성 여부·획득 쿠폰을 묶어서 조회하고 장소별로 조합한다. 장소마다 같은 DB 조회를 반복하지 않는다.
- 장소 목록이 비어 있으면 장소 관련 후속 조회·이미지 호출을 생략하되 길바닥 방명록 결과는 유지한다.
- 공통 조회 범위 계산·완료 판정·거리·시간·이미지 조회 책임은 재사용 가능한 컴포넌트로 유지한다.
- 조회 전용 트랜잭션으로 처리하며 방문 시각·미션 진행도·완료·보상 상태·쿠폰 획득·방명록을 생성하거나 변경하지 않는다.
- 반복 요청은 매번 현재 저장된 정보로 조회하며 조회 자체로 보상이나 쿠폰을 추가 지급하지 않는다.
- 미션 중복이나 예상하지 못한 DB 오류를 빈 목록이나 미션 없음으로 숨기지 않는다. 외부 이미지의 부가 정보 실패만 위 규칙에 따라 부분적으로 허용한다.

# 지도 모달 조회 비즈니스 규칙

## 1. 요청과 현재 사용자 확인

- 요청 형식과 유형별 응답·오류 계약은 [지도 모달 조회 API 명세](./API_SPEC.md#지도-모달-조회-api)를 따른다.
- 인증된 현재 사용자 ID를 사용하며, 조회 대상 ID를 사용자 ID나 미션 ID로 해석하지 않는다.
- 인증 정보에 해당하는 사용자가 실제로 존재하는지 확인한다. 없으면 기존 공통 인증 오류 처리에 전달한다.
- 대상 유형에 따라 장소 또는 길바닥 방명록 중 하나만 조회한다. 두 유형의 데이터를 합쳐 하나의 응답으로 구성하지 않는다.

## 2. 처리 순서

1. 요청값과 인증된 현재 사용자를 확인한다.
2. 대상 유형에 맞는 장소 또는 활성 길바닥 방명록을 조회한다.
3. 대상이 없으면 `MAP_MODAL_TARGET_NOT_FOUND`로 중단한다.
4. 실제 사용자 좌표와 조회 대상의 좌표로 공통 거리·예상 이동 시간을 계산한다.
5. 장소이면 활성 미션 연결의 중복 여부를 검증한다.
6. 장소의 대표 이미지와 방문 여부, 연결된 활성 미션의 완료·보상 수령 여부를 구성한다.
7. 장소에 연결된 활성 장소 방명록의 전체 개수와 최신 최대 세 건을 조회하고 작성자·온보딩 결과·참조 미션 정보를 조합한다.
8. 길바닥 방명록이면 작성자 닉네임과 공통 방명록의 저장된 콘텐츠를 조합한다.
9. 선택된 유형의 응답만 반환하며 조회 과정에서 데이터를 변경하지 않는다.

## 3. 조회 대상과 좌표

- 장소는 LOCATION.id로 조회한다. 미션이나 방명록이 없어도 존재하는 장소 자체를 제외하지 않는다.
- 길바닥 방명록은 ROAD_GUESTBOOK.guestbook_id로 조회하며 연결된 공통 GUESTBOOK.status가 ACTIVE인 경우만 허용한다.
- 현재 길바닥 방명록은 공통 GUESTBOOK과 PK를 공유한다. 별도의 ROAD_GUESTBOOK.id 또는 deleted_at 컬럼을 가정하지 않는다.
- 요청 유형의 대상이 없으면 다른 유형에서 같은 ID를 찾아 대신 반환하지 않는다.
- 비활성 길바닥 방명록은 없는 대상과 같은 도메인 오류로 처리한다.
- 장소 모달의 목적지 좌표는 LOCATION의 좌표를 사용하고, 길바닥 방명록 모달은 ROAD_GUESTBOOK 자체 좌표를 사용한다.
- 현재 사용자 좌표를 지도 중심이나 이전 지도 홈 요청 좌표로 대체하지 않는다. 모달 조회에 지도 홈의 화면 확장 범위 조건을 추가하지 않는다.
- 공통 TravelEstimator의 거리·도보 시간 추정·정수 반올림 기준을 재사용한다. 기존 공통 모듈의 거리·시간 계산 교체 TODO를 유지하며 모달 전용 계산 공식을 중복 구현하지 않는다.

## 4. 장소 기본 정보·이미지·방문 여부

- 장소명과 분류는 조회한 LOCATION의 title·category를 사용한다.
- 대표 이미지는 LOCATION.content_id로 기존 TourApiClient를 호출한다. firstimage를 우선하고 없으면 firstimage2를 사용한다.
- 이미지가 없거나 외부 조회가 실패하면 이미지 URL만 비우고 모달의 나머지 정보는 정상 구성한다.
- 장소 방명록의 첨부 이미지를 장소 대표 이미지로 대신 사용하지 않는다.
- 방문 여부는 현재 사용자와 해당 장소가 일치하는 VISITED_LOCATION의 존재 여부로 판단한다.
- 미션 완료·보상 수령·방명록 작성 여부로 방문 기록을 추정하거나 방문 기록을 새로 생성하지 않는다.

## 5. 연결된 활성 미션과 완료 여부

- 해당 장소를 참조하는 활성 보물찾기·협동 미션을 대상으로 한다. 장소를 참조하지 않는 문화 미션은 연결 후보에 포함하지 않는다.
- 유형을 합쳐 활성 미션이 한 건이면 단일 미션 정보로 조합한다. 활성 미션이 없거나 비활성 미션만 있으면 미션 정보를 비운다.
- 같은 유형 내 중복도 포함해 활성 미션이 여러 건이면 임의로 하나를 선택하지 않는다. 장소 ID, 충돌한 공통 미션 ID 목록·유형을 오류 로그에 남기고 기존 공통 서버 예외 처리에 전달한다.
- 미션 ID는 공통 MISSION.id를 사용한다. 현재 세부 미션의 mission_id와 같은 값이며, 장소 ID·미션 진행도 ID로 대체하지 않는다.
- 미션 유형·제목은 연결된 MISSION_TYPE의 type·title을 사용한다. 이전 FastAPI의 세부 미션 ID나 MISSION.mission_title을 현재 컬럼처럼 사용하지 않는다.
- 완료 여부는 기존 공통 MissionCompletionChecker의 기준을 재사용하며 보상 수령 여부로 대신 판단하지 않는다.
- 보물찾기는 현재 사용자의 해당 미션 진행도 상태로 판단한다. 협동 미션은 현재 사용자의 수락된 참가 기록과 연결된 완료 팀 진행도를 기준으로 판단한다.
- 협동 미션은 가장 최근 팀 하나만 확인하지 않고 완료 이력이 하나라도 있는지 판정한다. 현재 없는 삭제 플래그 조건을 추가하지 않는다.

## 6. 전체 보상과 현재 사용자 수령 여부

- 보상 원본은 연결된 보물찾기·협동 미션의 ar_character_id·point·coupon_id를 기준으로 기존 공통 보상 조합 기준을 따른다. 이전 FastAPI의 reward_detail JSON을 현재 컬럼처럼 사용하지 않는다.
- 이 모달은 미션에 설정된 전체 보상을 표시한다. 미션 홈 조회의 남은 보상만 반환하는 동작으로 대체하지 않는다.
- 이미 지급된 보상도 보상 정보는 유지하고 해당 항목의 수령 여부만 지급된 상태로 표시한다. 보상이 설정되지 않은 항목만 비운다.
- AR 캐릭터 보상은 연결된 캐릭터의 ID·이름·이미지 URL을 사용한다. 작성자의 온보딩 프로필 이미지와 구분한다.
- 쿠폰은 연결된 쿠폰의 금액과 사용처 장소 이름을 사용한다. 쿠폰은 있으나 사용처 장소가 없으면 사용처만 비운다.
- 수령 여부는 현재 사용자 ID와 공통 미션 ID로 식별되는 MISSION_REWARD_STATUS를 기준으로 한다.
- AR 캐릭터·포인트·쿠폰은 각각 ar_character_reward_granted·point_reward_granted·coupon_reward_granted를 사용한다. 상태 행이 없으면 설정된 보상의 수령 여부는 모두 미지급으로 판단한다.
- 다른 사용자의 보상 상태를 섞지 않는다. 이전 진행도의 개별 지급 플래그를 합치거나 보유 캐릭터·쿠폰만으로 해당 미션의 지급 이력을 추정하지 않는다.
- 상태 행이 없더라도 조회 중 새로 만들지 않는다. 보상 지급·포인트 갱신·캐릭터 및 쿠폰 획득 기록 생성도 수행하지 않는다.

## 7. 장소 방명록 전체 개수와 최신 세 건

- LOCATION_GUESTBOOK의 visited_location_id로 연결된 VISITED_LOCATION.location_id가 대상 장소와 일치하고 공통 GUESTBOOK.status가 ACTIVE인 기록만 대상으로 한다.
- 모든 작성자의 대상 장소 방명록을 포함하며 미션 연결 유무로 제외하지 않는다. 길바닥 방명록과 장소 참조가 없는 장소 방명록은 집계·목록에 포함하지 않는다.
- 같은 필터의 전체 개수를 별도로 집계한다. 최신 세 건의 목록 길이로 전체 개수를 대신하지 않는다.
- 최신 목록은 공통 GUESTBOOK.visited_at 내림차순, 같은 방문일이면 GUESTBOOK.id 내림차순으로 제한한다. created_at이나 saved_at으로 순서를 대체하지 않는다.
- 방명록이 없으면 전체 개수는 영이고 목록은 비어 있다. 방명록 부재를 대상 장소 없음으로 처리하지 않는다.
- 목록의 방명록 ID는 공통 GUESTBOOK.id이며 LOCATION_GUESTBOOK이 공유하는 guestbook_id와 같다.
- 대표 첨부 이미지는 GUESTBOOK.content_img_url의 단일 문자열을 사용한다. 배열의 첫 항목을 추출하는 로직이나 TourAPI 이미지 대체를 추가하지 않는다.
- 글과 방문일은 공통 GUESTBOOK의 저장값을 사용한다. 참조 미션 제목은 LOCATION_GUESTBOOK.mission_id로 연결된 미션 유형의 제목을 사용하며 연결된 미션이 없으면 비운다.

## 8. 작성자 정보와 탈퇴 사용자

- 장소 방명록 목록의 작성자 ID·닉네임은 공통 GUESTBOOK.user_id로 연결된 USER에서 가져온다.
- 작성자 이미지는 USER.onboarding_result_id로 연결된 ONBOARDING_RESULT.profile_img_url을 사용한다. 획득한 AR 캐릭터 중 하나를 임의로 고르지 않는다.
- 작성자는 있으나 온보딩 결과가 없으면 작성자 이미지만 비운다. 닉네임이 없으면 임의의 기본 닉네임을 만들지 않는다.
- 작성자 연결이 없으면 장소 방명록 목록의 작성자 ID·닉네임·이미지를 모두 비운다.
- 대상 장소에 연결된 활성 방명록은 작성자 연결이 없다는 이유로 집계·최신 목록에서 제거하지 않는다. 작성자·온보딩 결과를 조회하는 과정에서 해당 방명록이 누락되지 않도록 한다.
- 길바닥 방명록도 작성자가 없다는 이유로 제외하지 않으며 작성자 닉네임만 비운다. 두 유형의 기존 응답에 없는 작성자 필드를 추가하지 않는다.

## 9. 길바닥 방명록 콘텐츠

- 위치 별칭과 목적지 좌표는 ROAD_GUESTBOOK에서 가져오고 방문일·사진·글·음성·날씨·색상은 연결된 공통 GUESTBOOK에서 가져온다.
- 사진과 음성은 각각 content_img_url·content_audio_url의 단일 문자열을 사용한다. 배열로 감싸거나 여러 URL로 분리하지 않는다.
- 콘텐츠가 없으면 해당 값을 비우고 응답 키는 유지한다. 저장된 값이 있으면 의미나 내용을 변경하지 않는다.
- 방문일을 작성·저장 시각으로 대체하지 않는다. 길바닥 방명록의 이미지에 TourAPI 장소 이미지를 대신 넣지 않는다.

## 10. 공통 처리와 데이터 보존

- 현재 사용자 확인·거리·시간 계산·완료 판정·보상 조합·이미지 조회는 기존 공통 기준을 재사용한다. 대상 유형에 따라 응답 구성 책임만 분리한다.
- 최신 방명록은 최대 세 건만 조회한다. 작성자·온보딩 결과·참조 미션을 방명록마다 반복 조회하지 않도록 필요한 단일 연관 조회나 일괄 조회를 사용한다.
- 조회 전용 트랜잭션으로 처리한다. 반복 요청은 현재 저장된 정보를 조회할 뿐 방문 기록·방명록·미션 진행도·보상 상태·사용자 보유 보상을 생성하거나 수정하지 않는다.
- 미션 중복이나 예기치 않은 DB 오류를 미션 없음·빈 방명록으로 숨기지 않는다. 부가 이미지 조회 실패만 위 규칙에 따라 부분적으로 허용한다.

# 지도 장소 상세 조회 비즈니스 규칙

## 1. 요청과 현재 사용자 확인

- 요청·응답과 오류 계약은 [지도 장소 상세 조회 API 명세](./API_SPEC.md#지도-장소-상세-조회-api)를 따른다.
- 인증된 현재 사용자 ID와 요청의 장소 ID를 사용한다. 해당 사용자가 실제로 존재하는지 기존 공통 인증 처리 기준으로 확인한다.
- 요청 좌표·페이징 값의 필수 여부·형식·범위는 기존 DTO Bean Validation 방식으로 검증한다. 기존 검증과 중복되는 별도 유한성 검증을 추가하지 않는다.
- 이전 지도 홈·모달 요청이나 응답을 서버에 보관해 사용자 좌표·조회 결과로 대신 사용하지 않는다.

## 2. 처리 순서

1. 요청값과 인증된 현재 사용자를 확인한다.
2. 요청 ID의 장소를 조회하고 없으면 `LOCATION_NOT_FOUND`로 중단한다.
3. 장소 기본 정보·사용자 기준 거리·예상 이동 시간·방문 여부를 구성한다.
4. 장소의 TourAPI 설명과 상세 이미지 목록을 조회한다.
5. 별도 추천 모듈에서 활성 보물찾기·협동 미션의 완료 여부를 확인하고 사용자와 가까운 후보를 최대 세 건 선정한다.
6. 추천 미션들의 공통 정보·전체 보상·사용자 수령 여부·장소명·대표 이미지를 조합한다.
7. 현재 장소의 활성 방명록 페이지를 조회하고 작성자·온보딩 결과·참조 미션을 조합한다.
8. 현재 장소에 연결된 활성 미션의 중복을 확인하고 공통 정보·완료·전체 보상과 수령 여부를 구성한다.
9. 방명록 페이지 정보와 장소 상세 응답을 반환한다. 조회 중에는 상태를 변경하지 않는다.

## 3. 장소 기본 정보·거리·방문 여부

- LOCATION.id로 장소를 조회하며 title·category·address를 기본 정보로 사용한다. 미션이나 방명록이 없어도 장소를 제외하지 않는다.
- 요청의 실제 사용자 좌표와 LOCATION.latitude·longitude로 기존 공통 TravelEstimator를 사용한다. 거리 공식·이동 속도·정수 반올림 규칙을 지도 상세 서비스나 DTO에 복제하지 않는다.
- 공통 모듈의 거리·시간 계산 교체 TODO를 유지한다.
- 서비스가 계산 결과의 거리·시간 값을 꺼내 DTO에 전달하는 기존 다른 도메인의 응답 구성 방식을 따른다.
- 방문 여부는 현재 사용자와 해당 장소가 일치하는 VISITED_LOCATION의 존재 여부로만 판단한다. 방명록·미션 완료·보상으로 방문을 추정하거나 조회 중 방문 기록을 생성·갱신하지 않는다.

## 4. TourAPI 장소 설명과 상세 이미지

- 설명·이미지의 조회 키는 LOCATION.content_id이다. 장소명 기반 검색으로 대신 조회하지 않는다.
- 설명은 기존 TourApiClient의 장소 설명 조회를 재사용하며 detailCommon2.overview를 사용한다. HTML 엔티티를 일반 문자로 바꾸고 HTML 태그를 제거한 뒤 연속 공백·줄바꿈을 하나의 공백으로 정리하고 앞뒤 공백을 제거한다.
- 정리한 설명이 비어 있거나 조회에 실패하면 설명을 비운다.
- 상세 이미지는 TourAPI detailImage2에 contentId를 전달하고 originimgurl을 사용한다. detailCommon2.firstimage·firstimage2의 대표 이미지 한 장으로 상세 이미지 목록을 대신 구성하지 않는다.
- 숫자로 해석 가능한 serialnum을 오름차순 정렬하며 같은 순번은 외부 응답 순서를 유지한다. 순번을 해석할 수 없는 항목은 숫자 순번 뒤에서 원래 순서를 유지하는 기존 FastAPI 기준을 따른다.
- 문자열이 아니거나 공백뿐인 URL을 제외하고 저장된 URL 값이 같은 항목을 중복 제거한 뒤 최대 다섯 장을 선택한다. 정렬·중복 제거보다 먼저 다섯 장으로 제한하지 않는다. 유효한 URL 문자열 자체는 기존 FastAPI처럼 그대로 유지한다.
- 이미지가 다섯 장보다 적으면 있는 만큼 반환하고 유효한 이미지가 없으면 목록을 비운다. 공개 응답에서는 빈 배열 대신 null로 표현한다.
- 공통 TourAPI 클라이언트에 상세 이미지 조회 기능이 없으면 기존 클라이언트 형식으로 추가하여 다른 도메인에서도 재사용한다. 지도 서비스에 별도 외부 HTTP 호출 코드를 만들지 않는다.
- 외부 인증키 미설정·통신 오류·잘못된 JSON·빈 응답·값 누락은 설명 또는 이미지의 부가 정보 실패로 처리한다. 해당 필드만 비우고 전체 상세 조회를 실패시키지 않는다.

## 5. 주변 미션 후보와 가까운 세 건 선정

- 후보는 장소가 연결된 ACTIVE 보물찾기·협동 미션이다. INACTIVE와 장소 참조가 없는 미션, 문화 미션은 추천하지 않는다.
- 현재 사용자가 완료한 미션은 기존 공통 MissionCompletionChecker 기준으로 제외한다. 보상 수령 여부만으로 완료를 판단하지 않는다.
- 현재 조회 장소의 미션도 위 조건을 만족하면 후보에 포함할 수 있다. 현재 장소라는 이유로 임의 제외하지 않는다.
- 두 유형의 후보를 합친 뒤 요청 사용자 좌표에서 각 미션 장소까지의 공통 거리 계산값으로 가까운 순서대로 최대 세 건을 선정한다. 현재 상세 장소를 거리 계산의 원점으로 사용하지 않는다.
- 유형마다 세 건 또는 유형마다 한 건씩 선정하지 않는다. 같은 공통 미션 ID가 추천에 중복되지 않도록 한다.
- 후보가 세 건 미만이면 있는 만큼, 없으면 빈 목록을 반환한다. 별도 반경 조건이나 완료 미션을 이용한 부족분 보충 정책을 만들지 않는다.
- 후보 조회·완료 제외·거리순 선정은 별도 모듈이나 함수에서 담당한다. 기존 홈 MissionRecommender의 유형별 한 건 선정 결과를 그대로 사용하지 않고, 공통으로 재사용할 수 있는 후보 조회·거리 계산 부분을 활용한다. 기존 홈 추천의 유형별 선정 동작은 변경하지 않는다.
- 기존 FastAPI의 임시 추천이 정식 추천으로 교체될 예정인 점을 유지하여 해당 추천 코드에 `// TODO: 추후 정식 추천 로직으로 교체한다.`를 명시한다. 현재 동작은 위 거리순 선정 기준이다.

## 6. 미션 공통 정보·완료와 전체 보상

- 현재 장소의 미션과 추천 미션 모두 공통 MISSION.id를 사용한다. 유형별 상세의 mission_id와 같은 값이며 이전 FastAPI의 별도 상세 ID를 가정하지 않는다.
- 유형·제목·설명은 연결된 MISSION_TYPE.type·title·description을 사용한다. 이전 MISSION.mission_title·description 컬럼을 현재 스키마에 있다고 가정하지 않는다.
- 완료 여부는 지도 모달과 동일한 공통 판정기를 재사용한다. 보물찾기는 본인의 진행도 상태, 협동은 ACCEPTED 참가 기록과 연결된 팀 완료 이력을 사용한다.
- 여러 협동 팀 이력이 있으면 가장 최근 한 팀만 보지 않고 완료 이력이 하나라도 있는지 확인한다. 현재 없는 삭제 플래그를 추가하지 않는다.
- 보상 원본은 유형별 상세의 AR 캐릭터·포인트·쿠폰 설정이며, 지급 여부는 현재 사용자·공통 미션의 MISSION_REWARD_STATUS를 사용한다.
- 각 지급 플래그를 해당 보상의 수령 여부에 반영한다. 상태 행이 없으면 미지급이며 조회 중 새로 만들지 않는다.
- 전체 보상 정보는 이미 지급된 항목도 유지한다. 미설정 항목만 비우고, 포인트가 영으로 설정되어 있으면 그 값을 유지한다. 보상이 전혀 없어도 전체 보상 객체는 유지한다.
- 쿠폰은 있으나 사용처 장소가 없으면 쿠폰을 제외하지 않고 사용처 이름만 비운다.
- 지도 모달·현재 장소 미션·추천 미션에서 완료 판정과 보상 조합을 복제하지 않는다. 필요한 공통 처리만 기존 코드 형식에 맞춰 재사용한다.

## 7. 추천 미션의 장소 정보와 대표 이미지

- 각 추천 미션에 연결된 장소의 이름과 content_id를 사용한다. 현재 상세 조회 장소의 이름·이미지를 모든 추천 항목에 넣지 않는다.
- 대표 이미지는 기존 TourApiClient의 대표 이미지 조회를 사용하고 firstimage를 우선하며 없으면 firstimage2를 사용한다.
- 대표 이미지가 없거나 조회에 실패해도 미션 항목을 유지하고 이미지만 비운다.
- 같은 요청의 같은 content_id·공통 미션 정보를 반복 조회하지 않도록 기존 조회 결과를 재사용한다. 전체 후보의 외부 이미지를 먼저 조회하지 않고 선정된 후보만 구성한다.

## 8. 장소 방명록 페이지 조회

- LOCATION_GUESTBOOK.visited_location_id로 연결된 VISITED_LOCATION.location_id가 대상 장소와 일치하고 공통 GUESTBOOK.status가 ACTIVE인 기록만 조회한다.
- 모든 작성자의 방명록을 포함하고 미션 참조 유무로 제외하지 않는다. INACTIVE·길바닥 방명록·장소 참조 없음·다른 장소의 방명록은 포함하지 않는다.
- 정렬은 GUESTBOOK.visited_at 내림차순, 같은 방문일에는 GUESTBOOK.id 내림차순이다. 저장·생성 시각으로 정렬을 대신하지 않는다.
- 페이지 번호는 영부터 시작하고 생략 시 첫 페이지, 크기는 생략 시 스무 건이다. 요청 페이지와 크기로 DB 조회 범위를 제한하며 전체 엔티티를 가져와 Java에서 잘라내지 않는다.
- 다음 페이지가 있는지 판정할 정보만 추가로 확인한다. 전체 개수·전체 페이지 수를 응답에 요구하지 않으므로 이를 위해 불필요한 전체 개수 집계를 추가하지 않는다.
- 반환 방명록은 요청 크기 이하이고 다음 페이지 판정용 추가 항목은 공개 목록에 포함하지 않는다. 실제 반환 개수와 무관하게 페이지 정보의 크기는 요청 크기를 유지한다.
- 방명록이 없거나 페이지 범위를 넘으면 빈 목록과 다음 페이지 없음으로 구성한다. 이를 장소 없음 오류로 처리하지 않는다.
- 페이지별 조회는 매 요청 시점의 현재 데이터를 기준으로 하며 사용자별 조회 세션이나 방명록 스냅샷을 생성하지 않는다.

## 9. 방명록 콘텐츠와 작성자

- 방명록 ID는 공통 GUESTBOOK.id이며 LOCATION_GUESTBOOK의 공유 PK와 같다. 방문일·글·단일 첨부 이미지는 공통 방명록의 저장값을 사용한다.
- content_img_url은 현재 단일 문자열이므로 배열로 해석하거나 TourAPI 이미지로 대신하지 않는다.
- 참조 미션 제목은 LOCATION_GUESTBOOK.mission으로 연결된 MISSION_TYPE.title을 사용하며 미션이 없으면 비운다.
- 작성자 ID·닉네임은 GUESTBOOK.user, 프로필 이미지는 USER.onboardingResult.profileImgUrl을 사용한다. 획득 AR 캐릭터 이미지나 이전 USER.ar_character_id를 사용하지 않는다.
- 작성자 연결이 없으면 작성자 필드를 모두 비우고, 온보딩만 없으면 이미지만 비운다. 임의의 기본 닉네임을 추가하지 않는다.
- 작성자·온보딩·미션이 없어도 ACTIVE 방명록은 페이지에 포함한다. 이 연관을 조회하기 위해 방명록이 누락되거나 방명록마다 같은 연관 조회가 반복되지 않도록 한다.

## 10. 현재 장소의 활성 미션

- 현재 장소를 참조하는 ACTIVE 보물찾기·협동 미션을 합쳐 조회한다. 없거나 비활성 미션만 있으면 현재 장소의 미션을 비우되 장소 상세 응답은 유지한다.
- 활성 미션이 한 건이면 위 공통 미션 상세 조합을 적용한다. 이미 완료한 미션도 현재 장소의 미션에는 포함한다.
- 같은 유형 내 중복을 포함해 활성 미션이 둘 이상이면 임의로 하나를 선택하지 않는다. 지도 모달과 같은 방식으로 장소 ID·충돌한 공통 미션 ID·유형을 로그로 남기고 기존 공통 서버 예외 처리에 전달한다.
- 현재 장소의 미션에는 최상위 장소 정보와 중복되는 장소 이름·대표 이미지를 추가하지 않는다.

## 11. 조회 전용 처리와 구현 일관성

- 기존 다른 도메인 서비스처럼 공개 메서드에서 문서의 조회·검증·조합·응답 순서가 보이도록 구현하고 변수 타입·주석 형식을 맞춘다. 공통 계산 결과는 응답에 필요한 값으로 꺼내 DTO에 전달한다.
- 공통 미션·보상·완료·거리·외부 이미지 처리는 기존 컴포넌트를 재사용한다. 불필요한 단건용 목록 래퍼나 새 추상화를 추가하지 않는다.
- 조회 전용 트랜잭션을 사용하고 방문 기록·방명록·미션 진행도·지급 상태·보유 보상을 생성하거나 수정하지 않는다. 반복 조회로 보상을 추가 지급하지 않는다.
- 미션 중복·예기치 않은 DB 실패를 빈 목록이나 미션 없음으로 숨기지 않는다. TourAPI 부가 정보의 실패만 위 기준대로 부분적으로 허용한다.

# 지도 검색 결과 조회 비즈니스 규칙

## 1. 요청과 현재 사용자 확인

- 요청·응답·오류 계약은 [지도 검색 결과 조회 API 명세](./API_SPEC.md#지도-검색-결과-조회-api)를 따른다.
- 인증된 현재 사용자 ID를 사용하고 실제 사용자가 존재하는지 기존 공통 인증 처리 기준으로 확인한다.
- 필수 검색어·좌표와 페이지 값은 기존 요청 DTO의 Bean Validation 방식으로 검증한다. 좌표 범위 어노테이션과 중복되는 유한성 검증을 추가하지 않는다.
- 인증이나 요청 검증에 실패하면 장소 검색·미션 조회·거리 계산·외부 이미지 조회를 진행하지 않는다.

## 2. 처리 순서

1. 검색어의 앞뒤 공백을 정리하고 요청값과 인증된 현재 사용자를 확인한다.
2. 장소 이름에 검색어가 포함되는 장소를 ID 오름차순으로 페이지 조회한다.
3. 현재 페이지의 장소들에 연결된 활성 보물찾기·협동 미션을 묶어서 조회한다.
4. 장소별 활성 미션이 최대 한 건인지 검증한다.
5. 현재 페이지 장소의 대표 이미지를 조회하고 실제 사용자 좌표 기준 거리를 계산한다.
6. 단일 장소 목록과 다음 페이지 정보를 반환한다. 조회 과정에서 데이터를 변경하지 않는다.

## 3. 검색어와 포함 검색

- 검색어 정규화는 기존 DTO compact constructor 방식으로 처리한다. 앞뒤 공백만 제거하고 내부 공백은 삭제·축약하지 않는다.
- 정리된 검색어가 비어 있으면 요청 검증 실패로 처리한다. 빈 검색어를 전체 장소 조회로 바꾸지 않는다.
- 검색 대상은 LOCATION.title이다. 주소·분류·미션 제목을 검색 대상으로 추가하지 않는다.
- 검색어 전체가 장소 이름의 연속된 부분 문자열로 포함되는지 비교한다. 검색어 앞뒤에 포함 검색용 패턴을 붙이는 방식이며 단어 분리·공백 제거·초성 검색·유사어 검색을 추가하지 않는다.
- 예를 들어 `제주 카페`에는 `제`, `제주`, `제주 카`가 포함되지만 `제주카`는 포함되지 않는다. `제주 `는 앞뒤 공백 정리 후 `제주`로 검색한다.
- 검색어의 `%`, `_` 및 LIKE 이스케이프 문자는 문자 자체로 비교되도록 이스케이프하고 파라미터 바인딩으로 전달한다. 사용자가 입력한 기호를 추가 와일드카드로 해석하지 않는다.
- 응답에는 LOCATION.title 원문을 사용한다. 비교를 위해 저장된 장소 이름을 수정하거나 새로운 정규화 값을 저장하지 않는다.
- 기존 FastAPI처럼 향후 검색 정책을 독립적으로 바꿀 수 있도록 검색 조건의 책임은 응답 구성과 분리한다. 해당 검색 코드에 `// TODO: 추후 검색 정책 변경 시 검색 로직을 교체한다.`를 명시한다. 현재 검색 기준은 위 문자열 포함 비교다.

## 4. 한글 조합과 입력 지연 처리

- 한글 조합 중인지 확인하고 마지막 입력 이후 300ms를 기다리는 debounce는 프론트 책임이다. 백엔드에 사용자별 입력 타이머나 요청 대기 로직을 추가하지 않는다.
- 입력이 이어지면 프론트는 대기 시간을 다시 시작하고 마지막 입력 기준으로 호출한다. 공백 문자가 입력된 시점에만 호출하는 방식이 아니다.
- 검색어를 모두 지우면 프론트는 요청을 생략하고 기존 결과를 비운다. 백엔드는 실제로 전달된 빈 검색어를 공통 요청 검증 기준으로 거절한다.
- 이전 검색 응답이 늦게 도착해 최신 검색 결과를 덮지 않도록 프론트가 이전 요청을 취소하거나 최신 요청의 응답만 반영한다.
- 검색어가 바뀌면 첫 페이지로 초기화하고, 다음 페이지 요청은 같은 검색어의 결과에 연결한다. 백엔드는 각 요청을 독립적으로 처리하며 이전 검색어·페이지를 보관하지 않는다.

## 5. 정렬과 페이지 조회

- 정렬 기준은 LOCATION.id 오름차순이다. 사용자 거리·장소명·미션 유무로 순서를 바꾸지 않는다.
- 사용자 위치는 검색 범위에 영향을 주지 않는다. 별도 거리 반경·지도 화면 범위·현재 장소 제외 조건을 추가하지 않는다.
- 페이지 번호는 영부터 시작하며 생략하면 첫 페이지, 페이지 크기는 생략하면 스무 건을 사용한다.
- DB에서 요청 범위를 제한해 조회하고 전체 검색 결과를 엔티티로 가져온 후 Java에서 페이지를 자르지 않는다.
- 다음 페이지가 있는지 확인하는 데 필요한 정보만 조회한다. 전체 개수·전체 페이지 수를 구하기 위한 집계는 추가하지 않는다.
- 다음 페이지 판정용 추가 행은 공개 장소 목록·미션 조회·거리·외부 이미지 조회 대상에 포함하지 않는다.
- 실제 결과가 요청 크기보다 적더라도 페이지 정보에는 요청 크기를 유지한다. 결과 없음·페이지 범위 초과는 빈 목록과 다음 페이지 없음으로 처리한다.
- 현재 페이지가 비어 있으면 장소별 미션·외부 이미지·거리의 후속 처리를 생략한다.

## 6. 장소별 단일 활성 미션

- 현재 페이지 장소 ID로 활성 보물찾기·협동 미션을 묶어 조회한다. 문화 미션은 연결 후보에 포함하지 않는다.
- 미션 없음과 INACTIVE만 존재하는 경우 모두 장소는 유지하고 미션만 비운다. 미션 유무로 별도 배열에 분류하지 않는다.
- 미션 ID는 공통 MISSION.id를 사용하며 유형별 상세의 mission_id와 같다. 이전 FastAPI의 별도 세부 미션 ID를 가정하지 않는다.
- 미션 유형·제목은 MISSION_TYPE.type·title을 사용한다.
- 현재 사용자의 완료 여부를 조건으로 미션을 제외하지 않는다. 이 API에서는 진행도·완료 판정·보상 지급 상태를 조회할 필요가 없다.
- 같은 유형 내 중복도 포함해 한 장소의 활성 미션이 둘 이상이면 임의 선택·덮어쓰기를 하지 않는다. 기존 지도 중복 검증을 재사용하여 장소 ID·충돌한 공통 미션 ID·유형을 로그로 남기고 공통 서버 예외 처리에 전달한다.
- 미션 정보를 장소마다 다시 조회하지 않고 장소 ID별로 조합한다. 미션 연관 조회가 페이지의 장소 개수·순서를 바꾸지 않도록 한다.

## 7. 대표 이미지와 거리

- 현재 페이지의 LOCATION.content_id로 기존 TourApiClient의 대표 이미지 조회를 사용한다. firstimage를 우선하고 없으면 firstimage2를 사용한다.
- 이미지가 없거나 외부 조회가 실패하면 해당 장소의 이미지만 비우고 검색은 정상 처리한다. 상세 이미지 목록이나 장소명 검색으로 대신 조회하지 않는다.
- 같은 요청의 동일 content_id는 불필요하게 반복 호출하지 않는다. 페이지에 반환하지 않는 장소의 이미지는 조회하지 않는다.
- 거리 계산은 요청 사용자 좌표와 장소 좌표로 기존 공통 TravelEstimator를 재사용한다. 거리 공식·반올림 기준을 서비스나 DTO에 중복 구현하지 않는다.
- 공통 모듈의 추후 거리 계산 교체 TODO를 유지한다. 응답에는 서비스가 계산한 거리 값만 전달하고 예상 이동 시간은 추가하지 않는다.

## 8. 빈 결과·예외와 데이터 보존

- 검색 결과가 없거나 다음 페이지에 장소가 없어도 도메인 없음 오류로 처리하지 않는다.
- 미션 중복·DB 조회 실패·예기치 않은 응답 구성 오류를 정상 빈 목록으로 숨기지 않는다. 구체적인 내부 원인은 공통 서버 오류 응답에 노출하지 않는다.
- 이 API의 오류는 기존 공통 요청 검증·인증·인가·서버 오류를 사용하며 별도 도메인 오류를 추가하지 않는다.
- 조회 전용 트랜잭션으로 처리하고 방문 기록·방명록·진행도·보상 상태·보유 보상을 생성하거나 변경하지 않는다. 검색어·검색 이력도 별도로 저장하지 않는다.
- 기존 다른 도메인의 서비스처럼 공개 메서드에 조회·검증·조합·응답 흐름을 순서대로 두고 변수 타입·주석 규칙을 맞춘다. 기존 공통 로직으로 충족되는 검증이나 불필요한 추상화를 추가하지 않는다.
