# 보물찾기 시작/이어하기 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져오며 요청에서 별도로 받지 않는다.
- 인증 정보에 해당하는 사용자가 없으면 `UNAUTHORIZED`로 처리한다.
- 요청 좌표는 최초 시작·재시작 시 보물 생성의 기준 위치로 사용한다.
- 이어하기에서도 요청 좌표를 검증하지만 저장된 보물 위치를 다시 계산하는 데 사용하지 않는다.

## 2. 보물찾기 미션 확인

- 요청의 `missionId`로 `TREASURE_MISSION.mission_id`에 해당하는 보물찾기 미션을 조회한다.
- 보물찾기 미션 ID는 공통 `MISSION.id`와 동일하다.
- 해당 보물찾기 미션이 없으면 `TREASURE_MISSION_NOT_FOUND`로 처리한다.
- 미션 상태가 `INACTIVE`이면 `TREASURE_MISSION_INACTIVE`로 처리한다.
- 존재 여부와 활성 상태 검증은 최초 시작·이어하기·재시작 모두에 동일하게 적용한다.
- 검증을 완료하기 전에는 진행도나 보물 아이템을 생성·초기화·삭제하지 않는다.
- 미션에 연결된 장소가 없어도 요청을 거절하지 않는다. 보물 생성 기준은 미션 장소가 아닌 사용자 좌표이다.

## 3. 현재 진행도 조회

- 현재 사용자 ID와 보물찾기 미션 ID로 `TREASURE_MISSION_PROGRESS`를 조회한다.
- 같은 사용자와 같은 미션의 진행도는 상태에 관계없이 최대 한 건만 유지한다.
- 진행도가 없으면 최초 시작, `IN_PROGRESS`이면 이어하기, `COMPLETED`이면 재시작으로 판단한다.
- 다른 사용자의 진행도와 보물 아이템은 조회하거나 변경하지 않는다.

## 4. 보물 생성 상수 및 좌표 생성

- 보물찾기 도메인의 별도 상수 정의에 생성 개수 `TREASURE_ITEM_COUNT = 3`과 등장 반경 `TREASURE_APPEAR_RADIUS_METER = 100`을 둔다.
- 서비스에 개수와 반경 숫자를 직접 반복하지 않고 공통 상수를 참조한다.
- 위 상수의 개수는 새 보물을 만들 때만 사용한다. 기존 보물 목록의 개수나 응답의 `treasureCount`를 강제로 3으로 바꾸지 않는다.
- 사용자 요청 좌표를 중심으로 하고 등장 반경을 반지름으로 하는 전체 원 내부에서 좌표를 무작위 생성한다.
- 기존 FastAPI의 미션 장소 중심·사용자 방향 반원 방식은 사용하지 않는다.
- 생성한 보물은 각각 사용자 요청 좌표에서 100m 이내에 있어야 한다.
- 위도·경도를 미터 단위 평면 좌표처럼 직접 더하지 않고 미터 단위 거리를 위도·경도로 변환한다.
- 생성 좌표는 위도·경도의 DB 허용 범위를 만족해야 한다.
- 좌표 생성은 서비스의 진행도 처리와 분리한 보물찾기 도메인의 별도 컴포넌트 또는 함수로 구현한다.
- 등장 반경은 기존 임시 정책을 유지하므로 해당 상수 위치에 `// TODO: 추후 확정된 보물 등장 반경으로 상수 값을 조정한다.` 주석을 남긴다.

## 5. 진행 상태에 따른 처리

### 5.1 최초 시작

- 진행도가 없으면 현재 사용자와 해당 미션으로 새 진행도를 생성한다.
- `mission_status`는 `IN_PROGRESS`, `found_item_count`는 0, `completed_at`은 `null`로 설정한다.
- 진행도 ID를 확보한 뒤 생성 개수 상수만큼 `TREASURE_MISSION_PROGRESS_ITEM` 행을 저장한다.
- 각 행은 해당 진행도 ID와 1부터 시작하는 중복 없는 `item_index`로 식별한다.
- 각 행의 `longitude`, `latitude`에는 사용자 중심 원 내부에서 생성한 좌표를 저장한다.
- 각 행의 `item_status`는 `UNFOUND`, `found_at`은 `null`로 설정한다.
- 생성 개수는 `TREASURE_MISSION.item_total_count`가 아니라 도메인 상수를 사용하며, 이 요청으로 미션 설정의 `item_total_count`를 변경하지 않는다.

### 5.2 이어하기

- 기존 진행도가 `IN_PROGRESS`이면 해당 진행도와 저장된 아이템을 그대로 사용한다.
- 진행도와 아이템을 추가 생성하거나 삭제·초기화하지 않는다.
- 진행도 ID, 찾은 개수, 완료 시각과 각 아이템의 좌표·발견 상태·발견 시각을 유지한다.
- 기존 아이템이 4개 또는 5개이더라도 상수에 맞춰 3개로 줄이거나 새로 배치하지 않는다.

### 5.3 완료 후 재시작

- 기존 진행도가 `COMPLETED`이면 동일한 진행도 ID를 유지해 재사용한다.
- 새 진행도를 생성하거나 기존 진행도 행을 삭제하지 않는다.
- `mission_status`는 `IN_PROGRESS`, `found_item_count`는 0, `completed_at`은 `null`로 초기화한다.
- 해당 진행도에 연결된 이전 아이템 행을 삭제하고 현재 요청 좌표를 기준으로 상수 개수만큼 새 아이템 행을 생성한다.
- 새 아이템은 최초 시작과 동일하게 번호를 부여하고 `UNFOUND`·미발견 시각으로 초기화한다.
- 별도 `MISSION_REWARD_STATUS`의 기존 지급 여부와 사용자 포인트·획득 기록은 초기화하거나 삭제하지 않는다.

## 6. 장소 정보 및 설명 구성

- 연결된 `LOCATION`이 있으면 장소 ID·이름·주소·위도·경도로 미션 장소 정보를 구성한다.
- 장소가 없으면 응답의 `location` 전체를 `null`로 구성하고 TourAPI를 호출하지 않는다.
- 장소가 있으면 해당 `content_id`로 공통 TourAPI 클라이언트에서 `detailCommon2.overview`를 조회한다.
- HTML 엔티티·태그·불필요한 공백 정리는 공통 TourAPI 처리에서 담당하고 보물찾기 서비스에 중복 구현하지 않는다.
- 정리된 설명에서 `.`, `!`, `?` 중 가장 먼저 등장하는 문장 종결 부호까지 포함해 첫 문장을 구성한다.
- 종결 부호가 없으면 정리된 전체 설명을 사용한다.
- 인증키 미설정·외부 조회 실패·설명 부재·빈 설명이면 장소 객체는 유지하고 설명만 `null`로 구성한다.
- 최초 시작·이어하기·재시작에 같은 장소 응답 구성 방식을 사용하며, 설명 조회는 장소가 있을 때 응답 한 건당 한 번 수행한다.
- 조회한 설명은 응답에만 사용하고 장소나 진행도에 저장하지 않는다.

## 7. 실제 보물 개수 및 목록 구성

- 생성하거나 재사용한 `treasureMissionProgressId`를 기준으로 아이템 행 전체를 조회한다.
- `treasureCount`는 `TREASURE_MISSION_PROGRESS_ITEM.treasure_mission_progress_id`가 해당 진행도 ID인 행의 실제 DB COUNT로 반환한다.
- COUNT에는 발견·미발견 아이템을 모두 포함한다.
- 응답 개수를 상수 3, `TREASURE_MISSION.item_total_count`, `found_item_count`로 대체하지 않는다.
- 아이템 목록은 `item_index` 오름차순으로 정렬하고, 각 아이템의 번호와 저장된 좌표를 반환한다.
- `item_status`가 `FOUND`이면 `isFound`는 true, `UNFOUND`이면 false로 구성한다.
- `treasureCount`와 반환하는 전체 아이템 목록의 개수는 일치해야 한다.
- 미션 장소가 없어도 아이템 목록과 각 아이템 좌표는 정상 제공한다.
- 이 API에서는 보상 지급이나 보상 지급 여부 변경을 수행하지 않는다.
- 최초 생성 여부에 따른 응답 구분은 [API 명세](./API_SPEC.md)를 따른다. 이어하기와 재시작은 기존 진행도 재사용에 해당한다.

## 8. 재요청 및 트랜잭션

- 최초 시작 이후 같은 요청을 다시 처리하면 생성된 진행도를 이어서 반환하며 좌표를 재생성하지 않는다.
- 재시작 후 반복 요청도 현재 진행도를 이어서 반환한다.
- 진행도 조회·생성·초기화와 아이템 교체·저장은 하나의 트랜잭션으로 처리한다.
- 사용자·미션 쌍의 DB 유일성 제약을 유지한다. 사용자 조회는 기존 문화 미션과 동일한 일반 조회를 사용하며 별도 쓰기 잠금은 적용하지 않는다.
- 신규 아이템 저장 실패 시 새 진행도와 일부 저장된 아이템을 함께 롤백한다.
- 재시작 실패 시 진행도 초기화와 이전 아이템 삭제·새 아이템 삽입을 모두 롤백해 이전 완료 상태와 아이템을 유지한다.
- 장소 설명 조회 실패는 진행도 생성·재시작을 실패시키지 않는다.
- 예상하지 못한 DB 오류는 미션 없음으로 바꾸지 않고 공통 서버 오류로 처리한다.
