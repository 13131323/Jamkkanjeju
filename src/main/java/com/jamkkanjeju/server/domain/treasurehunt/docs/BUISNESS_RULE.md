# 보물찾기 시작/이어하기 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져오며 요청에서 별도로 받지 않는다.
- 인증 정보에 해당하는 사용자가 없으면 `UNAUTHORIZED`로 처리한다.
- 요청 좌표는 최초 시작·재시작 시 보물 생성의 기준 위치로 사용한다.
- 이어하기에서도 요청 좌표를 검증하지만 저장된 보물 위치를 다시 계산하는 데 사용하지 않는다.

## 2. 보물찾기 미션 확인

- 요청의 `missionId`로 `TREASURE_MISSION.mission_id`에 해당하는 보물찾기 미션을 조회한다.
- 보물찾기 미션 ID는 공통 `MISSION.id`와 동일하다.
- 해당 보물찾기 미션이 없으면 `TREASURE_MISSION_NOT_FOUND`로 처리한다.
- 미션 상태가 `INACTIVE`이면 `TREASURE_MISSION_INACTIVE`로 처리한다.
- 존재 여부와 활성 상태 검증은 최초 시작·이어하기·재시작 모두에 동일하게 적용한다.
- 검증을 완료하기 전에는 진행도나 보물 아이템을 생성·초기화·삭제하지 않는다.
- 미션에 연결된 장소가 없어도 요청을 거절하지 않는다. 보물 생성 기준은 미션 장소가 아닌 사용자 좌표이다.

## 3. 현재 진행도 조회

- 현재 사용자 ID와 보물찾기 미션 ID로 `TREASURE_MISSION_PROGRESS`를 조회한다.
- 같은 사용자와 같은 미션의 진행도는 상태에 관계없이 최대 한 건만 유지한다.
- 진행도가 없으면 최초 시작, `IN_PROGRESS`이면 이어하기, `COMPLETED`이면 재시작으로 판단한다.
- 다른 사용자의 진행도와 보물 아이템은 조회하거나 변경하지 않는다.

## 4. 보물 생성 상수 및 좌표 생성

- 보물찾기 도메인의 별도 상수 정의에 생성 개수 `TREASURE_ITEM_COUNT = 3`과 등장 반경 `TREASURE_APPEAR_RADIUS_METER = 100`을 둔다.
- 서비스에 개수와 반경 숫자를 직접 반복하지 않고 공통 상수를 참조한다.
- 위 상수의 개수는 새 보물을 만들 때만 사용한다. 기존 보물 목록의 개수나 응답의 `treasureCount`를 강제로 3으로 바꾸지 않는다.
- 사용자 요청 좌표를 중심으로 하고 등장 반경을 반지름으로 하는 전체 원 내부에서 좌표를 무작위 생성한다.
- 기존 FastAPI의 미션 장소 중심·사용자 방향 반원 방식은 사용하지 않는다.
- 생성한 보물은 각각 사용자 요청 좌표에서 100m 이내에 있어야 한다.
- 위도·경도를 미터 단위 평면 좌표처럼 직접 더하지 않고 미터 단위 거리를 위도·경도로 변환한다.
- 생성 좌표는 위도·경도의 DB 허용 범위를 만족해야 한다.
- 좌표 생성은 서비스의 진행도 처리와 분리한 보물찾기 도메인의 별도 컴포넌트 또는 함수로 구현한다.
- 등장 반경은 기존 임시 정책을 유지하므로 해당 상수 위치에 `// TODO: 추후 확정된 보물 등장 반경으로 상수 값을 조정한다.` 주석을 남긴다.

## 5. 진행 상태에 따른 처리

### 5.1 최초 시작

- 진행도가 없으면 현재 사용자와 해당 미션으로 새 진행도를 생성한다.
- `mission_status`는 `IN_PROGRESS`, `found_item_count`는 0, `completed_at`은 `null`로 설정한다.
- 진행도 ID를 확보한 뒤 생성 개수 상수만큼 `TREASURE_MISSION_PROGRESS_ITEM` 행을 저장한다.
- 각 행은 해당 진행도 ID와 1부터 시작하는 중복 없는 `item_index`로 식별한다.
- 각 행의 `longitude`, `latitude`에는 사용자 중심 원 내부에서 생성한 좌표를 저장한다.
- 각 행의 `item_status`는 `UNFOUND`, `found_at`은 `null`로 설정한다.
- 생성 개수는 `TREASURE_MISSION.item_total_count`가 아니라 도메인 상수를 사용하며, 이 요청으로 미션 설정의 `item_total_count`를 변경하지 않는다.

### 5.2 이어하기

- 기존 진행도가 `IN_PROGRESS`이면 해당 진행도와 저장된 아이템을 그대로 사용한다.
- 진행도와 아이템을 추가 생성하거나 삭제·초기화하지 않는다.
- 진행도 ID, 찾은 개수, 완료 시각과 각 아이템의 좌표·발견 상태·발견 시각을 유지한다.
- 기존 아이템이 4개 또는 5개이더라도 상수에 맞춰 3개로 줄이거나 새로 배치하지 않는다.

### 5.3 완료 후 재시작

- 기존 진행도가 `COMPLETED`이면 동일한 진행도 ID를 유지해 재사용한다.
- 새 진행도를 생성하거나 기존 진행도 행을 삭제하지 않는다.
- `mission_status`는 `IN_PROGRESS`, `found_item_count`는 0, `completed_at`은 `null`로 초기화한다.
- 해당 진행도에 연결된 이전 아이템 행을 삭제하고 현재 요청 좌표를 기준으로 상수 개수만큼 새 아이템 행을 생성한다.
- 새 아이템은 최초 시작과 동일하게 번호를 부여하고 `UNFOUND`·미발견 시각으로 초기화한다.
- 별도 `MISSION_REWARD_STATUS`의 기존 지급 여부와 사용자 포인트·획득 기록은 초기화하거나 삭제하지 않는다.

## 6. 장소 정보 및 설명 구성

- 연결된 `LOCATION`이 있으면 장소 ID·이름·주소·위도·경도로 미션 장소 정보를 구성한다.
- 장소가 없으면 응답의 `location` 전체를 `null`로 구성하고 TourAPI를 호출하지 않는다.
- 장소가 있으면 해당 `content_id`로 공통 TourAPI 클라이언트에서 `detailCommon2.overview`를 조회한다.
- HTML 엔티티·태그·불필요한 공백 정리는 공통 TourAPI 처리에서 담당하고 보물찾기 서비스에 중복 구현하지 않는다.
- 정리된 설명에서 `.`, `!`, `?` 중 가장 먼저 등장하는 문장 종결 부호까지 포함해 첫 문장을 구성한다.
- 종결 부호가 없으면 정리된 전체 설명을 사용한다.
- 인증키 미설정·외부 조회 실패·설명 부재·빈 설명이면 장소 객체는 유지하고 설명만 `null`로 구성한다.
- 최초 시작·이어하기·재시작에 같은 장소 응답 구성 방식을 사용하며, 설명 조회는 장소가 있을 때 응답 한 건당 한 번 수행한다.
- 조회한 설명은 응답에만 사용하고 장소나 진행도에 저장하지 않는다.

## 7. 실제 보물 개수 및 목록 구성

- 생성하거나 재사용한 `treasureMissionProgressId`를 기준으로 아이템 행 전체를 조회한다.
- `treasureCount`는 `TREASURE_MISSION_PROGRESS_ITEM.treasure_mission_progress_id`가 해당 진행도 ID인 행의 실제 DB COUNT로 반환한다.
- COUNT에는 발견·미발견 아이템을 모두 포함한다.
- 응답 개수를 상수 3, `TREASURE_MISSION.item_total_count`, `found_item_count`로 대체하지 않는다.
- 아이템 목록은 `item_index` 오름차순으로 정렬하고, 각 아이템의 번호와 저장된 좌표를 반환한다.
- `item_status`가 `FOUND`이면 `isFound`는 true, `UNFOUND`이면 false로 구성한다.
- `treasureCount`와 반환하는 전체 아이템 목록의 개수는 일치해야 한다.
- 미션 장소가 없어도 아이템 목록과 각 아이템 좌표는 정상 제공한다.
- 이 API에서는 보상 지급이나 보상 지급 여부 변경을 수행하지 않는다.
- 최초 생성 여부에 따른 응답 구분은 [API 명세](./API_SPEC.md)를 따른다. 이어하기와 재시작은 기존 진행도 재사용에 해당한다.

## 8. 재요청 및 트랜잭션

- 최초 시작 이후 같은 요청을 다시 처리하면 생성된 진행도를 이어서 반환하며 좌표를 재생성하지 않는다.
- 재시작 후 반복 요청도 현재 진행도를 이어서 반환한다.
- 진행도 조회·생성·초기화와 아이템 교체·저장은 하나의 트랜잭션으로 처리한다.
- 사용자·미션 쌍의 DB 유일성 제약을 유지한다. 사용자 조회는 기존 문화 미션과 동일한 일반 조회를 사용하며 별도 쓰기 잠금은 적용하지 않는다.
- 신규 아이템 저장 실패 시 새 진행도와 일부 저장된 아이템을 함께 롤백한다.
- 재시작 실패 시 진행도 초기화와 이전 아이템 삭제·새 아이템 삽입을 모두 롤백해 이전 완료 상태와 아이템을 유지한다.
- 장소 설명 조회 실패는 진행도 생성·재시작을 실패시키지 않는다.
- 예상하지 못한 DB 오류는 미션 없음으로 바꾸지 않고 공통 서버 오류로 처리한다.

# 보물찾기 진행도 저장 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md#보물찾기-진행도-저장-api)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져온다.
- 사용자 확인은 기존 문화 미션과 동일한 일반 조회를 사용한다.
- 인증 정보에 해당하는 사용자가 존재하지 않으면 `UNAUTHORIZED`로 처리한다.
- 요청의 진행도 ID는 공통 미션 ID가 아닌 `TREASURE_MISSION_PROGRESS.id`를 의미한다.
- 보물 발견 여부는 프론트에서 판단하며 서버에서 사용자와 보물 사이의 거리를 다시 검증하지 않는다.
- 요청 위치는 완료 후 다음 장소 추천과 해당 장소까지의 거리 계산에 사용한다.

## 2. 진행도와 보물찾기 미션 확인

- 요청 진행도 ID와 현재 사용자 ID를 함께 사용하여 `IN_PROGRESS` 상태의 진행도를 조회한다.
- 진행도가 없거나 다른 사용자 소유이거나 이미 완료된 경우 `TREASURE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 진행도에 연결된 보물찾기 미션을 확인한다.
- 미션 상태가 `INACTIVE`이면 `TREASURE_MISSION_INACTIVE`로 처리한다.
- 진행 도중 비활성화된 미션도 저장을 허용하지 않는다.
- 미션의 `location`이 없어도 보물 발견과 진행도 저장을 허용한다.
- 진행도·미션·보물 검증이 끝나기 전에는 발견 상태, 찾은 개수와 보상 이력을 변경하지 않는다.

## 3. 보물 확인 및 발견 처리

- 진행도 ID와 요청의 `treasureIndex`를 함께 사용하여 `TREASURE_MISSION_PROGRESS_ITEM`의 해당 아이템을 조회한다.
- 다른 진행도에 있는 같은 번호의 보물은 조회하거나 변경하지 않는다.
- 해당 아이템이 없으면 `TREASURE_ITEM_NOT_FOUND`로 처리한다.
- 해당 아이템의 `item_status`가 이미 `FOUND`이면 `TREASURE_ITEM_ALREADY_FOUND`로 처리한다.
- 아직 찾지 않은 아이템은 `item_status`를 `FOUND`로 변경하고 `found_at`을 기록한다.
- 발견 시각은 주입받은 `Clock`을 기준으로 구한다.
- 정상적인 신규 발견 한 건에 대해서만 진행도의 `found_item_count`를 1 증가시킨다.
- 보물 번호순 발견을 요구하지 않으며, 아직 찾지 않은 유효한 보물이면 어느 번호든 처리한다.
- 아이템의 저장 좌표와 다른 아이템의 발견 상태·시각은 변경하지 않는다.
- 이 API에서는 진행도나 보물을 새로 만들거나 재배치하지 않는다.

## 4. 실제 보물 개수와 완료 판단

- 전체 보물 수는 해당 진행도 ID에 연결된 `TREASURE_MISSION_PROGRESS_ITEM` 전체 행의 실제 DB COUNT로 구한다.
- 전체 개수를 생성 상수 3이나 미션 설정의 `item_total_count`로 대체하지 않는다.
- 기존 진행도에 4개 또는 5개가 저장되어 있으면 해당 개수 전체를 완료 기준으로 사용한다.
- 이번 발견을 반영한 뒤 해당 진행도의 모든 보물이 `FOUND`인지 확인한다.
- 아직 `UNFOUND`인 보물이 있으면 진행 중이고, 전체 보물을 찾았으면 완료로 판단한다.
- 기존 FastAPI의 `current_step`, `item_detail`, `current_found_item_idx`를 별도 컬럼이나 JSON 값으로 만들지 않고 현재 진행도·아이템 구조를 사용한다.

### 4.1 진행 중 처리

- `mission_status`는 `IN_PROGRESS`를 유지하고 `completed_at`은 변경하지 않는다.
- 이번 보물 발견에 해당하는 보상 한 종류를 즉시 지급한다.
- 다음 장소를 추천하거나 장소 이미지를 조회하지 않는다.

### 4.2 완료 처리

- 마지막 보물도 발견 상태와 찾은 개수에 반영한다.
- `mission_status`를 `COMPLETED`로 변경한다.
- `completed_at`을 주입받은 `Clock` 기준의 이번 완료 시각으로 기록한다.
- 마지막 보물에 대해서도 남은 보상 중 한 종류만 지급한다.
- 요청 위치를 기준으로 다음 장소를 추천한다.
- 완료했다는 이유로 추가 보상을 지급하거나 누적 발견 개수만큼 다시 지급하지 않는다.

## 5. 보상 계산과 중복 지급 방지

- 미션에 설정된 `ar_character_id`, `point`, `coupon_id`를 보상 정보로 사용한다.
- 같은 사용자와 같은 미션의 지급 여부는 공통 `MISSION_REWARD_STATUS`의 `(mission_id, user_id)`로 확인한다.
- 지급 여부 기록이 없으면 아직 해당 보상을 지급하지 않은 것으로 판단한다.
- 이미 지급한 항목과 미션에 설정되지 않은 항목은 지급 후보에서 제외한다.
- 남은 후보 중 AR 캐릭터, 포인트, 쿠폰 순서로 가장 앞의 한 항목만 지급한다.
- 지급 한도는 이번 요청에서 새로 발견한 보물 한 개에 대한 한 항목이며, 누적 `found_item_count`를 지급 개수로 사용하지 않는다.
- 예를 들어 AR 캐릭터가 없거나 기지급 상태이면 첫 발견에서도 남은 포인트를 지급할 수 있다.
- 재시작한 진행도에서도 기존 공통 지급 이력을 유지하므로 같은 미션의 같은 보상을 다시 지급하지 않는다.
- 남은 보상이 없으면 보물을 정상 발견 처리하되 추가 보상을 지급하지 않는다.
- 보상 처리는 진행도 저장 서비스와 분리한다. 문화 미션과 겹치는 후보 구성·실제 지급·지급 이력 기록은 다른 미션에서도 재사용 가능한 공통 컴포넌트로 추출하고, 보물 한 개당 지급 한도 한 개라는 기준은 보물찾기에서 전달한다.

## 6. 보상 저장 및 결과 구성

- 실제 보상 저장 방식은 현재 문화 미션과 동일하게 적용한다.
- 포인트는 `USER.point`에 누적한다.
- AR 캐릭터는 `ACQUIRED_AR_CHARACTER`에 사용자·캐릭터·공통 미션 ID를 연결한 획득 기록으로 저장한다.
- AR 캐릭터 획득 기록의 유일성 기준은 현재 스키마의 `(mission_id, user_id)`이며, 기존 FastAPI의 `(user_id, ar_character_id)` 기준을 적용하지 않는다.
- 쿠폰은 `ACQUIRED_COUPON`에 획득 기록을 저장한다.
- 이미 같은 `(coupon_id, user_id)`의 보유 쿠폰이 있으면 획득 행은 추가하지 않고, 문화 미션과 동일하게 해당 미션의 쿠폰 보상은 지급 처리한다.
- 획득 시각이 필요한 기록은 주입받은 `Clock`을 사용한다.
- 이번에 지급한 항목의 공통 지급 여부만 `true`로 기록하고, 기존에 `true`인 항목을 초기화하지 않는다.
- 응답에는 이번 요청에서 지급 처리한 보상만 포함한다.
- 쿠폰 사용처는 연결된 `LOCATION.title`로 구성하며 연결 장소가 없으면 `null`로 구성한다.
- 지급한 보상이 없어도 보상 객체는 유지하고 모든 보상 항목을 `null`로 구성한다.

## 7. 다음 장소 추천

- 문화 미션에서 사용하는 장소 도메인의 `NextLocationRecommender`를 재사용하며 보물찾기 전용 추천 로직을 만들지 않는다.
- 추천 후보와 선정 기준은 문화 미션과 동일하게 적용하여 요청 위치에서 직선거리가 가장 가까운 장소 하나를 선택한다.
- 거리가 같으면 `LOCATION.id`가 작은 장소를 선택한다.
- 기존 FastAPI의 현재 미션 장소 제외 조건은 별도로 추가하지 않고 기존 공통 추천 기준을 따른다.
- 미션 장소가 `null`이어도 사용자 요청 위치로 다음 장소를 추천한다.
- 개인화 조건을 새로 추가하지 않고 공통 추천 구현의 `// TODO: 추후 사용자 개인화된 추천 로직을 적용한다.` 주석을 유지한다.
- 거리 계산은 기존 `TravelEstimator`를 재사용하고 장소 좌표는 `LOCATION.latitude`, `LOCATION.longitude`를 사용한다.
- 장소명은 `LOCATION.title`, 거리 값은 정수 미터 단위로 구성한다.
- 진행 중에는 추천 컴포넌트를 호출하지 않는다.
- 완료 응답에는 추천 장소가 필요하므로 후보가 없으면 문화 미션과 동일하게 완료 처리를 실패시킨다.
- 장소 이미지 조회는 공통 `TourApiClient`를 사용하고 선정한 장소의 `content_id`로 조회한다.
- 인증키 미설정·통신 실패·이미지 없음이면 이미지 URL만 `null`로 구성하고 완료 처리는 계속한다.

## 8. 다음 장소의 미션 구성

- 문화 미션과 동일한 다음 미션 선택 방식을 재사용한다. 중복되는 선택 로직은 여러 도메인에서 재사용 가능한 공통 컴포넌트로 분리한다.
- 추천 장소에 연결된 협동 미션과 보물찾기 미션 중 `ACTIVE`인 미션만 후보로 사용한다.
- 문화 미션은 장소가 없으므로 다음 장소에 연결된 미션 후보로 선택하지 않는다.
- 연결된 활성 미션이 없으면 미션 정보를 `null`로 구성한다.
- 여러 활성 미션이 연결되어 있으면 기존 문화 미션 방식대로 그중 하나를 무작위로 선택한다.
- 선택한 미션의 ID는 공통 `MISSION.id`, 유형은 `MISSION_TYPE.type`을 사용한다.

## 9. 응답 구성 및 재요청

- 진행 상태는 이번 발견을 반영한 진행도를 기준으로 구성한다.
- `treasureCount`는 해당 진행도의 실제 전체 아이템 수로 구성한다.
- `foundTreasureIndexes`는 해당 진행도의 `FOUND` 아이템 번호를 오름차순으로 구성하며 이번에 발견한 번호를 포함한다.
- 진행 중에는 다음 장소를 `null`로 구성하고, 완료 시에는 다음 장소 객체를 구성한다.
- 보상 객체는 진행 상태와 관계없이 이번 요청에서 지급 처리한 항목만 채운다.
- 이미 발견한 보물을 진행 중에 다시 제출하면 발견 시각·찾은 개수·보상 이력을 바꾸지 않고 `TREASURE_ITEM_ALREADY_FOUND`로 처리한다.
- 이미 완료된 진행도에 다시 저장을 요청하면 `TREASURE_MISSION_PROGRESS_NOT_FOUND`로 처리하며 완료 시각을 다시 갱신하거나 보상을 다시 지급하지 않는다.
- 오류 응답과 정상 응답 구조는 [API 명세](./API_SPEC.md#보물찾기-진행도-저장-api)를 따른다.

## 10. 트랜잭션 범위

- 사용자·진행도·미션·아이템 확인, 발견 상태와 개수 갱신, 완료 처리, 보상 지급과 공통 지급 이력 기록을 하나의 트랜잭션으로 처리한다.
- 완료 시 다음 장소와 응답 구성에 필요한 처리까지 성공한 경우에만 변경을 커밋한다.
- 보상 지급이나 필수 다음 장소 추천 등에서 실패하면 이번 요청의 발견 처리와 보상 관련 변경을 모두 롤백한다.
- 실패 시 기존 아이템의 좌표·발견 상태·발견 시각, 찾은 개수, 진행 상태·완료 시각, 사용자 포인트·획득 기록·지급 이력이 유지되어야 한다.
- 부가 정보인 장소 이미지 조회 실패는 전체 롤백 사유로 취급하지 않는다.
- 기존 문화 미션과 다른 별도 잠금·동시 요청 직렬화 방식은 추가하지 않는다.

# 보물찾기 중단 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md#보물찾기-중단-api)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져온다.
- 사용자 확인은 기존 문화 미션과 동일한 일반 조회를 사용한다.
- 인증 정보에 해당하는 사용자가 존재하지 않으면 `UNAUTHORIZED`로 처리한다.
- 요청의 진행도 ID는 공통 미션 ID가 아닌 `TREASURE_MISSION_PROGRESS.id`를 의미한다.
- 요청 위치는 다음 장소 추천과 해당 장소까지의 거리 계산에 사용한다.
- 중단 요청에서는 보물 번호나 발견 여부를 받지 않는다.

## 2. 진행도와 보물찾기 미션 확인

- 요청 진행도 ID와 현재 사용자 ID를 함께 사용하여 `IN_PROGRESS` 상태의 진행도를 조회한다.
- 진행도가 없거나 다른 사용자 소유이거나 이미 완료된 경우 `TREASURE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 진행도에 연결된 보물찾기 미션의 상태가 `INACTIVE`이면 `TREASURE_MISSION_INACTIVE`로 처리한다.
- 진행 도중 비활성화된 미션도 중단을 허용하지 않는다.
- 연결된 미션 장소가 `null`이어도 중단할 수 있다.
- 검증이 끝나기 전에는 진행 상태와 완료 시각을 변경하지 않는다.

## 3. 즉시 완료 처리 및 기존 기록 유지

- 검증이 끝나면 찾은 보물 개수와 남은 보물 개수에 관계없이 `mission_status`를 즉시 `COMPLETED`로 변경한다.
- `completed_at`을 이번 중단 처리 시각으로 기록하며 주입받은 `Clock`을 사용한다.
- `found_item_count`는 기존 값을 유지하고 증가시키거나 초기화하지 않는다.
- 아이템의 `item_status`, `found_at`, 좌표와 번호를 변경하지 않는다.
- 아직 찾지 않은 보물을 `FOUND`로 바꾸거나 발견 시각을 채우지 않는다.
- 진행도·아이템을 새로 생성하거나 삭제·재배치하지 않는다.
- 완료 상태 변경과 다음 장소 응답 구성은 같은 트랜잭션에서 처리하고 완료 상태만 먼저 커밋하지 않는다.

## 4. 보상 미지급

- 보물 발견 시 진행도 저장 API에서 이미 보상을 지급하므로 중단에서는 보상 지급 컴포넌트를 호출하지 않는다.
- 남은 보상이 있어도 중단을 이유로 지급하지 않는다.
- 공통 `MISSION_REWARD_STATUS`를 생성·초기화하거나 기존 지급 여부를 변경하지 않는다.
- 사용자 포인트와 AR 캐릭터·쿠폰 획득 기록을 변경하지 않는다.
- 응답에 보상 객체를 만들지 않으며 `reward` 필드 자체를 포함하지 않는다.

## 5. 다음 장소 추천 및 연결 미션

- 보물찾기 진행도 저장과 문화 미션에서 사용하는 `NextLocationRecommender`를 그대로 재사용한다.
- 사용자 요청 위치에서 직선거리가 가장 가까운 장소 하나를 선택하고, 거리가 같으면 장소 ID가 작은 것을 선택한다.
- 기존 FastAPI의 중단한 미션 장소 제외 조건은 적용하지 않는다. 현재 미션 장소도 다른 장소와 동일하게 후보에 포함한다.
- 미션 장소가 `null`이어도 요청한 사용자 위치를 기준으로 추천한다.
- 공통 추천 구현의 `// TODO: 추후 사용자 개인화된 추천 로직을 적용한다.` 주석을 유지한다.
- 거리 계산은 기존 `TravelEstimator`를 재사용하고 장소 좌표는 `LOCATION.latitude`, `LOCATION.longitude`를 사용한다.
- 장소명은 `LOCATION.title`, 거리 값은 정수 미터 단위로 구성한다.
- 장소 이미지 조회는 공통 `TourApiClient`에 선정한 장소의 `content_id`를 전달한다.
- 인증키 미설정·통신 실패·이미지 없음이면 이미지 URL만 `null`로 구성한다.
- 추천 장소가 없으면 문화 미션 중단과 동일하게 처리를 실패시키고 완료 상태 변경을 롤백한다.
- 연결 미션 선택은 기존 `NextMissionSelector`를 재사용하고 중단 전용 선택 로직을 만들지 않는다.
- 추천 장소의 협동·보물찾기 미션 중 `ACTIVE`인 미션만 후보로 사용하고, 여러 후보이면 기존 방식대로 하나를 무작위로 선택한다.
- 연결된 활성 미션이 없으면 미션 정보를 `null`로 구성한다.
- 미션 ID는 공통 `MISSION.id`, 유형은 `MISSION_TYPE.type`을 사용한다.

## 6. 응답 구성 및 재요청

- 진행 상태는 `COMPLETED`로 구성한다.
- `treasureCount`는 해당 진행도 ID에 연결된 전체 아이템 행의 실제 DB COUNT로 구성한다.
- 전체 개수를 생성 상수 3이나 미션 설정의 `item_total_count`, 찾은 개수로 대체하지 않는다.
- `foundTreasureIndexes`는 중단 시점에 저장된 `FOUND` 아이템 번호를 오름차순으로 구성한다.
- 찾은 보물이 없으면 발견 번호 목록은 빈 배열로 구성한다.
- 다음 장소는 객체로 구성하고 이미지·연결 미션이 없으면 해당 항목만 `null`로 구성한다.
- 이미 완료된 진행도에 중단을 다시 요청하면 `TREASURE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 반복 중단 요청으로 완료 시각을 다시 갱신하거나 보물 발견 정보·보상 이력을 변경하지 않는다.
- 중단 후 시작/이어하기 요청은 기존 완료 후 재시작 규칙을 그대로 따른다. 같은 진행도 ID를 초기화하고 새 보물 3개를 생성하되 보상 지급 이력은 유지한다.

## 7. 트랜잭션 범위

- 사용자·진행도·미션 확인, 완료 상태 변경, 다음 장소·연결 미션 조회와 응답 구성을 하나의 트랜잭션으로 처리한다.
- 전체 처리가 성공한 경우에만 변경을 커밋한다.
- 필수 추천 장소 구성이나 응답에 필요한 처리에 실패하면 완료 상태와 완료 시각 변경을 롤백한다.
- 실패 시 기존 진행 상태·완료 시각·찾은 개수·아이템 전체와 포인트·획득 기록·공통 지급 이력이 유지되어야 한다.
- 부가 정보인 장소 이미지 조회 실패는 전체 롤백 사유로 취급하지 않는다.
- 기존 문화 미션과 다른 별도 잠금·동시 요청 직렬화 방식은 추가하지 않는다.
