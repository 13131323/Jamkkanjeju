1. DTO·좌표 생성·서비스·설명 클라이언트 단위 테스트를 구현하고 실행한다.
2. 시작/이어하기 통합 테스트를 구현하고 실행한다.
3. 기존 전체 테스트를 실행해 회귀 오류를 확인한다.
4. 계획은 보존하고 실제 실행 결과를 기록한다.

## 발견하고 수정한 점

- 잠금 제거 전에는 운영 코드 수정 없이 단위 → 통합 → 전체 회귀 테스트를 실행해 모두 통과했다. DTO·좌표 생성·설명 클라이언트와 기존 테스트의 결과 표는 해당 실행 기록이다.
- 이어하기 좌표 테스트의 소수 리터럴 정확 비교가 부동소수점 표현 차이로 실패해 작은 허용 오차(1e-10)로 검증하도록 수정했다. 저장 전후 DB 행의 좌표·상태·시각은 별도로 정확 비교한다.
- 최초·반복 요청과 응답 형식은 연속 요청 한 테스트에서, 재시작·반복·보상 이력·미지급·미션 격리는 한 테스트에서 함께 검증했다. 좌표·인증 오류도 여러 요청의 오류 응답과 데이터 유지를 묶어 확인했다.
- 4·5개 이어하기, 비활성의 세 분기, 신규·재시작 롤백은 매개변수화했다. 좌표 생성은 여섯 기준 위치에서 각 100회 반복하며 특정 무작위 좌표가 아닌 불변조건을 검증했다.
- 실제 롤백은 아이템 한 개를 DB에 flush한 뒤 예외를 발생시켰다. 신규 진행도·아이템 미잔존과 기존 완료 상태·개수·완료 시각·아이템 전체 복원을 확인했다.
- 사용자 요청에 따라 문화 미션과 동일한 일반 사용자 조회로 변경하고 쓰기 잠금 메서드를 제거했다. 잠금을 전제로 한 동시 최초 시작·재시작 테스트 2개와 관련 계획도 제거했다. 순차 반복 요청·격리·롤백 검증은 유지한다.
- 잠금 제거 후 Java 21로 컴파일과 서비스 단위 테스트 14개를 실행해 모두 통과했다. 통합 테스트 소스도 컴파일했지만 실행하지 않았으며, DB·컨테이너는 건드리지 않았다.
- TourAPI는 설명 클라이언트 단위 테스트의 로컬 응답과 통합 테스트 Mock으로 격리했다. 실제 외부 API 응답을 검증한 것은 아니다.
- 실행별 임시 MySQL DB에 Flyway V1~V3를 적용했다. 전체 실행 종료 후 남은 `tour_test_` DB와 접근 권한이 모두 0건임을 확인했다. 직접 커밋한 준비 데이터도 테스트에서 정리했다.
- 2026-10-16 진행도 저장 테스트와 함께 전체 회귀를 재실행했다. 잠금 제거 후의 시작/이어하기 통합 15개를 포함해 전체 412개가 통과했다. 위의 이전 실행·미재실행 설명은 당시 작업 이력이며 이번 재검증으로 해소했다.

# 보물찾기 진행도 저장 API 테스트 계획

- 상태: **완료**
- 실행일: 2026-10-16
- 전체 결과: 신규 단위 20개·통합 14개 및 기존 테스트 378개, 총 412개 통과. 실패·오류·건너뜀 0개.
- 대상 API: `PATCH /api/v2/treasure-missions/{treasureMissionProgressId}/progress`
- 기준 문서: `API_SPEC.md`, `BUISNESS_RULE.md`

## 진행 방식

| 구분 | 방법 |
| --- | --- |
| 단위 테스트 | Spring·DB 없이 JUnit 5·AssertJ·Mockito로 DTO, 저장 서비스 분기와 공통 다음 미션 선택을 검증한다. |
| 통합 테스트 | `MySqlIntegrationTestSupport`의 임시 MySQL DB에서 실제 JWT·MockMvc·JPA·서비스 트랜잭션을 검증한다. 외부 TourAPI는 Mock으로 격리한다. |

시각은 `Clock.fixed`로 고정하고 테스트 데이터를 직접 준비한다. 일반 통합 테스트는 롤백하며 실제 롤백 검증은 테스트 트랜잭션 없이 커밋한 준비 데이터에 요청한 뒤 해당 행만 정리한다. 기존 실행 중인 앱·개발 DB·볼륨을 변경하지 않는다. 공통 보상 후보·획득 중복 방지는 기존 `CultureMissionRewardGranterTest`를 재사용하고 보물 한 개당 지급 연결과 실제 저장은 새 테스트에서 확인한다. 거리·이미지의 세부 분기도 기존 테스트를 재사용한다. 별도 잠금이나 동시 요청 직렬화는 테스트·구현에 추가하지 않는다.

아이템 없음 오류 메시지는 최신 사용자 수정값인 `보물찾기 아이템을 찾을 수 없습니다.`를 기준으로 확인하며, 현재 API 명세의 `보물 아이템을 찾을 수 없습니다.`와 다른 점은 결과에 기록한다. 사용자 수정값과 명세를 임의 변경하지 않는다.

## 실행 순서

2. 저장 API 통합 테스트를 구현하고 실행한다.
3. 전체 기존 테스트를 실행해 공통화한 문화 미션과 시작/이어하기의 회귀 오류를 확인한다.
4. 계획은 보존하고 실제 실행일·클래스별 결과·발견 사항을 기록한다.

## 발견하고 수정한 점

- 운영 코드 수정 없이 단위 → 통합 → 전체 회귀 순서로 실행해 총 412개가 통과했다.
- 신규 서비스 테스트의 실제 개수 1·4·5개 완료 분기와 통합 테스트의 실제 개수·두 종류 롤백은 매개변수화했다. 여러 인증·요청 오류는 각각의 상태·code·message와 동일 준비 데이터 유지 여부를 한 테스트에서 묶어 확인했다.
- 통합 테스트의 보상 지급은 2 → 1 → 3 순서의 발견 요청으로 AR → 포인트 → 쿠폰 즉시 지급, 정렬된 번호 목록, 실제 획득·공통 지급 이력을 함께 검증했다. 완료 후 같은 ID로 재시작해 세 보물을 다시 찾아도 기지급 보상이 추가되지 않음을 확인했다.
- 공통 미션 선택은 후보가 없거나 한 개일 때 결정적으로 검증하고, 여러 후보는 특정 난수 결과가 아니라 반환값이 후보 안에 있는지만 확인했다.
- 테스트용 지급 상태 조회 도우미 이름이 MockMvc의 `status()`와 충돌해 `rewardStatus()`로 변경했다. 목록 JSON 검증은 기존 테스트와 동일한 `contains(...)` Matcher로 수정했다. 서버 응답 자체의 문제는 아니었다.
- 별도 서비스 트랜잭션에서 실제 지급 상태를 persist·flush한 뒤 예외를 던지거나 마지막 발견의 필수 추천 결과를 비워 실패를 유도했다. 아이템·진행도·포인트·획득·공통 지급 이력 전체가 원복되고 500 응답에 내부 메시지가 노출되지 않음을 확인했다.
- `TREASURE_ITEM_NOT_FOUND`의 최신 사용자 수정 메시지(`보물찾기 아이템을 찾을 수 없습니다.`)와 현재 API 명세 메시지(`보물 아이템을 찾을 수 없습니다.`)는 여전히 다르다. 테스트는 최신 사용자 수정값을 검증했고 코드·API 명세는 임의 변경하지 않았다.
- 임시 MySQL DB에 Flyway V1~V3를 적용했고, 종료 후 남은 `tour_test_` DB와 해당 DB 접근 권한이 모두 0건임을 확인했다. 직접 커밋한 준비 데이터도 FK 순서대로 정리했다. 기존 앱·MySQL 컨테이너와 개발 DB·볼륨은 변경하지 않았다.
