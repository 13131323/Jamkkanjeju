# 문화 미션 시작/이어하기 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져온다.
- 요청에서 사용자 ID를 받지 않는다.
- 인증 정보의 사용자 ID에 해당하는 사용자를 조회한다.
- 사용자가 존재하지 않으면 `UNAUTHORIZED`로 처리한다.

## 2. 문화 미션 확인

- 요청의 `missionId`로 `CULTURE_MISSION.mission_id`에 해당하는 문화 미션을 조회한다.
- 문화 미션 ID는 공통 `MISSION.id`와 동일하다.
- 해당 문화 미션이 존재하지 않으면 `CULTURE_MISSION_NOT_FOUND`로 처리한다.
- 문화 미션의 상태가 `INACTIVE`이면 `CULTURE_MISSION_INACTIVE`로 처리한다.
- 비활성 여부는 최초 시작, 이어하기, 완료 후 재시작 모두에 동일하게 적용한다.
- 문화 미션의 존재 여부와 활성 상태를 확인하기 전에는 진행도를 생성하거나 초기화하지 않는다.

## 3. 현재 진행도 조회

- 현재 사용자 ID와 문화 미션 ID를 함께 사용해 `CULTURE_MISSION_PROGRESS`를 조회한다.
- 같은 사용자와 같은 문화 미션의 진행도는 상태에 관계없이 최대 한 건만 유지한다.
- 진행도가 없으면 최초 시작, `IN_PROGRESS`이면 이어하기, `COMPLETED`이면 재시작으로 판단한다.
- 다른 사용자의 진행도는 조회하거나 변경하지 않는다.

## 4. 진행 상태에 따른 처리

### 4.1 최초 시작

- 현재 사용자와 문화 미션에 해당하는 진행도가 없으면 새 진행도를 생성한다.
- `culture_mission_id`에는 요청한 문화 미션 ID를 설정한다.
- `user_id`에는 현재 사용자 ID를 설정한다.
- `mission_status`는 `IN_PROGRESS`로 설정한다.
- `current_quiz_index`는 1로 설정한다.
- `correct_count`는 0으로 설정한다.
- `last_completed_at`은 `null`로 설정한다.
- 새로 생성한 진행도를 반환 대상으로 사용한다.

### 4.2 이어하기

- 기존 진행도가 `IN_PROGRESS`이면 해당 진행도를 그대로 사용한다.
- 진행도를 추가로 생성하거나 기존 진행도를 초기화하지 않는다.
- 진행도 ID, 현재 퀴즈 번호, 정답 개수와 마지막 완료 시각을 유지한다.

### 4.3 완료 후 재시작

- 기존 진행도가 `COMPLETED`이면 같은 진행도를 초기화해 재사용한다.
- 새 진행도를 생성하거나 기존 진행도를 삭제하지 않는다.
- 기존 진행도 ID를 유지한다.
- `mission_status`는 `IN_PROGRESS`로 변경한다.
- `current_quiz_index`는 1로 초기화한다.
- `correct_count`는 0으로 초기화한다.
- `last_completed_at`은 마지막으로 완료한 시각이므로 재시작 시 지우지 않고 유지한다.
- 보상 지급 이력은 별도 `CULTURE_MISSION_REWARD_STATUS`에서 관리하므로 진행도 재시작 시 초기화하거나 삭제하지 않는다.

## 5. 퀴즈 조회 및 응답 구성

- 해당 문화 미션에 연결된 `CULTURE_MISSION_QUIZ`를 조회한다.
- 퀴즈는 `quiz_index` 오름차순으로 정렬한다.
- `quizCount`는 해당 문화 미션의 전체 퀴즈 개수로 구성한다.
- `cultureMissionProgressId`는 생성하거나 재사용한 진행도의 ID로 구성한다.
- `currentQuizNumber`는 진행도의 `current_quiz_index`를 사용한다.
- `current_quiz_index`는 사용자가 다음에 풀 퀴즈 번호를 의미한다.
- 최초 시작과 재시작의 현재 퀴즈 번호는 1이며, 이어하기는 저장된 번호를 그대로 사용한다.
- `quizDetails`에는 정렬된 전체 문제의 이미지, 질문, 선택지와 힌트를 포함한다.
- 최초 시작, 이어하기, 재시작 응답 모두 정답과 해설을 포함하지 않는다.
- 정답과 해설은 진행도 저장 요청에서 해당 문제를 채점한 후 제공한다.
- 이미지, 선택지와 힌트가 없으면 해당 값을 `null`로 유지한다.
- 최초 생성과 기존 진행도 재사용 여부에 따른 정상 응답 구분은 [API 명세](./API_SPEC.md)를 따른다.

## 6. 재요청 및 진행도 유지

- 최초 시작 이후 같은 요청을 다시 처리하면 생성된 `IN_PROGRESS` 진행도를 이어서 반환한다.
- 재시작 직후 같은 요청을 다시 처리해도 이미 `IN_PROGRESS`인 진행도를 다시 초기화하지 않는다.
- 반복 요청으로 같은 사용자와 문화 미션에 진행도가 중복 생성되지 않아야 한다.
- 이 API는 퀴즈 풀이 결과를 제출하는 요청이 아니므로 현재 퀴즈 번호와 정답 개수를 증가시키지 않는다.
- 이 API에서는 미션을 완료 처리하거나 보상을 지급하지 않는다.

## 7. 트랜잭션 범위

- 현재 사용자와 문화 미션 확인, 진행도 조회, 최초 생성 또는 재시작 초기화, 응답에 필요한 퀴즈 조회를 하나의 트랜잭션으로 처리한다.
- 진행도 생성이나 초기화 이후 처리에 실패하면 해당 변경을 롤백한다.
- 재시작 요청이 실패하면 기존 완료 상태, 퀴즈 번호, 정답 개수와 마지막 완료 시각이 유지되어야 한다.
- 모든 처리가 성공한 경우에만 정상 응답을 반환한다.

# 문화 미션 진행도 저장 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져온다.
- 인증 정보에 해당하는 사용자가 존재하지 않으면 `UNAUTHORIZED`로 처리한다.
- 요청의 진행도 ID는 공통 미션 ID가 아닌 `CULTURE_MISSION_PROGRESS.id`를 의미한다.
- 요청 위치는 완료 후 다음 장소를 추천하고 해당 장소까지의 거리를 계산하는 데 사용한다.
- 정답 여부는 프론트에서 받지 않고 제출한 답변을 서버에서 채점한다.

## 2. 진행도와 문화 미션 확인

- 요청 진행도 ID와 현재 사용자 ID를 함께 사용하여 `IN_PROGRESS` 상태의 진행도를 조회한다.
- 진행도가 없거나 다른 사용자 소유이거나 이미 완료된 경우 `CULTURE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 진행도에 연결된 문화 미션을 확인한다.
- 문화 미션의 상태가 `INACTIVE`이면 `CULTURE_MISSION_INACTIVE`로 처리한다.
- 진행 도중 비활성화된 미션도 저장을 허용하지 않는다.
- 진행도와 미션 검증이 끝나기 전에는 퀴즈 번호, 정답 수와 보상 이력을 변경하지 않는다.

## 3. 퀴즈 확인 및 서버 채점

- 제출한 `quizIndex`가 진행도의 `current_quiz_index`와 일치하는지 확인한다.
- 일치하지 않으면 `CULTURE_MISSION_QUIZ_INDEX_MISMATCH`로 처리하고 진행도를 변경하지 않는다.
- 진행도에 연결된 문화 미션 ID와 제출한 퀴즈 번호를 함께 사용해 `CULTURE_MISSION_QUIZ`의 해당 문제를 조회한다.
- 다른 미션에 있는 같은 번호의 문제로 채점하지 않는다.
- 객관식과 주관식 모두 제출한 답변 문자열을 해당 문제의 저장된 `answer`와 비교해 정답 여부를 판단한다.
- 별도로 확정되지 않은 유사어 판정이나 대소문자·공백 정규화 정책을 추가하지 않는다.
- 정답이면 `correct_count`를 1 증가시키고 오답이면 기존 값을 유지한다.
- 마지막 문제도 같은 방식으로 채점하고 최종 정답 수에 반영한다.
- 응답의 정답과 해설은 방금 제출한 문제에서 가져온다. 다음 문제의 정답이나 해설을 제공하지 않는다.

## 4. 진행 중과 완료 분기

- 전체 문제 수는 해당 문화 미션의 `CULTURE_MISSION_QUIZ` 개수로 계산한다.
- 현재 퀴즈 번호가 전체 문제 수보다 작으면 진행 중으로 처리한다.
- 현재 퀴즈 번호가 전체 문제 수와 같으면 마지막 문제를 제출한 것으로 판단한다.

### 4.1 진행 중 처리

- 채점 결과를 반영한 뒤 `current_quiz_index`를 1 증가시킨다.
- `mission_status`는 `IN_PROGRESS`를 유지한다.
- 과거 완료 이력이 있는 재도전의 `last_completed_at`은 유지한다.
- 보상을 지급하거나 다음 장소를 추천하지 않는다.
- 응답은 갱신된 진행 정보와 방금 제출한 문제의 채점 결과로 구성한다.

### 4.2 완료 처리

- 마지막 문제의 채점 결과를 반영한다.
- `current_quiz_index`는 증가시키지 않고 마지막 퀴즈 번호를 유지한다.
- `mission_status`를 `COMPLETED`로 변경한다.
- `last_completed_at`을 이번 완료 시각으로 갱신한다. 시각은 주입받은 `Clock`을 기준으로 구한다.
- 최종 정답 수와 기존 지급 이력을 기준으로 보상을 지급한다.
- 요청 위치를 기준으로 다음 장소를 추천한다.

## 5. 보상 계산과 중복 지급 방지

- 보상 지급 로직은 진행도 저장 서비스와 분리하여 문화미션 도메인의 별도 보상 지급 컴포넌트로 구현한다.
- 정답 수에 따른 지급 순서와 개수 계산은 문화미션 도메인에서 관리한다.
- 미션에 설정된 `ar_character_id`, `point`, `coupon_id`를 보상 정보로 사용한다.
- 같은 사용자와 같은 문화 미션의 지급 여부는 `CULTURE_MISSION_REWARD_STATUS`에서 확인한다.
- 지급 여부 기록이 없으면 아직 해당 보상을 지급하지 않은 것으로 판단한다.
- 이미 지급한 항목과 미션에 설정되지 않은 보상 항목은 지급 후보에서 제외한다.
- 남은 후보를 AR 캐릭터, 포인트, 쿠폰 순서로 정렬한다.
- 이번 지급 개수는 최종 `correct_count`와 남은 보상 후보 개수 중 작은 값으로 정한다.
- 정답 하나당 보상 항목 하나를 지급하며, 정답 수보다 많은 항목을 지급하지 않는다.
- 정답 수가 0이거나 남은 보상이 없더라도 미션은 정상 완료한다.
- 재시작한 진행도도 기존 보상 지급 이력을 유지하므로 같은 미션의 같은 보상을 다시 지급하지 않는다.
- 예를 들어 첫 완료에서 정답 하나로 AR 캐릭터를 받았다면, 재도전에서 정답 하나를 맞혔을 때는 남은 후보 중 포인트를 지급한다.

## 6. 보상 저장 및 결과 구성

- 포인트는 `USER.point`에 누적한다.
- AR 캐릭터는 `ACQUIRED_AR_CHARACTER`에 사용자, 캐릭터와 공통 미션 ID를 연결한 획득 기록으로 저장한다.
- AR 캐릭터 획득 기록의 `mission_id`에는 완료한 문화 미션의 공통 미션 ID를 사용한다.
- 현재 AR 캐릭터 획득 기록의 유일성 기준은 `(mission_id, user_id)`이며, 기존 FastAPI의 `(user_id, ar_character_id)` 유일성 조건을 그대로 적용하지 않는다.
- 쿠폰은 응답만 반환하던 기존 방식 대신 현재 스키마의 `ACQUIRED_COUPON`에 획득 기록을 저장한다.
- 쿠폰 획득 기록의 `(coupon_id, user_id)` 유일성을 지키며 같은 보유 쿠폰 행을 중복 생성하지 않는다.
- 이번 요청에서 지급한 항목의 지급 여부를 `CULTURE_MISSION_REWARD_STATUS`에서 `true`로 기록한다.
- 기존에 `true`인 지급 여부를 `false`로 되돌리지 않는다.
- 응답에는 이번 요청으로 실제 지급된 보상만 포함한다.
- 지급되지 않은 항목은 `null`로 구성한다.
- 쿠폰 사용처는 연결된 `LOCATION.title`을 사용하고 연결 장소가 없으면 `null`로 구성한다.
- 보상 응답 구조는 [API 명세](./API_SPEC.md)를 따른다.

## 7. 다음 장소 추천

- 다음 장소 추천은 진행도 저장 서비스 안에 직접 작성하지 않고 장소 도메인의 별도 추천 컴포넌트로 분리한다.
- 문화미션 외의 완료 처리에서도 사용할 수 있도록 사용자 좌표를 받아 추천 장소를 반환하는 책임을 갖게 한다.
- 현재는 요청 위치와 `LOCATION`의 좌표를 비교해 직선거리가 가장 가까운 장소 하나를 추천한다.
- 현재 추천에는 사용자 취향, 온보딩 선택값, 방문 이력이나 미션 완료 이력에 따른 개인화 조건을 적용하지 않는다.
- 거리가 같으면 `LOCATION.id`가 작은 장소를 선택한다.
- 문화 미션에는 수행 장소가 없으므로 방금 수행한 장소를 제외하는 조건을 적용하지 않는다.
- 추천 구현 코드에 `// TODO: 추후 사용자 개인화된 추천 로직을 적용한다.` 주석을 남긴다.
- 진행 중에는 추천 컴포넌트를 호출하지 않는다.
- 완료 응답에는 추천 장소가 필요하므로 장소 후보가 없는 경우 완료 처리를 실패시킨다.
- 거리 계산은 기존 공통 `TravelEstimator`를 재사용한다.
- 장소 좌표는 `LOCATION.latitude`, `LOCATION.longitude`를 사용한다.
- 장소명은 `LOCATION.title`, 거리 값은 정수 미터 단위로 구성한다.
- 장소 이미지 조회는 추천 대상 선정과 분리하고, `LOCATION.content_id`로 TourAPI에서 조회한다.
- 인증키 미설정, 통신 실패 또는 이미지 없음이면 이미지 URL만 `null`로 구성하고 완료 처리는 계속한다.

## 8. 다음 장소의 미션 구성

- 추천 장소에 연결된 협동 미션과 보물찾기 미션을 확인한다.
- 상태가 `ACTIVE`인 미션만 다음 미션 후보로 사용하고, `INACTIVE` 미션은 선택하지 않는다.
- 문화 미션은 장소가 없으므로 다음 장소에 연결된 미션으로 선택하지 않는다.
- 연결된 활성 미션이 없으면 미션 정보는 `null`로 구성한다.
- 여러 미션이 연결되어 있으면 기존 방식대로 그중 하나를 무작위로 선택한다.
- 선택한 미션의 ID는 공통 `MISSION.id`를 사용한다.
- 미션 유형은 연결된 `MISSION_TYPE.type`을 사용한다.

## 9. 응답 구성 및 재요청

- 채점 결과는 이번에 제출한 문제의 정답 여부, 저장된 정답과 해설로 구성한다.
- 해설이 없으면 `null`을 유지한다.
- 진행 상태, 현재 퀴즈 번호와 정답 수는 채점 후 갱신한 진행도를 기준으로 구성한다.
- 진행 중에는 다음 장소와 보상 정보를 `null`로 구성한다.
- 완료 시 다음 장소와 이번에 실제 지급한 보상 정보를 객체로 구성한다.
- 완료했지만 지급한 보상이 없으면 보상 객체의 항목을 모두 `null`로 구성한다.
- 이미 완료된 진행도에는 추가 저장을 허용하지 않는다.
- 완료 요청을 다시 받더라도 완료 응답을 재반환하거나 정답 수와 보상을 다시 반영하지 않고 `CULTURE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 진행 중 문제를 이미 저장한 뒤 같은 번호를 재제출하면 현재 번호와 일치하지 않으므로 `CULTURE_MISSION_QUIZ_INDEX_MISMATCH`로 처리한다.

## 10. 트랜잭션 범위

- 진행도 검증, 서버 채점, 정답 수와 단계 갱신, 완료 처리, 보상 지급과 지급 여부 기록을 하나의 트랜잭션으로 처리한다.
- 완료 시 다음 장소와 응답 구성에 필요한 처리까지 성공한 경우에만 변경을 커밋한다.
- 보상 지급이나 필수 다음 장소 추천 등에서 실패하면 진행도와 보상 관련 변경을 모두 롤백한다.
- 실패 시 기존 퀴즈 번호, 정답 수, 진행 상태, 마지막 완료 시각, 포인트, 획득 기록과 지급 여부가 유지되어야 한다.
- 부가 정보인 장소 이미지 조회 실패는 위의 전체 실패로 취급하지 않는다.
