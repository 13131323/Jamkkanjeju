# 문화 미션 시작/이어하기 API 테스트 계획

- 상태: **실행 완료**
- 실행일: 2026-10-14
- 결과: **문화 미션 43개 전부 통과, 전체 210개 전부 통과**
- 대상 API: `POST /api/v2/culture-missions/{missionId}/progress`
- 기준 문서: `API_SPEC.md`, `BUISNESS_RULE.md`

## 진행 방식

| 구분 | 방법 |
| --- | --- |
| 단위 테스트 | Spring과 DB 없이 JUnit 5, AssertJ, Mockito로 진행도 초기화, 서비스 분기와 응답 구성을 검증한다. |
| 통합 테스트 | `@SpringBootTest` + `@AutoConfigureMockMvc` + 실제 MySQL로 인증, Path 바인딩, JPA 저장·조회, 트랜잭션과 JSON 응답을 검증한다. 일반 테스트는 테스트마다 롤백한다. |

통합 테스트에서는 `app.dev-auth.enabled=false`로 고정하고 `JwtTokenProvider`로 발급한 실제 액세스 토큰을 사용한다. 테스트별 사용자, 문화 미션, 퀴즈와 진행도를 준비하여 기존 1번 사용자나 초기 데이터의 ID에 의존하지 않는다.

## 통합 테스트 계획

### `StartCultureMissionApiIntegrationTest`

| 구분 | 요청 및 검증 내용 |
| --- | --- |
| 최초 시작 | 진행도가 없는 사용자가 활성 문화 미션을 요청하면 201을 반환하고 DB 생성 ID가 응답 ID와 일치하는지 확인 |
| 최초 저장 상태 | 사용자·미션 연결, `IN_PROGRESS`, 퀴즈 번호 1, 정답 수 0, 마지막 완료 시각 `null`이 실제 DB에 저장되는지 확인 |
| 이어하기 | 진행 중 기록이 있으면 200을 반환하고 ID, 퀴즈 번호, 정답 수와 마지막 완료 시각이 그대로인지 확인 |
| 완료 후 재시작 | 완료 기록이 있으면 200을 반환하고 같은 ID로 상태·퀴즈 번호·정답 수가 초기화되며 마지막 완료 시각은 유지되는지 확인 |
| 보상 이력 유지 | 재시작 전 준비한 `CULTURE_MISSION_REWARD_STATUS`의 지급 여부가 초기화·삭제되지 않는지 확인 |
| 보상 미지급 | 시작·이어하기·재시작이 사용자 포인트, 보유 AR 캐릭터와 쿠폰을 변경하지 않는지 확인 |
| 최초 요청 반복 | 최초 요청은 201, 이후 요청은 200이며 진행도 ID가 같고 사용자·미션별 행이 하나인지 확인 |
| 재시작 후 이어하기 | 재시작한 진행도에 퀴즈 번호·정답 수를 저장한 뒤 다시 호출해 해당 값이 재초기화되지 않는지 확인 |
| 사용자 격리 | 다른 사용자의 기존 진행도가 있어도 현재 사용자의 진행도를 새로 생성하고 타인 기록을 변경하지 않는지 확인 |
| 미션 격리 | 같은 사용자의 다른 문화 미션 진행도는 변경하지 않고 요청한 미션만 처리하는지 확인 |
| 정렬과 문제 수 | 퀴즈를 번호순이 아닌 순서로 저장한 뒤 응답이 오름차순이고 `quizCount`가 해당 미션의 퀴즈 수인지 확인 |
| 응답 형식 | 명세의 필드와 문제 상세를 반환하며 내부 제어값인 `created`가 JSON에 노출되지 않는지 확인 |
| nullable 필드 | 주관식의 `options`와 없는 이미지·힌트·해설을 필드 누락이 아닌 JSON `null`로 반환하는지 확인 |
| Path 오류 | 정수로 변환할 수 없는 `missionId`에 400 `INVALID_REQUEST`와 명세의 메시지를 반환하는지 확인 |
| 토큰 없음 | 토큰 없이 호출하면 401 `UNAUTHORIZED`를 반환하고 진행도가 생성·변경되지 않는지 확인 |
| 유효하지 않은 토큰 | 변조된 토큰에 401 `INVALID_TOKEN`을 반환하고 진행도가 생성·변경되지 않는지 확인 |
| 만료된 토큰 | 만료된 토큰에 401 `EXPIRED_TOKEN`을 반환하고 진행도가 생성·변경되지 않는지 확인 |
| 사용자 없음 | 유효한 토큰의 사용자 ID가 DB에 없으면 401 `UNAUTHORIZED`를 반환하는지 확인 |
| 문화 미션 없음 | 없는 ID 또는 문화 미션이 아닌 공통 미션 ID에 404 `CULTURE_MISSION_NOT_FOUND`를 반환하는지 확인 |
| 비활성 최초 시작 | 비활성 미션에 404 `CULTURE_MISSION_INACTIVE`를 반환하고 새 진행도가 생성되지 않는지 확인 |
| 비활성 이어하기 | 진행 중 기록이 있어도 미션이 비활성이면 같은 404를 반환하고 기존 기록을 유지하는지 확인 |
| 비활성 재시작 | 완료 기록이 있어도 미션이 비활성이면 같은 404를 반환하고 완료 기록을 초기화하지 않는지 확인 |
| 최초 생성 롤백 | 진행도 저장 이후 퀴즈 조회 실패를 유도해 500 공통 응답을 반환하고 신규 진행도 행이 남지 않는지 확인 |
| 재시작 롤백 | 초기화 이후 퀴즈 조회 실패를 유도해 500 공통 응답을 반환하고 기존 ID, 완료 상태, 퀴즈 번호, 정답 수와 마지막 완료 시각이 보존되는지 확인 |

오류 응답은 상태 코드와 `code`, `message`를 함께 검증하고, 서버 오류에서는 내부 예외 메시지가 노출되지 않는지 확인한다.

롤백 테스트는 테스트 자체의 `@Transactional`을 비활성화해 서비스 트랜잭션의 실제 롤백을 확인한다. `@MockitoSpyBean`으로 진행도 생성·초기화 이후 퀴즈 조회에서 예외를 발생시키고 별도 조회로 DB 상태를 확인한다. 테스트 데이터는 의존 관계에 맞춰 정리하고 Spy 설정은 테스트마다 초기화한다. 일반 DB 상태 검증도 영속성 컨텍스트를 비운 뒤 다시 조회한다.

## 실행 순서

1. `CultureMissionProgressTest`, `StartCultureMissionResponseTest`를 작성하고 실행한다.
2. `CultureMissionServiceTest`를 작성하고 실행한다.
3. `StartCultureMissionApiIntegrationTest`를 작성하고 실행한다.
4. 문화 미션 테스트와 기존 전체 테스트를 함께 실행해 회귀 오류가 없는지 확인한다.
5. 계획 내용은 보존하고 상태, 실행일, 전체 결과, 클래스별 결과와 발견·수정 사항을 실제 실행 결과로 기록한다.

## 발견하고 수정한 점

- 운영 코드에서 발견된 오류 없음
- 완료 후 재시작을 위해 `CultureMissionProgress`에 상태 변경 메서드 `restart()`를 추가 (컬럼 변경 없음)
- 실행 중 사용자가 학습용으로 만든 `CultureMissionControllerCopy`가 같은 경로를 중복 등록해 컨텍스트 로딩이 실패함. 사용자가 해당 파일을 삭제한 뒤 재실행
- `CultureMissionServiceTest`의 재사용 응답은 이어하기와 재시작을 한 테스트에서, 처리 실패는 저장 실패와 퀴즈 조회 실패를 한 테스트에서 검증
- 통합 테스트의 문화 미션 없음은 없는 ID와 문화 미션이 아닌 보물찾기 공통 미션 ID를 한 테스트에서 검증
- 롤백 테스트는 `@MockitoSpyBean`으로 퀴즈 조회 레포지토리가 예외를 던지게 하고, 커밋한 테스트 데이터는 `JdbcTemplate`으로 FK 순서에 맞춰 삭제. 실행 후 DB에 남은 데이터 없음을 확인
