# 마이페이지 조회 비즈니스 규칙

## 1. 요청과 현재 사용자 확인

- 요청·응답·오류 계약은 [마이페이지 조회 API 명세](./API_SPEC.md)를 따른다.
- 인증 정보에서 현재 사용자 ID를 가져오며 사용자 ID를 요청으로 받지 않는다.
- 인증된 사용자가 존재하지 않으면 공통 인증 오류로 처리하고 후속 조회를 중단한다.
- 이 API는 저장된 프로필·활동·조각 획득 기록을 조회하여 응답을 구성한다.

## 2. 처리 순서

1. 현재 사용자와 연결된 온보딩 결과를 확인한다.
2. 목표 걸음 수, 방문 장소 수, 완료 미션 진행도 수, 보유 포인트를 구성한다.
3. 현재 사용자에게 연결된 진행 중인 문화·보물찾기·협동 미션을 조회하고 진행 수를 구성한다.
4. 도감 범위의 캐릭터와 현재 사용자에게 속한 캐릭터 획득 기록을 조회한다.
5. 캐릭터별 필요 조각 수·현재 조각 수·완성 여부·최초 완성 날짜를 계산한다.
6. 미완성 캐릭터를 보상으로 주는 활성 미션을 조회하고 사용자별 완료·지급 내역을 제외한다.
7. 캐릭터별 남은 후보를 정렬·제한하여 전체 마이페이지 응답을 반환한다.

## 3. 프로필과 목표 걸음 수

- 닉네임과 목표 걸음 수는 현재 `USER`의 저장값을 사용한다.
- `USER.onboarding_result_id`로 연결된 `ONBOARDING_RESULT.user_type`, `hashtags`로 여행 유형을 구성한다. 현재 Spring의 `USER_TRAVEL_STYLE` 선택 기준 데이터를 온보딩 진단 결과로 대신 사용하지 않는다.
- 프로필 이미지도 연결된 온보딩 결과의 `profile_img_url`을 사용한다. 온보딩 결과가 없으면 여행 유형과 프로필 이미지만 비운다.
- 대표 AR 캐릭터 선택 기능을 가정하거나 캐릭터 획득 기록에서 대표 캐릭터를 임의로 선정하지 않는다. 기존 대표 캐릭터 객체 대신 승인된 온보딩 프로필 이미지 필드를 사용한다.
- 조회 시 온보딩 결과를 새로 배정하거나 목표 걸음 수를 초기화하지 않는다.

## 4. 활동 요약

- 방문 장소 수는 현재 사용자와 연결되고 실제 장소가 존재하는 `VISITED_LOCATION`의 장소 ID를 중복 제거하여 센다.
- 완료 미션 수는 현재 사용자의 문화·보물찾기 완료 진행도 수와, 본인이 수락된 참가자로 속한 협동 완료 팀 진행도 수를 합산한다. 역할별 진행 기록 수를 완료 미션 수로 사용하지 않는다.
- 협동 미션의 대기 참가자는 완료 집계에서 제외하며, 삭제되어 존재하지 않는 참가자·팀 기록도 포함하지 않는다. 이전 FastAPI의 소프트 삭제 컬럼을 현재 Spring 스키마에 있다고 가정하지 않는다.
- 같은 협동 미션을 다른 팀에서 완료한 기록은 각 팀 진행도 단위로 집계한다. 미션별 보상 지급 횟수로 완료 진행도 수를 대신 계산하지 않는다.
- 보유 포인트는 현재 사용자 잔액을 그대로 사용한다. 이번 조회에서 미션 보상 설정값을 더하지 않는다.

## 5. 진행 중인 미션

- 문화·보물찾기는 본인의 진행도 중 진행 중 상태인 기록을 사용한다.
- 협동은 본인이 수락된 참가자로 연결된 진행 중 팀을 사용한다. 대기 중인 참가자는 기존 마이페이지 기준에 따라 제외한다.
- 각 항목의 미션 ID는 `MISSION.id`, 유형·제목은 연결된 `MISSION_TYPE`으로 구성한다.
- 문화의 현재 진행 수는 현재 퀴즈 번호이며 전체 진행 수는 실제 연결된 퀴즈 개수다.
- 보물찾기의 현재 진행 수는 `found_item_count`, 전체 진행 수는 `item_total_count`다.
- 협동의 현재 진행 수는 팀의 현재 단계, 전체 진행 수는 공통 미션 유형의 단계 배열 항목 수다. 현재 단계 체계는 초대·역할 배정을 함께 하는 첫 단계, 수행 단계, 완료 단계다.
- 완료된 진행도는 진행 중 목록에서 제외한다. 협동 역할이나 참가자 조인으로 같은 팀을 중복해서 포함하지 않는다.

## 6. AR 캐릭터 도감과 조각 집계

- 기존 도감 범위인 `AR_CHARACTER.id` 1~6을 유지하고 캐릭터 ID 오름차순으로 구성한다. 대상 캐릭터가 없으면 목록을 비운다.
- 이름·실제 이미지·대표 색상·이야기 제목·내용·해시태그·획득 조건은 완성 여부와 관계없이 반환한다. 이미지 실루엣 처리는 클라이언트가 완성 여부로 결정한다.
- 이야기 제목은 `story_title`, 내용은 `description`, 대표 색상은 `representative_color`를 사용한다. 이전 프로젝트의 컬럼명을 현재 스키마에 있다고 가정하지 않는다.
- 필요 조각 수는 캐릭터의 `required_fragment_count`다. 현재 초기 데이터의 캐릭터는 모두 열 개를 요구하며 캐릭터마다 열 개보다 큰 설정도 가능하다.
- 현재 조각 수는 현재 사용자·캐릭터 조합의 `ACQUIRED_AR_CHARACTER` 기록 개수다. 획득 기록 한 건을 조각 하나로 센다.
- 동일한 캐릭터를 서로 다른 미션에서 얻은 기록은 각각 한 조각이다. 캐릭터 ID로 중복 제거하여 한 건으로 줄이지 않는다.
- 출처 미션이 없거나 삭제된 획득 기록도 사용자·캐릭터 연결이 유지되면 조각에 포함한다. 다른 사용자의 기록은 포함하지 않는다.
- 획득 기록이 없으면 현재 조각 수는 영이다. 필요 조각 수를 넘어도 실제 개수를 반환하며 상한으로 잘라 저장하거나 표시용 수치로 대체하지 않는다.
- 온보딩 프로필 배정만으로 조각이 생겼다고 간주하지 않는다. 캐릭터 이미지 노출이나 보상 미션 설정 여부도 획득 기록을 대신하지 않는다.

## 7. 완성 여부와 최초 완성 날짜

- 현재 조각 수가 필요 조각 수 이상이면 캐릭터 완성으로 판정한다. 획득 기록이 한 건이라도 존재하면 완성으로 보던 이전 기준은 사용하지 않는다.
- 아직 필요 조각 수에 못 미치면 획득 날짜를 비운다. 중간 조각을 받은 날짜를 완성 날짜로 반환하지 않는다.
- 완성된 캐릭터는 본인의 해당 캐릭터 획득 기록을 `created_at` 오름차순, 같은 시각이면 획득 기록 ID 오름차순으로 정렬한다.
- 그 목록에서 필요 조각 수 번째 기록의 생성 날짜가 최초 완성 날짜다. 필요 열 개이면 열 번째 기록의 날짜를 사용하며 추가 획득으로 날짜를 바꾸지 않는다.
- 날짜는 저장 시각의 한국 표준시 기준으로 구성한다. 조회 과정에서 기록의 생성 시각을 덮어쓰거나 별도 완성 기록을 생성하지 않는다.

## 8. 캐릭터 획득 가능 미션

- 응답 이름은 실제 의미에 맞게 `availableMissions`를 사용한다. 획득 장소와 기존 획득 미션 이름의 필드는 응답에서 제거한다.
- 캐릭터가 완성되었다면 획득 가능 미션 목록은 비운다. 다른 미션에서 추가 조각을 받을 수 있는 기존 지급 동작은 이 조회 API에서 제한하지 않는다.
- 미완성 캐릭터는 문화·보물찾기·협동 세부 미션의 `ar_character_id`가 해당 캐릭터와 같은 활성 미션을 전체 후보로 사용한다.
- 사용자에게 이미 완료된 것으로 판정되는 공통 미션 ID를 제외한다. 문화·보물찾기는 본인의 진행도, 협동은 본인이 수락된 참가자로 속한 완료 팀을 기준으로 판정한다.
- 완료 판정과 별도로 해당 캐릭터를 이미 지급받은 미션도 제외한다. 획득 기록의 출처 미션과 사용자별 `MISSION_REWARD_STATUS.ar_character_reward_granted`를 확인한다. 재진행 중이어도 이미 캐릭터 조각을 받은 미션을 다시 추천하지 않는다.
- 포인트·쿠폰 지급 여부로 캐릭터 보상 지급 여부를 대신 판정하지 않는다. 반대로 캐릭터를 받지 못했더라도 완료된 미션이면 사용자가 정한 제외 기준을 적용한다.
- 사용자 완료·캐릭터 지급 내역은 공통 미션 ID로 비교하고, 여러 협동 팀이나 조인 결과 때문에 같은 미션이 중복되지 않도록 한다.
- 모든 제외 조건을 적용한 뒤 공통 미션 ID 오름차순으로 최대 세 개를 고른다. 먼저 세 개를 자르고 완료 기록을 제거하는 방식은 사용하지 않는다.
- 유효 후보가 네 개면 세 개, 두 개면 두 개, 한 개면 한 개를 반환한다. 없으면 목록을 비우며 이미 완료한 미션이나 비활성 미션으로 채우지 않는다.
- 현재 사용자 좌표를 받지 않으므로 거리나 장소 근접도로 선정하지 않는다.

## 9. 조회 일관성과 오류 처리

- 캐릭터 전체, 본인 획득 기록·집계, 유형별 보상 미션·진행 내역을 일괄 조회·조합하여 캐릭터나 미션마다 같은 조회를 반복하지 않는다.
- 응답은 공통 래퍼 없이 구성하고 nullable 키를 생략하지 않는다. 목록이 비어 있더라도 프로필·목표 걸음 수·요약 수치는 정상 구성한다.
- 조회는 읽기 전용 트랜잭션으로 처리한다. 포인트·쿠폰·캐릭터 조각을 지급하거나 보상 상태·진행도·획득 기록을 갱신하지 않는다.
- 도감 범위 밖의 캐릭터나 사용자에게 추천할 미션이 없는 경우를 도메인 오류로 만들지 않는다. 공통 인증·요청·서버 오류 처리는 기존 공통 방식을 따른다.

# 사용자 정보 조회 비즈니스 규칙

## 1. 요청과 현재 사용자 확인

- 요청·응답·오류 계약은 [사용자 정보 조회 API 명세](./API_SPEC.md#사용자-정보-조회-api)를 따른다.
- 인증 정보의 사용자 ID로 현재 사용자를 조회한다. 사용자가 없으면 기존 서비스와 동일하게 공통 인증 오류로 처리하고 후속 조회를 중단한다.
- 요청으로 사용자 ID를 받지 않으며 다른 사용자의 선택값을 조합하지 않는다.

## 2. 처리 순서

1. 현재 사용자와 연결된 온보딩 결과를 확인한다.
2. 본인의 여행 기대 항목 목록과 연결된 기준 항목을 함께 조회한다.
3. 본인의 주 이동 수단·여행 방식 선택 내역을 각각 연결된 기준 항목과 함께 조회한다.
4. 온보딩 결과·사용자 저장값·선택값을 전용 응답 DTO로 구성한다.

## 3. 프로필과 목표 걸음 수

- 여행 유형명과 프로필 이미지는 `USER.onboarding_result_id`로 연결된 `ONBOARDING_RESULT.user_type`, `profile_img_url`을 사용한다.
- 온보딩 결과가 없으면 유형명과 이미지만 비운다. 닉네임과 목표 걸음 수는 현재 사용자 저장값을 그대로 반환한다.
- 대표 AR 캐릭터 선택 상태나 캐릭터 획득 기록은 조회하지 않는다. 캐릭터 도감의 조각 집계도 이 API에서 수행하지 않는다.
- 목표 걸음 수에 서비스의 기본값을 다시 적용하거나 다른 값으로 대체하지 않는다.

## 4. 여행 선택값

- 여행 기대 항목은 현재 사용자의 `USER_EXPECTATION`을 `EXPECTATION`과 연결하여 기준 항목의 영문 코드를 반환한다. 선택 내역이 없으면 빈 목록이다.
- 주 이동 수단은 `USER_TRANSPORTATION`의 사용자 기본 키로 찾고 `TRANSPORTATION`의 영문 코드를 사용한다. 사용자당 한 건이며 없으면 비운다.
- 여행 방식은 `USER_TRAVEL_STYLE`의 사용자 기본 키로 찾고 `TRAVEL_STYLE`의 영문 코드를 사용한다. 사용자당 한 건이며 없으면 비운다.
- 여러 기대 항목을 허용하는 관계와 사용자당 하나인 이동 수단·여행 방식 관계를 응답 형태에도 반영한다. 이전 FastAPI의 사용자 JSON 배열 컬럼을 현재 스키마에 있다고 가정하지 않는다.
- 기준 항목을 함께 조회하여 기대 항목마다 지연 조회를 반복하지 않는다. 조회 과정에서 선택값을 새로 생성하거나 온보딩 결과를 다시 배정하지 않는다.

## 5. 응답과 상태 보존

- 마이페이지 전체 응답을 재사용하지 않고 사용자 정보 조회 전용 응답을 구성한다.
- 조회는 읽기 전용 트랜잭션으로 처리하며 사용자·온보딩 결과·선택 내역·목표 걸음 수·방명록 확인 시각을 갱신하지 않는다.
- nullable 키를 생략하지 않고 기대 항목은 항상 목록으로 구성한다. 선택 내역 부재를 전용 도메인 오류로 처리하지 않는다.

# 사용자 정보 변경 비즈니스 규칙

## 1. 요청 해석과 입력값 검증

- 요청·응답·오류 계약은 [사용자 정보 변경 API 명세](./API_SPEC.md#사용자-정보-변경-api)를 따른다.
- 요청에 실제로 포함된 필드만 변경 대상으로 사용한다. 요청 객체의 기본값으로 생략된 필드를 덮어쓰지 않는다.
- 생략과 명시적인 null을 구분한다. 여행 기대 항목은 빈 목록으로 해제하고, 주 이동 수단·여행 방식은 명시적인 null로 해제한다.
- 닉네임은 앞뒤 공백 제거 후 검증·저장하며, 다른 사용자와 같은 닉네임도 허용한다. 닉네임·목표 걸음 수·여행 기대 항목의 명시적인 null은 요청 검증 오류다.
- 기대 항목 중복과 각 필드의 형식·범위를 검증한다. 정의되지 않은 필드나 사용자 유형·이미지를 직접 지정하는 요청도 공통 요청 검증으로 처리한다.
- 빈 요청 객체는 아무것도 변경하지 않는 요청으로 처리한다. 온보딩 건너뛰기로 해석하거나 기존 선택값을 초기화하지 않는다.

## 2. 현재 사용자와 기준 데이터 확인

- 검증된 인증 정보의 사용자 ID로 현재 사용자를 확인한다. 요청에서 사용자 ID를 받지 않는다.
- 해당 사용자가 없으면 기존 사용자 조회와 동일한 공통 인증 오류로 처리하고 변경을 중단한다.
- 전달된 선택 코드에 해당하는 기준 데이터를 확인한다. 해제하는 값에는 새로운 기준 데이터를 연결하지 않는다.
- 기준 데이터나 배정 가능한 온보딩 결과가 누락되어 저장할 수 없으면 기존 공통 서버 오류로 처리한다. 별도 도메인 오류는 추가하지 않는다.

## 3. 부분 변경과 선택 관계 저장

1. 사용자의 현재 선택값을 읽고 요청에 포함된 값만 적용한 최종 선택값을 구성한다.
2. 모든 입력과 필요한 기준 데이터를 확인한 뒤 변경 사항을 반영한다.
3. 닉네임·목표 걸음 수는 요청에 포함됐을 때만 `USER.nickname`, `target_step`을 갱신한다.
4. 여행 기대 항목을 전달했으면 본인의 `USER_EXPECTATION`을 최종 목록으로 교체한다. 빈 목록이면 기존 연결을 모두 제거한다. 생략했으면 기존 연결을 유지한다.
5. 주 이동 수단·여행 방식을 전달했으면 각각 `USER_TRANSPORTATION`, `USER_TRAVEL_STYLE`의 사용자당 하나인 연결을 교체한다. 명시적인 null이면 해당 연결을 제거하고, 생략했으면 유지한다.
6. 실제 여행 선택값 변경 여부에 따라 온보딩 결과를 재배정한다.

- 이전 FastAPI의 사용자 JSON 배열 컬럼에 저장하는 방식을 복사하지 않고 현재 Spring의 선택 관계를 사용한다.
- 다른 사용자의 선택 내역, 보유 포인트, 방명록 확인 시각, 미션 진행도, 획득 쿠폰과 캐릭터 조각은 변경하지 않는다.

## 4. 여행 유형과 프로필 이미지 재배정

- 최종 여행 기대 항목·주 이동 수단·여행 방식 중 하나라도 저장된 선택값과 실제로 다를 때만 재배정한다. 요청에 필드가 있다는 이유만으로 재배정하지 않는다.
- 기대 항목은 순서에 의미가 없으므로 집합으로 비교한다. 동일한 항목의 순서만 바뀐 경우에는 재배정하지 않는다. 선택 내역이 없는 상태는 빈 기대 목록·선택하지 않은 단일 값으로 비교한다.
- 닉네임이나 목표 걸음 수만 변경한 요청, 같은 선택값을 다시 보낸 요청, 아무것도 변경하지 않는 요청은 기존 `USER.onboarding_result_id`를 유지한다.
- 재배정에는 생략된 필드의 기존 선택까지 포함한 최종 선택값을 사용한다. 요청에 들어온 일부 값만으로 매칭하지 않는다.
- 배정 규칙은 [기존 온보딩 비즈니스 규칙](../../onboarding/docs/BUISNESS_RULE.md#4-온보딩-결과-배정)을 재사용한다. 선택값이 모두 해제되면 기본 결과인 `여행자`를 배정하고, 하나라도 남아 있으면 일반 결과를 배정한다.
- 현재의 일반 결과 배정은 `여행자`를 제외한 결과 중 무작위 배정이다. 따라서 선택값이 달라져 재배정하더라도 기존과 동일한 결과가 나올 수 있다.
- TODO: 온보딩 결과 매칭 기준이 확정되면 기존 온보딩과 이 API가 공통으로 사용하는 배정 규칙을 최종 매칭 기준으로 변경한다. 구현 시 공통 배정 위치에 TODO 주석을 유지한다.
- 여행 유형과 프로필 이미지는 같은 `ONBOARDING_RESULT`에서 제공하므로 새 결과 연결로 함께 변경한다. AR 캐릭터 획득 기록을 생성·삭제하거나 캐릭터 조각을 지급하지 않는다.
- 온보딩 완료 처리 전체를 다시 실행하여 생략한 선택값을 지우거나 닉네임·목표 걸음 수를 초기화하지 않는다.

## 5. 재요청과 상태 보존

- 같은 최종 선택값으로 반복 요청해도 선택 관계가 중복 생성되지 않고, 이미 반영된 선택값을 이유로 온보딩 결과를 다시 뽑지 않는다.
- 온보딩 결과가 없는 사용자도 저장된 선택값과 요청으로 최종 선택값을 구성한다. 실제 선택 변경이 없는 요청에서는 결과가 없다는 이유만으로 새 결과를 배정하지 않는다.
- 이번 API에서 요청하지 않은 필드나 다른 도메인 상태를 초기화하지 않는다.

## 6. 트랜잭션과 정상 처리

- 사용자 확인 이후 필드 변경·선택 관계 교체·온보딩 결과 재배정을 하나의 쓰기 트랜잭션으로 처리한다.
- 선택 연결이나 결과 배정 중 하나라도 실패하면 닉네임·목표 걸음 수를 포함한 이번 변경 전체를 롤백한다. 기존 선택 관계를 삭제한 상태로 남기지 않는다.
- 전체 변경이 성공한 뒤 본문 없는 정상 응답을 반환한다. 최신 값은 사용자 정보 조회와 마이페이지 조회에서 확인한다.

# 여행 마무리 엽서 요소 조회 비즈니스 규칙

## 1. 현재 사용자 확인

- 요청·응답·오류 계약은 [여행 마무리 엽서 요소 조회 API 명세](./API_SPEC.md#여행-마무리-엽서-요소-조회-api)를 따른다.
- 인증 정보의 사용자 ID로 본인을 조회한다. 사용자가 없으면 기존 공통 인증 오류로 처리하고 후속 조회를 중단한다.
- 포인트는 현재 `USER.point`를 그대로 사용한다. 보상을 합산하거나 엽서 생성 비용을 차감하지 않는다.

## 2. 방문 장소

- 본인의 `VISITED_LOCATION`과 실제 존재하는 `LOCATION`을 연결한다. 다른 사용자의 기록이나 연결 장소가 없는 기록은 포함하지 않는다.
- 현재 스키마의 사용자·장소 유일 관계에 따라 같은 장소는 한 번만 반환한다.
- 정렬은 `last_visited_at` 내림차순, 동률이면 장소 ID 내림차순이다. FastAPI의 방문 시각 컬럼명 대신 현재 마지막 방문 시각을 사용한다.
- 장소 ID와 현재 장소명을 구성한다. 사진·TourAPI 이미지는 조회하지 않는다.

## 3. 완료 미션 후보

- 문화·보물찾기는 본인의 완료 상태 진행도 중 실제 완료 시각이 있는 기록을 사용한다.
- 문화 완료 시각은 `last_completed_at`, 보물찾기와 협동은 `completed_at`을 사용한다. `updated_at`이나 생성 시각을 완료 시각으로 대체하지 않는다.
- 협동은 본인이 수락된 참가자로 연결된 완료 팀을 사용한다. 공통 완료 판정기를 재사용하고 대기 참가자·진행 중 팀은 제외한다.
- 세 유형 모두 현재 세부 미션의 활성 상태를 확인하여 활성 미션만 포함한다. 완료 이후 비활성화됐어도 반환하지 않는다.
- 문화 미션은 장소가 없으므로 완료 장소를 비운다. 보물찾기·협동은 연결 장소가 실제 존재할 때만 포함하며 해당 장소명을 사용한다.
- 중단 API에서 완료 상태와 완료 시각이 기록된 미션도 포함한다. 보상 전부 수령·모든 문제 정답 여부로 완료 목록을 다시 제한하지 않는다.
- 문화·보물찾기를 재시작해 현재 진행 상태가 진행 중이면 이번 목록에서 제외한다. 이전 완료 시각만 남아 있다는 이유로 현재 진행 중인 기록을 완료로 취급하지 않는다.
- 이전 FastAPI의 소프트 삭제 컬럼은 현재 Spring 스키마에 있다고 가정하지 않는다. 존재하지 않는 미션·팀·참여 기록은 조합하지 않는다.

## 4. 중복 제거와 정렬

- 현재 Spring의 공통 `MISSION.id`로 동일 미션을 구분한다. 유형별 세부 미션은 이 기본 키를 공유하므로 별도 세부 ID를 생성하지 않는다.
- 같은 협동 미션을 여러 팀에서 완료했으면 가장 최근 완료 시각 한 건만 남긴다. 팀 수나 참가 기록 수만큼 같은 미션을 반복하지 않는다.
- 완료 시각 내림차순, 같은 시각이면 미션 유형의 영문 이름·공통 미션 ID 오름차순으로 순서를 고정한다.
- 미션 제목은 기존 v2 조회와 동일하게 연결된 `MISSION_TYPE.title`을 사용한다.

## 5. 보상 설정과 수령 여부

- 세부 미션의 캐릭터·포인트·쿠폰 설정 전체를 유지하고, 이미 받은 보상도 항목을 제거하지 않는다.
- 본인과 최종 미션 ID 목록에 해당하는 `MISSION_REWARD_STATUS`를 일괄 조회한다. 가장 최근 팀의 진행 기록만으로 보상 수령을 추측하지 않는다.
- 각 수령 여부는 해당 미션·사용자의 종류별 지급 플래그를 사용한다. 상태 기록이 없으면 모든 수령 여부를 거짓으로 구성한다.
- 설정된 보상이 없으면 그 항목만 비운다. 모든 보상이 없어도 보상 상세 객체는 유지한다. 포인트가 영으로 설정됐으면 영을 그대로 표시한다.
- 쿠폰 사용 여부와 보상 지급 여부를 혼동하지 않는다. 쿠폰 사용처 연결이 없어져도 쿠폰 설정을 제거하지 않고 사용처 이름만 비운다.
- 기존 지도 모달의 전체 보상 응답 변환을 재사용한다. 미션·보상 캐릭터·쿠폰·쿠폰 사용처를 함께 읽어 미션마다 지연 조회를 반복하지 않는다.

## 6. 응답과 읽기 전용 처리

- 방문 장소·완료 미션은 페이징 없이 최종 목록 전체를 반환하며 두 개수는 각각 구성한 배열 길이로 계산한다.
- 목록이 없으면 빈 목록과 영을 사용하고 현재 포인트는 유지한다. 미션이나 방문 내역 부재를 도메인 오류로 처리하지 않는다.
- 전체 조회는 읽기 전용 트랜잭션으로 처리한다. 방문 기록·미션 진행도·보상 상태·포인트·캐릭터 조각·쿠폰·방명록 확인 시각을 변경하지 않는다.
- 엽서 이미지 생성·사진 조회·외부 API 호출·DB 스키마 변경은 수행하지 않는다.
