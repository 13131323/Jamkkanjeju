## 발견하고 수정한 점

- 일반·길바닥 및 본인·타인 작성의 등록→취소→재등록, 실제 행 삭제·복합 PK 한 행, 전체 개수와 조회 API의 상태 일치, 작성자 삭제·장소 연결 없는 활성 기록 허용, 타 사용자/타 방명록 격리와 원본 저장값 보존을 확인했다. 본문 없는 POST와 양수 ID·인증·404 문구·Swagger 계약도 통과했다.
- 테스트 외부 트랜잭션을 끄고 실제 등록·취소 커밋을 확인했다. flush 후 집계 실패를 주입하면 생성·삭제가 모두 롤백됐으며 내부 예외 메시지가 응답에 노출되지 않았다.
- 같은 사용자의 두 요청은 기존 좋아요 유무 각각에서 첫 요청이 잠금을 쥔 동안 두 번째 요청이 사용자 조회를 마치고 잠금에 도달하게 했다. 두 응답은 등록·취소 한 번씩이며 최종 상태가 원래대로 돌아왔다. 서로 다른 두 사용자 동시 등록은 각 한 행·응답 개수 1과 2·최종 개수 2로 확인했다.
- 최초 동시성 실행의 2개 오류는 테스트에서 Spring Data 인터페이스 Spy에 `callRealMethod()`를 사용한 것이 원인이었다. 기존 레포지토리 프록시로 위임하는 Spy의 기본 Answer를 호출하도록 테스트만 보정했다. API 운영 코드·설정·스키마는 수정하지 않았다.
- 계획의 클래스·순서와 검증 항목을 유지했다. 동일 조건의 유형·작성자·경계·초기 좋아요 유무는 매개변수화하고, 준비와 정리는 `GuestbookLikeIntegrationTestSupport`로 공유했다. 프론트 버튼 차단 구현은 이번 백엔드 테스트에 포함하지 않았다.
- 최종 전체 1,118개가 통과했다. 최초 통합 `tour_test_812b702fadf64facaf2e93334a628561`, 보정 후 동시성 `tour_test_e4fa41e674484f35aed096bdb7cf4147`, 전체 회귀 `tour_test_a7170a04fc34426daddf146a18809347`의 임시 DB와 접근 권한이 모두 제거된 것을 확인했다. 개발 DB·볼륨과 외부 API는 변경하거나 호출하지 않았다.

- 실행일: 2026-10-27
- 전체 결과: 방명록 관련 단위 56개·통합 28개와 기존 테스트 971개, 총 1,055개 통과. 최종 실행 실패·오류·건너뜀 0개.
- 대상 API: `POST /api/v2/guestbooks`
- 기준 문서: `API_SPEC.md`, `BUISNESS_RULE.md`, `common/docs/commonError.md`

## 진행 방식

| 구분 | 방법 |
| --- | --- |
| 단위 테스트 | JUnit 5·AssertJ·Mockito로 요청·응답·서비스 분기를 검증하고, 공통 오디오 검증은 실제 FFmpeg와 고정 미디어로 확인한다. 고정 Clock과 `guestbook/support` 픽스처를 사용한다. 기존 공통 이미지 검증은 회귀 테스트로 재사용한다. |
| 통합 테스트 | MySqlIntegrationTestSupport·실제 JWT·MockMvc·임시 MySQL로 저장·격리·롤백을 검증한다. Blob만 Mock으로 격리하고 고정 UTC Clock으로 KST 저장을 확인한다. 실제 multipart 제한은 임의 포트 HTTP 서버에서 확인한다. |

일반 통합 테스트는 트랜잭션으로 롤백한다. 실제 커밋·서비스 실패·커밋 실패와 HTTP 서버 검증은 테스트 외부 트랜잭션을 끄고, 직접 준비한 데이터를 `finally`에서 정리한다. 개발 DB·실제 Azure·OpenAI를 사용하지 않는다.

## 실행 순서

1. 요청·응답·오디오·서비스 단위 테스트를 구현하고 실행한다.
2. 임시 MySQL에서 MockMvc·실제 HTTP 통합 테스트를 구현하고 실행한다.
3. 기존 전체 테스트를 실행하여 회귀 확인한다. 기존과 같이 실행 시 컨텍스트 캐시 크기를 제한한다.
4. 임시 DB·접근 권한 제거를 확인하고 실제 결과를 기록한다.

## 발견하고 수정한 점

- 2026-10-27 최종 요구에 맞춰 이미지·오디오 각각 10,000,000바이트, 오디오 30초 이하와 실제 디코딩 검증으로 변경했다. 시간 초과·손상 오류를 추가했으며 서블릿의 선행 크기 제한은 해제했다. 기존 임의 전체 요청 상한과 이를 위해 추가한 Tomcat 잔여 본문 설정은 현재 적용하지 않는다.
- 여섯 형식은 작은 정상 인코딩 파일로 검증했다. 정확히 10MB의 정상 WAV는 JUNK 청크로 파일 크기를 맞추고, 30초/30.001초 WAV는 실제 PCM 샘플 수로 경계를 고정했다. 헤더만 남은 WAV·M4A·MP3와 오디오 없는 컨테이너는 손상 오류로 거절했다. 디코더 미설치는 파일 오류로 숨기지 않고 서버 오류로 구분했다.
- 단위 56개·통합 28개가 통과했다. 오디오 시간 초과·손상으로 실패한 요청에서도 먼저 업로드한 이미지를 정리하고 DB 행을 롤백했다. 실제 HTTP에서 이미지·오디오 각각 10MB의 동시 업로드, 각 파일의 1바이트 초과 오류, 30초 경계와 손상 오류를 확인했다.
- 첫 전체 회귀 중 MySQL 컨테이너가 종료되어 연결 오류가 발생했다. MySQL만 다시 기동한 뒤 전체 회귀 1,055개가 통과했다. 중단된 실행 이름 `tour_test_2b410154db3c46b183b57aa9dab12fa5`의 DB·권한은 남지 않았다. 별도 통합의 `tour_test_251b857aee204d66ae795ae2e4e71256`과 최종 전체 실행의 `tour_test_34bb72367fb34c90ae805bdaef1a4194`도 정리되었음을 확인했다.
- `Dockerfile`에 FFmpeg 설치를 추가한 검증용 이미지 `tour-audio-validation` 빌드가 성공했다. 로컬 검증용 실행 파일은 `target/audio-test-tools`에만 내려받아 `FFMPEG_PATH`로 지정했다. Maven 의존성이나 시스템 전역 설치는 추가하지 않았다. 관련 임시 DB·권한과 오디오 검증 임시 폴더는 남지 않았다.
- 아래 기록은 최초 구현·이전 설정의 실행 이력이며, 현재 크기·시간·손상 기준과 설정은 위 최종 결과를 따른다.
- 2026-10-27 사용자 요청으로 전체 요청 용량 전용 에러코드와 전역 핸들러 분기를 제거하고 공통 `400 INVALID_REQUEST`로 변경했다. 변경 후 `CreateGuestbookHttpIntegrationTest` 5개를 재실행하여 모두 통과했다. 이 변경에서는 전체 회귀를 반복하지 않았다. 이번 임시 DB `tour_test_6f26a2088d7c429c948ac40e055b648e`와 접근 권한 삭제를 확인했다.
- 새 테스트 77개와 기존 971개가 최종 전체 실행에서 통과했다. 계획의 클래스와 실행 순서를 유지했고, 요청 오류·파일 헤더·미션 유형·실패 시점은 매개변수화하거나 같은 준비 조건의 여러 요청으로 묶었다.
- 최초 단위 실행에서 UTC Clock을 주입하면 `savedAt`이 KST보다 아홉 시간 이르게 저장되는 문제를 발견했다. `GuestbookService`를 기존 AR 사진 저장과 동일하게 `Clock.instant()`를 `Asia/Seoul`로 변환하도록 수정했다. 방문 날짜는 사용자 입력을 그대로 유지했다.
- 최초 통합 실행의 시각 JSON 기대값에 초가 빠져 두 케이스가 실패했다. 실제 명세 형식인 `2026-10-27T12:00:00`으로 테스트 기대값을 수정했으며 응답 직렬화 정책은 변경하지 않았다.
- 실제 HTTP에서 전체 41MB 초과 요청의 오류 응답이 연결 종료로 유실되는 문제를 발견했다. [Tomcat HTTP Connector 문서](https://tomcat.apache.org/tomcat-11.0-doc/config/http.html)의 `maxSwallowSize` 동작과 로컬 Spring Boot 소스를 확인하여 `server.tomcat.max-swallow-size=-1`로 잔여 본문을 소비하도록 설정했다. 이미지 10MB·오디오 30MB·전체 요청 41MB 저장 제한은 유지했다.
- HTTP 테스트는 기존 사진 HTTP 테스트처럼 일반 HTTP/1.1 전송을 사용했다. JDK 클라이언트의 `Expect: 100-continue` 옵션에서 추가 전송 오류가 발생해 해당 옵션을 제거했다. 이후 동일 테스트를 기본 Tomcat 잔여 본문 한도(2MiB)로 비교 실행하면 연결 오류가 재현되고, 최종 설정에서는 지정한 400 JSON을 받음을 확인했다.
- 정확히 이미지 10,000,000바이트와 오디오 30,000,000바이트의 동시 업로드는 실제 서버에서 성공했다. 각 파일 한 바이트 초과는 개별 용량 오류, boundary 누락은 공통 요청 오류로 반환했다. 당시 전체 요청 초과는 별도 용량 오류로 검증했으며, 이후 사용자 요청으로 공통 요청 오류로 변경했다. 기존 사진 업로드의 10MB 제한도 전체 회귀 테스트에서 유지되었다.
- GENERAL/ROAD는 공통 ID를 공유하는 행과 단일 URL로 저장됐다. 사용자 제목 20자, 제목/오디오 선택 조합, nullable 응답, 날짜 불일치 허용, 새 ID·UUID를 쓰는 반복 작성과 기존 사용자·방문·미션·보상 상태 보존을 확인했다.
- 세 유형의 본인 완료 미션만 연결하고 타 사용자 완료·미완료·협동 PENDING은 연결하지 않았다. 협동의 과거 ACCEPTED 완료는 현재 진행 중인 팀이 있어도 인정했다. 비활성 미션은 완료 이력보다 먼저 거절했고 미션이 작성 장소와 연결되지 않아도 기존 정책대로 연결했다.
- 실제 커밋 성공 시 Blob 삭제가 호출되지 않았다. 뒤쪽 오디오 검증/업로드 실패와 DB flush/커밋 직전 실패에서는 새 공통·유형별 행이 롤백되고 성공한 업로드만 삭제됐다. Blob 삭제 실패 시 방명록 식별자와 오류 로그를 확인했으며 최초 오류 응답은 유지됐다.
- Swagger에 파일·제목 최대 길이·201 응답이 반영되고 검증용 내부 메서드는 요청 필드에서 제외됨을 확인했다. 외부 Azure·OpenAI 호출은 없었다.
- 전체 회귀는 실행 시 컨텍스트 캐시 크기를 4로 제한해 진행했다. `tour_test_3c940884e2ba4e868f54d8546000a3e9`, `tour_test_1b1023a86abf4ffdb96dd57fbc06a62a`, `tour_test_214bec4fe2dc4fdfb45d2a6045fd4bfb`, `tour_test_87390b5a6b2c48bdaf414edc1ada7592`, `tour_test_8be04d92eeaa493f92fb4dde3cc6b397`, `tour_test_e81ac6b9b0484bb4b49dcdcc76350241`이 자동 삭제되었고 해당 DB와 접근 권한은 각각 0개임을 확인했다. 개발 DB·컨테이너·볼륨은 변경하지 않았다.
