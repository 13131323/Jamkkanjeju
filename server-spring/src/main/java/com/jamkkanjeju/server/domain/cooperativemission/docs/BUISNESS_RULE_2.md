# 협동 미션 상태 조회 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC_2.md)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져오며 요청에서 참가자 ID·역할·참가 상태를 별도로 받지 않는다.
- 요청의 진행도 ID는 팀 단위 `COOPERATIVE_MISSION_PROGRESS.id`이며 공통 미션 ID와 구분한다.
- 사용자 좌표는 완료 단계의 다음 장소 추천과 거리 계산에 사용한다.
- 조회 단계와 관계없이 요청 좌표 검증은 동일하게 적용한다.

## 2. 진행도와 미션 확인

- 요청 ID에 해당하는 팀 진행도와 연결된 협동 미션을 조회한다.
- 진행도가 없으면 `COOPERATIVE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 진행 중인 팀뿐 아니라 완료된 팀도 조회하므로 진행 상태를 `IN_PROGRESS`로 제한하지 않는다.
- 연결된 협동 미션이 비활성 상태이면 `COOPERATIVE_MISSION_INACTIVE`로 처리한다.
- 협동 미션의 장소가 없어도 상태 조회를 허용한다.
- 조회 과정에서 진행도를 생성·초기화하거나 단계를 변경하지 않는다.

## 3. 현재 참가자 확인

- 진행도 ID와 현재 사용자 ID가 모두 일치하는 참가자를 조회한다.
- 참가자가 없으면 `COOPERATIVE_MISSION_PARTICIPANT_NOT_FOUND`로 처리한다.
- 참여 요청 거절로 행이 삭제된 경우도 참가자 없음으로 처리한다.
- 방장·팀원과 대기·수락 상태 모두 조회할 수 있다. 대기 참가자를 조회 과정에서 자동 수락하지 않는다.
- 완료 단계에서도 참가자 확인을 먼저 수행한다. 완료 응답에서 현재 참가자 정보를 숨긴다는 이유로 권한 확인을 생략하지 않는다.
- 요청에 포함된 다른 사용자의 참가자 ID를 신뢰하거나 다른 팀 상태를 반환하지 않는다.

## 4. 단계와 응답 구성 범위

| 단계 | 의미 | 진행 상태 |
| --- | --- | --- |
| 1 | 초대·역할 배정 | `IN_PROGRESS` |
| 2 | 미션 수행 및 사진 인증 | `IN_PROGRESS` |
| 3 | 미션 완료 | `COMPLETED` |

- 별도의 역할 배정 단계를 두지 않고 초대와 역할 배정을 같은 첫 단계에서 진행한다.
- 모든 단계에서 팀 진행도 ID, 공통 미션 ID, 연결된 미션 제목, 저장된 진행 상태와 현재 단계를 반환한다.
- 첫 단계와 수행 단계에서는 현재 참가자·전체 참가자·역할 카드·역할 수행 목록과 역할 집계를 구성한다.
- 완료 단계에서는 참가자·역할 관련 필드를 사용하지 않고 완료 장소·현재 사용자 보상 정보·다음 장소를 구성한다.
- 현재 단계에 사용하지 않는 필드는 생략하지 않고 명세에 따라 null로 구성한다.
- 역할이 모두 인증되었다는 이유만으로 조회 API에서 완료 상태로 전환하지 않는다. 저장된 팀 상태를 기준으로 응답한다.
- 완료 시 단계·진행 상태·완료 시각을 변경하는 책임은 진행도 저장 API에 있다.

## 5. 참가자 목록 구성

- 해당 팀에 등록된 방장과 대기·수락된 팀원을 모두 조회한다.
- 방장을 먼저 배치하고 그 외 참가자는 생성 시각 오름차순으로 정렬한다.
- 참가자 ID·닉네임·팀 내 역할·참가 상태는 각 참가자와 연결된 사용자 정보를 기준으로 구성한다.
- 현재 참가자 정보는 앞서 조회한 현재 사용자의 참가자 행을 기준으로 구성한다.
- 거절되어 삭제된 참가자는 목록에 포함하지 않는다.
- 참가자 조회를 위해 합류 시각이나 참가 상태를 갱신하지 않는다.

## 6. 역할 카드와 역할 수행 목록

- 첫 단계부터 공통 역할 카드 전체와 현재 저장된 배정·수행 기록을 반환한다.
- 역할 카드는 카드 ID 오름차순으로 정렬한다.
- 역할 수행 기록은 대상 팀 참가자와 연결된 기록만 조회하며 다른 팀의 같은 카드 수행 기록을 포함하지 않는다.
- 현재 스키마에서 역할 수행 기록은 참가자 ID와 역할 카드 ID의 복합키로 식별한다.
- 응답에는 참가자 ID와 역할 카드 ID가 이미 있으므로 별도의 단일 `roleProgressId`를 만들거나 가상 ID로 대체하지 않는다.
- 역할 수행 목록은 참가자 ID, 역할 카드 ID 오름차순으로 정렬한다.
- 각 수행 기록은 담당 참가자 ID·닉네임, 역할 카드 ID·이름, 인증 진행 상태와 이미지 URL로 구성한다.
- 아직 저장된 역할 배정이 없으면 빈 목록을 반환한다.
- 역할 카드 하나는 같은 팀에서 최대 한 명에게 배정하고 한 참가자는 서로 다른 여러 카드를 맡을 수 있다는 기존 배정 규칙을 유지한다.
- 미배정 카드는 역할 카드 목록에는 포함하지만 수행 목록에는 포함하지 않는다.
- 역할 배정 저장 이후의 조회에는 커밋된 배정 결과를 반영한다.
- 이 API는 역할 카드를 배정하거나 역할 수행 기록을 생성·변경하지 않는다.

## 7. 역할 집계

- 전체 역할 수는 해당 팀에 실제 생성된 역할 수행 기록 수로 계산한다.
- 완료 역할 수는 그중 인증 진행 상태가 완료인 기록 수로 계산한다.
- 참가자 수나 공통 역할 카드 전체 개수를 전체 역할 수로 대신 사용하지 않는다.
- 배정이 없으면 전체·완료 역할 수는 모두 0이다.
- 첫 단계와 수행 단계에서 집계값을 반환하며 완료 단계에서는 사용하지 않는다.
- 집계 결과만으로 인증 상태·팀 진행 상태를 변경하거나 보상을 지급하지 않는다.

## 8. 완료 장소 구성

- 완료 단계에서 해당 협동 미션에 연결된 장소의 ID와 장소명을 구성한다.
- 연결된 장소가 없으면 완료 장소는 null로 구성한다.
- 완료 장소는 방금 완료한 미션의 장소이며 다음 추천 장소와 구분한다.
- 첫 단계와 수행 단계에서는 완료 장소를 구성하지 않는다.

## 9. 완료 보상 조회

- 보상 정산과 지급은 진행도 저장 API에서 팀을 완료 처리할 때 수행한다.
- 협동 미션 보상은 완료 역할 수·사진 인증 성공 여부와 관계없이 사용자별 해당 미션 최초 완료 시 한 번만 지급한다.
- 지급 대상은 완료 시점의 `ACCEPTED` 참가자이며 방장·팀원 역할을 구분하지 않는다. `PENDING` 참가자에게는 지급하지 않는다.
- 참가자마다 사용자와 공통 미션 조합의 `MISSION_REWARD_STATUS` 및 기존 완료 참가 이력을 확인한다. 현재 진행 중인 팀의 참가 기록이 있다는 이유만으로 재도전으로 판단하지 않는다.
- 기존 완료·지급 이력이 없는 참가자에게 미션에 설정된 AR 캐릭터·포인트·쿠폰을 모두 지급하고 지급 상태를 갱신한다. 미션에 설정되지 않은 보상은 지급하지 않는다.
- 기존에 같은 미션의 보상을 지급받은 참가자에게는 아무 보상도 지급하지 않는다. 일부 항목만 남아 있다고 재도전에서 나누어 지급하는 방식은 사용하지 않는다.
- 같은 팀에 최초 완료 사용자와 재도전 사용자가 섞여 있으면 각 사용자의 이력에 따라 지급 여부를 따로 결정한다.
- 진행도 저장에서는 완료 상태·완료 시각 변경과 참가자 보상 지급을 하나의 트랜잭션으로 처리한다. 지급 실패 시 완료 처리와 보상 변경을 함께 롤백한다.
- 기존 FastAPI처럼 완료 상태를 처음 조회할 때 보상을 정산하는 처리는 가져오지 않는다.
- 이 API는 현재 사용자가 수락된 참가자로 완료한 동일 미션의 팀 이력을 조회하여 최초 완료 팀을 찾는다.
- 최초 완료 팀은 완료 시각이 가장 이른 팀이며, 완료 시각이 같으면 진행도 ID가 작은 팀을 선택한다. 최초 완료 판단은 전체 팀이나 방장 기준이 아니라 현재 사용자 기준으로 수행한다.
- 조회 중인 팀이 현재 사용자의 최초 완료 팀이면 해당 팀에서 지급된 미션의 보상 정보를 구성한다. 보상 구성은 완료 역할 수에 따라 줄이지 않는다.
- 조회 중인 팀이 이후 재도전 팀이면 `reward` 객체의 모든 항목을 null로 구성한다. 사용자·미션의 누적 지급 상태가 true여도 과거 팀의 보상을 현재 팀의 보상처럼 반환하지 않는다.
- 최초 완료 팀을 나중에 다시 조회하더라도 해당 최초 완료 보상 정보를 동일하게 반환한다. 이후 팀이 생겼다는 이유로 최초 팀의 보상 표시를 바꾸지 않는다.
- 최초 완료 팀의 보상 항목은 미션에 설정된 보상과 현재 사용자의 지급 상태를 함께 확인하여 구성한다. 설정되지 않았거나 지급되지 않은 항목은 null이다.
- 이 방식으로 보상 지급 결과를 재구성할 수 있도록 완료된 진행도와 참가자 이력은 유지한다. Redis·서버 메모리 등에 별도의 지급 결과를 보관하지 않는다.
- 반복 폴링이나 여러 참가자의 동시 조회로 포인트·AR 캐릭터·쿠폰을 추가 지급하지 않는다.
- `MISSION_REWARD_STATUS`는 사용자와 공통 미션 조합의 지급 관리 데이터이며, 조회 과정에서 생성·초기화하거나 지급 여부를 변경하지 않는다.
- 완료 보상이 하나도 없어도 완료 응답의 보상 객체는 유지하고 각 항목을 null로 구성한다.
- 첫 단계와 수행 단계에서는 보상 정보를 구성하지 않는다.
- 아직 지급되지 않은 보상이 보이더라도 이 조회를 복구·재지급 작업으로 사용하지 않는다.

## 10. 다음 장소 구성

- 완료 단계에서 현재 사용자의 요청 좌표를 기준으로 다음 장소를 추천한다.
- 사용자 좌표에서 직선거리가 가장 가까운 장소를 선택하고 거리가 같으면 장소 ID가 작은 장소를 선택한다.
- 완료한 협동 미션에 장소가 연결되어 있으면 그 장소는 추천 후보에서 제외한다. 연결된 장소가 없으면 제외할 장소도 없다.
- 기존 장소 추천 공통 컴포넌트를 재사용하며 이 서비스에 거리·추천 로직을 중복 구현하지 않는다.
- 공통 추천 구현에 `// TODO: 추후 사용자 개인화된 추천 로직을 적용한다.` 주석을 유지한다.
- 사용자마다 좌표가 다르므로 추천 결과가 다를 수 있고 폴링 사이에 같은 장소를 유지할 의무는 없다.
- 기존 FastAPI 상태 조회와 동일하게 추천 후보가 없으면 다음 장소를 null로 구성한다.
- 추천 장소 이미지 조회에 실패하거나 이미지가 없으면 이미지 URL은 null로 구성한다.
- 추천 장소에 연결된 미션이 없으면 다음 미션은 null로 구성한다. 연결된 미션이 있으면 기존 공통 추천 규칙으로 미션 ID와 유형을 구성한다.
- 거리 정보는 요청 좌표에서 추천 장소까지의 직선거리를 미터 단위로 구성한다.
- 첫 단계와 수행 단계에서는 장소 추천과 이미지 조회를 실행하지 않는다.
- 추천 결과를 저장하거나 추천 실패를 이유로 기존 완료 상태·보상 결과를 변경하지 않는다.

## 11. 폴링과 반복 조회

- 첫 단계에서는 현재 참가 상태로 대기·수락 여부를 확인하고 역할 배정 변경을 반영한다.
- 수행 단계에서는 역할별 인증 상태와 집계값을 반영한다.
- 완료 단계의 응답을 받은 프론트는 폴링을 중단하고 완료 화면을 표시한다.
- 대기 중이던 사용자의 참가자 행이 삭제되어 참가자 없음 오류가 반환되면 프론트는 거절로 처리하고 폴링을 중단한다.
- 비활성 미션이나 진행도 없음 오류를 받은 경우에도 폴링을 중단한다.
- 동일 조건의 반복 조회는 팀·참가자·역할·보상 데이터를 변경하지 않는다.
- 보상·상태 변경이 커밋된 뒤의 새 조회는 변경 결과를 읽어야 한다.

## 12. 조회 트랜잭션과 실패 시 보존

- 진행도·미션 검증, 현재 참가자 확인과 단계별 데이터 조회를 읽기 전용 트랜잭션으로 처리한다.
- 보상 정산을 위한 비관적 쓰기 잠금은 사용하지 않는다.
- 같은 응답의 팀 단계와 참가자·역할 집계가 서로 다른 시점의 변경을 섞지 않도록 같은 조회 트랜잭션에서 구성한다.
- 첫 단계부터 완료 단계까지 DB 쓰기 작업을 수행하지 않는다.
- 오류가 발생해도 기존 진행도·참가자·역할 수행·보상 지급 상태와 사용자 획득 데이터는 그대로 유지한다.
- 예상하지 못한 조회 오류를 진행도 없음이나 참가자 없음으로 바꾸지 않고 공통 서버 오류로 처리한다.

# 협동 미션 진행도 저장 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC_2.md#협동-미션-진행도-저장-api)를 따른다.
- 현재 사용자 ID는 검증된 인증 정보에서 가져온다.
- 요청의 진행도 ID는 팀 단위 `COOPERATIVE_MISSION_PROGRESS.id`이며 공통 미션 ID와 구분한다.
- 요청의 `currentStep`은 현재 단계가 아니라 변경하려는 다음 단계이다.
- 방장 ID·현재 단계·역할 배정·보상 지급 여부를 요청에서 받지 않는다. 저장된 데이터를 기준으로 판단한다.

## 2. 처리 순서

1. 요청 형식과 현재 사용자를 확인한다.
2. 대상 팀 진행도를 쓰기 잠금으로 조회하고 연결된 협동 미션의 활성 상태를 확인한다.
3. 현재 사용자가 대상 팀의 수락된 방장인지 확인한다.
4. 팀의 완료 여부와 요청 단계가 순차적인 다음 단계인지 확인한다.
5. 수행 단계 진입이면 대기 참가자 여부와 수락된 참가자의 역할 배정을 검증한다.
6. 완료 단계 진입이면 배정된 역할의 인증이 모두 완료되었는지 검증한다.
7. 수행 단계 진입은 단계만 변경한다.
8. 완료 단계 진입은 참가자별 최초 완료·지급 여부를 판단하여 보상을 지급하고 단계·진행 상태·완료 시각을 함께 변경한다.
9. 전체 처리가 성공하면 커밋한다. 응답 본문은 구성하지 않는다.

## 3. 진행도와 미션 확인

- 요청 ID에 해당하는 진행도가 없으면 `COOPERATIVE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 완료된 진행도를 진행도 없음으로 처리하지 않도록 조회 조건을 진행 중 상태로 제한하지 않는다.
- 연결된 협동 미션이 비활성 상태이면 `COOPERATIVE_MISSION_INACTIVE`로 처리한다.
- 미션의 장소는 nullable이며 장소가 없다는 이유로 단계 변경이나 완료 처리를 막지 않는다.
- 이 API는 진행도나 참가자를 새로 생성하지 않는다.

## 4. 방장 권한 확인

- 대상 진행도와 현재 사용자에 해당하는 참가자를 확인한다.
- 팀 내 역할이 방장이고 참가 상태가 수락인 경우에만 변경을 허용한다.
- 참가자가 없거나 팀원이거나 대기 상태이면 `COOPERATIVE_MISSION_HOST_ONLY`로 처리한다.
- 다른 팀의 방장이라는 이유로 대상 진행도에 대한 변경을 허용하지 않는다.

## 5. 순차 단계 변경

- 초대·역할 배정 단계에서 수행 단계로, 수행 단계에서 완료 단계로 한 단계씩만 변경한다.
- 동일 단계·역행·건너뛰기·지원하지 않는 단계 요청은 `COOPERATIVE_MISSION_STEP_NOT_ALLOWED`로 처리한다.
- 이미 완료 상태이거나 마지막 단계인 팀의 변경 요청도 같은 오류로 처리한다.
- 기존 FastAPI의 완료된 미션 오류를 별도로 사용하지 않고 단계 변경 오류로 통합한다.
- 역할 배정 저장과 역할 인증 저장은 별도 API의 책임이다. 이 API는 해당 기록을 조회하여 전환 조건만 검증한다.

## 6. 초대·역할 배정 단계에서 수행 단계로 변경

- 해당 팀에 대기 참가자가 있는지 먼저 확인한다.
- 대기 참가자가 한 명이라도 있으면 `COOPERATIVE_MISSION_PENDING_PARTICIPANT_EXISTS`로 처리한다.
- 대기 참가자를 자동 수락하거나 삭제하지 않는다. 방장이 참여 요청 수락·거절을 마친 뒤 다시 요청해야 한다.
- 대기 참가자가 없으면 방장을 포함한 수락된 참가자 모두에게 역할 수행 기록이 최소 하나 연결되어 있는지 확인한다.
- 역할을 하나도 배정받지 않은 수락된 참가자가 있으면 `COOPERATIVE_PARTICIPANT_ROLE_REQUIRED`로 처리한다.
- 역할 보유 여부는 해당 팀 참가자의 실제 역할 수행 기록으로 판단하고 다른 팀 기록은 포함하지 않는다.
- 공통 역할 카드 전체를 배정할 필요는 없으며 한 참가자가 서로 다른 여러 역할을 맡아도 된다.
- 두 검증을 모두 통과하면 현재 단계만 다음 단계로 변경한다.
- 진행 상태는 유지하고 완료 시각·보상 지급 상태·사용자 획득 데이터는 변경하지 않는다.

## 7. 수행 단계에서 완료 단계로 변경

- 해당 팀에 배정된 역할 수행 기록의 인증이 모두 완료되었는지 확인한다.
- 전체 공통 역할 카드가 아니라 실제로 해당 팀에 배정된 역할 수행 기록을 검증한다.
- 미인증 역할이 하나라도 남아 있으면 `COOPERATIVE_MISSION_STEP_NOT_ALLOWED`로 처리한다.
- 미인증 상태에서의 강제 종료는 별도의 협동 미션 중단 API 책임이며 이 API에서 허용하지 않는다.
- 검증을 통과하면 완료 시점의 수락된 참가자를 보상 지급 대상으로 확정한다. 방장·팀원을 구분하지 않으며 대기 참가자는 제외한다.
- 참가자별 지급 판단과 처리가 성공하면 현재 단계를 마지막 단계로, 진행 상태를 완료로 변경한다.
- 완료 시각은 주입받은 `Clock`으로 구한 현재 시각을 저장하며 팀에 한 번만 기록한다.
- 기존 역할 수행 기록·참가자 이력은 삭제하거나 초기화하지 않는다.

## 8. 사용자별 최초 완료 판단

- 판단 기준은 참가자별 사용자와 공통 미션 조합이다. 방장이나 팀 전체의 최초 완료 여부로 대신하지 않는다.
- 현재 팀을 완료 처리하기 전에 동일 사용자가 수락된 참가자로 완료했던 다른 팀 이력과 `MISSION_REWARD_STATUS`를 확인한다.
- 현재 진행 중인 팀의 참가 기록이나 다른 진행 중인 팀의 기록을 기존 완료 이력으로 판단하지 않는다.
- 기존 완료 이력이 없고 보상 지급 상태 행이 없으면 최초 완료 지급 대상이다.
- 지급 상태 행이 있어도 세 항목이 모두 미지급이고 기존 완료 이력이 없으면 최초 완료 지급 대상이다.
- 지급 상태 중 하나라도 지급 완료이면 추가 지급하지 않는다. 다른 항목이 미지급이어도 재도전에서 채워 지급하지 않는다.
- 지급 상태가 없거나 전부 미지급이어도 기존 완료 이력이 있으면 재도전으로 판단하여 지급하지 않는다.
- 같은 팀에 최초 완료 사용자와 재도전 사용자가 섞여 있어도 각 사용자를 독립적으로 판단한다.
- 지급 대상이 아닌 참가자도 팀의 완료 결과에는 포함되며 기존 지급 상태를 초기화하지 않는다.

## 9. 최초 완료 보상 지급

- 최초 완료 지급 대상에게 미션에 설정된 AR 캐릭터·포인트·쿠폰을 모두 지급한다.
- 완료 역할 수에 비례하여 일부만 지급하거나 참가자 수로 나누지 않는다.
- 미션에 설정되지 않은 보상은 지급하지 않고 해당 지급 여부를 임의로 지급 완료로 변경하지 않는다.
- AR 캐릭터 획득 기록, 사용자 포인트 증가, 쿠폰 획득 기록과 미션별 지급 상태 반영은 기존 공통 보상 지급 컴포넌트를 재사용한다.
- 공통 컴포넌트는 미지급 항목을 추가 지급할 수 있으므로 협동 미션의 최초 완료 판단을 먼저 통과한 사용자에게만 호출한다.
- 지급 상태 행이 없고 실제 지급할 보상이 있으면 사용자·공통 미션 조합으로 생성한다.
- 지급 상태 행이 이미 있으면 기존 행을 사용하고 실제 지급한 항목만 지급 완료로 갱신한다.
- 설정된 보상이 하나도 없으면 획득 데이터나 지급 완료 표시를 만들지 않는다. 재도전 여부는 보존된 완료 참가 이력으로 판단할 수 있어야 한다.
- 동일 캐릭터·쿠폰의 기존 보유 여부에 따른 획득 기록 처리는 공통 보상 지급 컴포넌트의 기존 규칙을 따른다.
- 완료된 진행도와 참가자 이력은 상태 조회 API의 최초 완료 팀 판단에 필요하므로 보존한다.

## 10. 응답과 상태 조회 연계

- 성공 시 응답 본문 없이 반환하며 보상이나 다음 장소를 응답으로 구성하지 않는다.
- 사용자 좌표를 받거나 장소 추천·이미지 조회를 실행하지 않는다.
- 프론트는 다음 상태 조회에서 변경된 단계와 완료 상태·사용자별 보상을 확인한다.
- 상태 조회 API에서 보상을 지급하거나 복구하도록 의존하지 않는다. 이 API의 커밋 시점에 지급 처리가 끝나 있어야 한다.
- 완료 단계의 보상 표시는 기존 상태 조회 규칙을 따르며 최초 완료 팀에는 지급된 항목, 재도전 팀에는 빈 보상 객체가 표시된다.

## 11. 동시 요청과 중복 지급 방지

- 대상 팀 진행도 행을 잠근 상태에서 권한·현재 단계·전환 조건을 확인하고 변경한다.
- 참여 요청·수락·거절 등 기존 팀 변경 API와 동일한 팀 진행도 잠금 기준을 사용한다.
- 같은 단계 변경 요청이 동시에 들어오면 선행 요청의 처리가 끝난 뒤 후행 요청이 최신 상태를 확인한다.
- 선행 요청이 이미 단계를 변경했다면 후행 요청은 동일 단계 또는 완료된 팀에 대한 요청이므로 단계 변경 오류로 처리한다.
- 보상 최초 지급 판단과 획득·포인트·지급 상태 반영도 잠금 및 동일 트랜잭션 안에서 수행한다.
- 중복 요청이 참가자 보상 지급이나 포인트 증가를 반복하지 않도록 한다.

## 12. 트랜잭션과 실패 시 보존

- 진행도 조회부터 권한·전환 조건 검증, 참가자별 최초 완료 확인, 보상 지급과 완료 처리까지 하나의 쓰기 트랜잭션으로 처리한다.
- 한 참가자의 지급 처리라도 실패하면 팀 완료와 다른 참가자의 지급 결과까지 함께 롤백한다.
- 실패 시 기존 단계·진행 상태·완료 시각·역할 기록·지급 상태·사용자 포인트·획득 기록을 유지한다.
- 검증 실패를 보완하려고 역할 배정이나 참가 상태를 임의로 변경하지 않는다.
- 예상하지 못한 지급·저장 오류를 정상 완료로 숨기지 않고 공통 서버 오류로 처리한다.

# 협동 미션 역할 배정 저장 비즈니스 규칙

## 1. 요청 및 현재 사용자 확인

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC_2.md#협동-미션-역할-배정-저장-api)를 따른다.
- 현재 사용자는 검증된 인증 정보에서 식별한다.
- 경로의 진행도 ID는 팀 진행도, 역할 카드 ID는 공통 역할 카드, 본문의 참가자 ID는 역할을 맡을 팀 참가자를 식별한다.
- 참가자 ID를 사용자 ID로 해석하지 않는다.
- 현재 단계·방장 여부·기존 담당자·역할 수행 상태를 요청에서 받지 않고 저장된 데이터를 기준으로 판단한다.

## 2. 처리 순서

1. 요청 형식과 현재 사용자를 확인한다.
2. 팀 진행도를 쓰기 잠금으로 조회하고 연결된 미션의 활성 상태를 확인한다.
3. 현재 사용자가 대상 팀의 수락된 방장인지 확인한다.
4. 팀이 진행 중이며 초대·역할 배정 단계인지 확인한다.
5. 요청한 공통 역할 카드가 존재하는지 확인한다.
6. 배정 대상이 같은 팀의 수락된 참가자인지 확인한다.
7. 해당 팀과 역할 카드 조합의 기존 역할 수행 기록을 조회한다.
8. 배정이 없으면 생성하고, 같은 담당자이면 유지하며, 다른 담당자이면 배정을 교체한다.
9. 전체 처리가 성공하면 커밋한다. 응답 본문은 구성하지 않는다.

## 3. 팀 진행도와 미션 확인

- 진행도가 없으면 `COOPERATIVE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 완료된 팀을 진행도 없음으로 처리하지 않도록 진행 중 상태로 조회 조건을 제한하지 않는다.
- 연결된 미션이 비활성 상태이면 `COOPERATIVE_MISSION_INACTIVE`로 처리한다.
- 미션에 장소가 없어도 역할 배정을 허용한다.
- 이 API는 팀 진행도나 참가자를 새로 생성하지 않는다.

## 4. 방장 권한과 배정 단계 검증

- 현재 사용자와 대상 진행도가 모두 일치하는 참가자를 확인한다.
- 방장 역할이며 수락된 참가자인 경우에만 요청을 허용한다.
- 참가자가 없거나 팀원이거나 대기 상태이면 `COOPERATIVE_MISSION_HOST_ONLY`로 처리한다.
- 팀이 완료 상태이거나 현재 단계가 첫 단계가 아니면 `COOPERATIVE_MISSION_STEP_NOT_ALLOWED`로 처리한다.
- FastAPI의 이미 완료된 팀 오류와 배정 단계가 아닌 오류를 하나로 통합한다.
- 진행도 저장과 역할 배정 저장은 같은 오류 코드와 공통화된 메시지를 사용한다.
- 동일한 배정의 재요청이라도 먼저 미션 활성 상태·방장 권한·배정 가능 단계를 검증한다. 수행·완료 단계에서 멱등 요청이라는 이유로 성공 처리하지 않는다.

## 5. 역할 카드와 배정 대상 검증

- 역할 카드는 모든 협동 미션에서 사용하는 공통 마스터 데이터이므로 특정 미션 ID로 제한하지 않는다.
- 요청한 카드가 없으면 `COOPERATIVE_ROLE_CARD_NOT_FOUND`로 처리한다.
- 배정 대상은 요청 참가자 ID와 팀 진행도 ID가 모두 일치해야 한다.
- 대상 참가자가 없거나 다른 팀 소속이거나 대기 상태이면 `COOPERATIVE_MISSION_PARTICIPANT_NOT_FOUND`로 처리한다.
- 같은 팀의 수락된 방장·팀원 모두 대상이 될 수 있다.
- 현재 방장이 다른 팀의 참가자를 지정하거나 대기 참가자를 자동 수락하여 배정하지 않는다.

## 6. 기존 배정 조회와 관계 규칙

- 참가자와 팀 진행도의 연결을 따라 해당 팀과 역할 카드 조합의 역할 수행 기록을 조회한다.
- 카드 ID만으로 전체 팀에서 조회하지 않고 다른 팀의 동일 카드 기록은 변경하지 않는다.
- 한 팀에서 같은 역할 카드는 최대 한 참가자에게만 배정한다.
- 한 참가자는 서로 다른 여러 카드를 맡을 수 있다.
- 모든 공통 카드를 배정할 필요는 없다. 요청하지 않은 카드는 미배정 상태로 둔다.
- 역할 배정 저장에서는 수락된 참가자 전원이 역할을 갖는지 검증하지 않는다. 이 조건은 진행도 저장의 수행 단계 진입에서 검증한다.

## 7. 최초 배정

- 팀과 카드 조합의 기존 역할 수행 기록이 없으면 요청한 참가자와 카드로 새 기록을 생성한다.
- 수행 상태는 진행 중으로 생성하며 인증 이미지와 완료 시각은 null로 둔다.
- 복합키는 해당 참가자 ID와 역할 카드 ID로 구성한다.
- 다른 참가자의 배정이나 다른 카드의 수행 기록을 초기화하지 않는다.

## 8. 동일 배정 재요청

- 기존 담당자와 요청한 참가자가 같으면 기존 기록을 그대로 유지한다.
- 행을 추가하거나 삭제·재생성하지 않는다.
- 수행 상태·인증 이미지·완료 시각·생성 시각·수정 시각을 불필요하게 변경하지 않는다.
- 별도의 결과 본문 없이 정상 처리한다.

## 9. 담당자 변경과 현재 스키마 적용

- 기존 담당자가 요청한 참가자와 다르면 같은 카드의 담당자를 교체한다.
- 현재 역할 수행 기록은 참가자·카드의 복합키이므로 관리 중인 엔티티의 PK나 `@MapsId` 참가자 연관관계를 직접 변경하지 않는다.
- 기존 기록의 수행 상태·인증 이미지·완료 시각을 보존한 뒤 이전 참가자·카드 조합의 행을 제거하고 새 참가자·동일 카드 조합의 행으로 교체한다.
- 역할 카드와 보존할 인증 정보는 바꾸지 않는다. 정상 첫 단계에서는 인증 전이므로 수행 상태는 진행 중이고 인증 이미지·완료 시각은 null이다.
- 단일 역할 진행도 ID를 유지한다는 FastAPI 설명은 가져오지 않는다. 현재 스키마에 단일 ID를 추가하거나 가상의 ID를 만들지 않는다.
- 변경 이후 팀·카드 조합의 배정은 한 건만 존재해야 한다.
- 이전 담당자의 다른 역할과 새 담당자의 기존 다른 역할은 그대로 유지한다.
- 이전 담당자에게 역할이 하나도 남지 않아도 교체를 허용한다. 새로운 담당자를 자동 배정하거나 수행 단계로 자동 전환하지 않는다.

## 10. 응답과 폴링 연계

- 배정 저장이 끝나면 응답 본문 없이 반환한다.
- 이후 상태 조회의 역할 수행 목록에는 새 참가자 ID·닉네임과 동일 역할 카드 정보가 반영되어야 한다.
- 상태 조회의 실제 역할 기록 집계는 최초 배정이면 증가하고 담당자 변경이면 유지된다.
- 다른 팀의 배정은 해당 팀 상태 조회에서도 그대로 유지되어야 한다.
- 이 API는 팀 단계·팀 완료 상태·완료 시각·보상 지급 상태·사용자 포인트와 획득 데이터를 변경하지 않는다.
- 역할 인증·보상 지급·다음 장소 추천은 실행하지 않는다.

## 11. 동시 요청과 트랜잭션

- 팀 조회부터 모든 검증과 최초 배정·담당자 교체까지 하나의 쓰기 트랜잭션으로 처리한다.
- 기존 참여 요청·수락·거절·진행도 저장과 동일한 팀 진행도 행을 잠가 같은 팀의 변경을 순서대로 처리한다.
- 팀 잠금을 얻은 뒤 현재 단계와 기존 배정을 확인한다.
- 기존 배정은 잠금 조회로 최신 커밋 데이터를 읽는다. 팀 잠금 전에 사용자 조회로 생성된 MySQL 스냅샷을 재사용하여 직전 요청의 배정을 누락하지 않는다.
- 동시 최초 배정도 팀·카드 조합의 역할 수행 기록을 중복 생성하지 않는다.
- 서로 다른 담당자로 동시에 변경하면 잠금 순서대로 처리하며 최종적으로 한 참가자의 배정만 남는다.
- 수행 단계 전환과 경합하면 먼저 커밋된 상태를 기준으로 판단한다. 수행 단계 전환이 먼저 끝났으면 배정을 변경하지 않는다.
- 담당자 교체의 삭제·신규 저장 중 하나라도 실패하면 전체 교체를 롤백하여 기존 배정을 유지한다.
- 예상하지 못한 저장 오류를 정상 응답이나 참가자 없음으로 숨기지 않고 공통 서버 오류로 처리한다.

# 협동 미션 역할 진행도 저장 비즈니스 규칙

## 1. 요청과 처리 대상 식별

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC_2.md#협동-미션-역할-진행도-저장-api)를 따른다.
- 현재 사용자는 검증된 인증 정보로 식별한다.
- 팀 진행도 ID와 역할 카드 ID로 해당 팀의 배정·수행 기록을 찾는다. 현재 스키마에 없는 단일 역할 진행도 ID를 만들지 않는다.
- 참가자 ID·인증 결과·이미지 URL·완료 시각을 프론트에서 받지 않는다.
- 한 팀에서 카드별 담당자는 최대 한 명이며, 실제 수행 기록의 복합키는 참가자 ID와 카드 ID이다.

## 2. 처리 순서

1. 경로와 multipart 요청, 이미지 필수 여부·크기·실제 형식·디코딩을 검증한다.
2. 현재 사용자를 확인한다.
3. 팀 진행도를 잠금 조회하고 미션 활성 상태와 수행 단계를 확인한다.
4. 해당 팀·카드의 역할 수행 기록을 최신 데이터로 잠금 조회한다.
5. 현재 사용자의 담당자 권한과 수락 상태를 확인한다.
6. 역할의 기존 인증 완료 여부를 확인한다.
7. 역할 카드 정보와 검증된 이미지를 별도 사진 판정 모듈에 전달한다.
8. 판정 실패이면 업로드·DB 변경 없이 실패 판정 응답을 구성한다.
9. 판정 성공이면 Blob 업로드 후 해당 역할의 URL·완료 상태·완료 시각을 저장한다.
10. 트랜잭션 커밋까지 성공하면 성공 판정 응답을 반환한다.

## 3. 이미지 검증과 오류 구분

- 기존 사진 저장 API의 공통 이미지 검증 컴포넌트를 재사용한다.
- 누락·빈 파일과 잘못된 multipart 요청은 공통 요청값 검증 실패를 따른다.
- 이미지 형식·용량·손상은 공통 요청 오류로 뭉치지 않고 명세의 `INVALID_IMAGE_FORMAT`, `IMAGE_SIZE_EXCEEDED`, `INVALID_IMAGE`로 각각 구분한다.
- 파일 크기는 제한을 포함해 검증하며 기준과 허용 경계값은 API 명세를 따른다.
- multipart 파싱 단계에서 크기 제한으로 거절된 경우도 같은 용량 오류로 변환한다. 파일 본문 크기와 multipart 헤더·경계의 추가 크기를 구분한다.
- 읽는 과정에서도 크기를 제한하고 파일 전체를 무제한으로 메모리에 올리지 않는다.
- 파일명·클라이언트 Content-Type만 신뢰하지 않고 시그니처로 실제 형식을 판별한다.
- 실제 형식과 파일명·Content-Type이 다르면 실제 형식을 기준으로 허용 여부와 저장 형식을 결정한다.
- 지원하는 형식인지 판별한 뒤 실제 디코딩으로 손상 여부를 검증한다. 헤더·크기만 읽고 성공으로 처리하지 않는다.
- 허용한 WebP도 디코딩 검증을 수행한다. 디코더 부재를 이유로 형식 검사만 통과시키지 않는다.
- 파일 검증은 이미지 내용의 역할 적합성 판정과 별개이며, 검증한 원본을 임의로 리사이즈·재압축·변환하지 않는다.
- 검증이 끝나기 전에는 사진 판정이나 Blob 업로드·역할 갱신을 수행하지 않는다.

## 4. 팀 진행도와 수행 단계 확인

- 요청한 팀 진행도가 없으면 `COOPERATIVE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 완료된 팀도 조회한 뒤 구분하도록 진행 중 상태로 조회 조건을 제한하지 않는다.
- 연결된 미션이 비활성이면 `COOPERATIVE_MISSION_INACTIVE`로 처리한다.
- 진행 중인 팀의 수행 단계에서만 사진 인증을 허용한다.
- 완료된 팀이거나 수행 단계가 아니면 `COOPERATIVE_MISSION_STEP_NOT_ALLOWED`로 처리한다. FastAPI의 팀 완료 오류는 따로 사용하지 않는다.
- 미션의 장소가 없어도 사진 인증을 허용한다.

## 5. 역할 수행 기록과 담당자 확인

- 해당 팀의 참가자와 연결되고 요청한 카드를 참조하는 수행 기록을 조회한다.
- 다른 팀의 동일 카드나 현재 사용자의 다른 팀 수행 기록을 대신 사용하지 않는다.
- 해당 팀·카드의 배정이 없으면 `COOPERATIVE_ROLE_PROGRESS_NOT_FOUND`로 처리한다. 카드 마스터만 존재한다고 수행 기록을 생성하지 않는다.
- 배정된 참가자의 사용자 ID가 현재 사용자와 일치하고 참가 상태가 수락이어야 한다.
- 담당자가 아니거나 참가 상태가 수락이 아니면 `COOPERATIVE_ROLE_PROGRESS_ACCESS_DENIED`로 처리한다.
- 방장도 다른 참가자의 역할을 대신 인증할 수 없다.
- 이미 인증 완료된 기록이면 `COOPERATIVE_ROLE_PROGRESS_ALREADY_COMPLETED`로 처리하며 재판정·재업로드·사진 덮어쓰기를 하지 않는다.
- 한 참가자의 여러 역할은 각각 별개의 수행 기록으로 처리한다.

## 6. 별도 사진 판정 모듈과 임시 구현

- 사진 내용이 역할에 적합한지 판단하는 책임은 서비스·컨트롤러에서 분리한 별도 사진 판정 컴포넌트에 둔다.
- 서비스는 검증된 이미지 데이터·실제 MIME type과 역할 카드의 이름·설명·찾아야 할 대상 목록을 전달한다.
- 판정 컴포넌트는 성공 여부만 반환하며 Blob 업로드나 DB 변경은 수행하지 않는다.
- 현재는 실제 사진 내용 판정 로직을 구현하지 않고 유효한 입력에 대해 항상 성공을 반환한다.
- 현재 단계에서 실제 외부 AI API를 호출하거나 프롬프트·API 키 등 추가 설정을 요구하지 않는다.
- 구현 시 임시 성공 반환 위치에 `// TODO: 추후 역할 카드 정보와 사진 내용을 기반으로 실제 사진 인증 판정 로직을 구현한다. 현재는 항상 인증 성공을 반환한다.` 주석을 눈에 띄게 남긴다.
- 향후 판정 방식을 교체해도 요청·응답 계약과 서비스의 업로드·진행도 저장 흐름을 유지할 수 있도록 분리한다.
- 임시로 항상 성공하더라도 이미지 검증·미션 활성·단계·권한·중복 완료 검증은 생략하지 않는다.

## 7. 판정 실패와 예외 구분

- 현재 임시 판정은 성공만 반환하지만 서비스에는 실패 판정 처리 경로를 유지한다.
- 판정 결과가 실패이면 Blob을 업로드하지 않고 이미지 URL·진행 상태·완료 시각을 그대로 유지한다.
- 실패 판정은 정상적인 판정 결과로 응답하며 API 오류로 변환하지 않는다.
- 이미지 검증 오류나 판정 모듈의 예기치 못한 실행 예외를 실패 판정으로 숨기지 않는다.
- 내부 실행 장애는 기존 공통 서버 오류 처리와 로깅을 따른다.

## 8. Azure Blob 저장

- 판정이 성공한 사진만 기존 공통 Blob 스토리지 컴포넌트로 업로드한다.
- 대상 컨테이너는 기존 `AZURE_STORAGE_CONTAINER` 설정을 사용하며 연결 정보·키를 코드나 로그에 남기지 않는다.
- Blob 이름은 `cooperative_mission_role/{cooperativeMissionProgressId}/{roleCardId}/{uuid}.{extension}`으로 구성한다.
- 팀·카드는 검증된 수행 기록을 기준으로 하고 UUID는 서버가 생성한다. 현재 스키마에 없는 역할 진행도 ID를 경로에 사용하지 않는다.
- 원본 파일명은 Blob 이름에 사용하지 않는다.
- 실제 JPEG는 `.jpg`와 `image/jpeg`, PNG는 `.png`와 `image/png`, WebP는 `.webp`와 `image/webp`로 저장한다.
- 이미지 파일은 Azure Blob에 저장하고 DB에는 URL만 저장한다. MySQL BLOB 컬럼이나 앱·Docker 컨테이너의 로컬 파일 시스템을 영구 저장소로 사용하지 않는다.

## 9. 인증 성공과 역할 완료 저장

- 업로드가 성공한 뒤 기존 역할 수행 기록의 이미지 URL을 업로드된 Blob URL로 설정한다.
- 해당 역할의 수행 상태를 완료로 변경하고 주입받은 `Clock`으로 구한 서버 시각을 완료 시각에 저장한다.
- 담당자·역할 카드·팀 연결과 복합키는 유지하며 다른 역할 기록은 변경하지 않는다.
- 팀의 현재 단계·진행 상태·완료 시각을 변경하지 않는다.
- 사용자 포인트·AR 캐릭터·쿠폰·미션 보상 지급 상태를 변경하지 않는다.
- 마지막 역할이 인증되어도 팀을 자동 완료하지 않는다. 팀 완료와 보상 지급은 방장의 별도 진행도 저장에서 수행한다.

## 10. 응답과 폴링 연계

- 인증 결과만 응답하며 파일 URL·참가자·카드·팀 상태를 응답에 추가하지 않는다.
- 성공 응답은 업로드와 역할 변경·커밋까지 끝난 뒤 반환한다.
- 이후 상태 조회의 역할 목록에는 완료 상태와 저장된 이미지 URL이 반영되어야 한다.
- 전체 역할 수는 그대로이고 완료 역할 수는 이번에 완료한 역할만큼 증가한다.
- 프론트는 판정 응답으로 본인의 인증 결과를 확인하고 팀 동기화는 기존 상태 조회 폴링으로 계속 진행한다.

## 11. 반복·동시 요청과 트랜잭션

- 팀 진행도와 역할 수행 기록 확인부터 판정·업로드·역할 갱신까지 같은 쓰기 트랜잭션으로 처리한다.
- 기존 팀 변경 API와 같은 팀 진행도 잠금 기준을 사용하고 역할 기록도 잠금 조회하여 최신 커밋 데이터를 확인한다.
- 팀 잠금 뒤 역할 기록을 확인하여 완료·중단·배정 변경과 경합해도 저장된 최신 단계·담당자·인증 여부를 기준으로 검증한다.
- 같은 역할의 동시 인증은 첫 요청이 완료를 커밋한 뒤 후행 요청에서 이미 완료된 역할 오류로 처리한다. 후행 요청은 추가 판정·업로드를 하지 않는다.
- 오류나 판정 실패가 나면 잠금을 해제하며 기존 역할·팀·보상 상태를 유지한다.

## 12. 업로드·저장 실패와 정리

- Blob 업로드가 실패하면 역할의 URL·완료 상태·완료 시각을 변경하지 않는다.
- 업로드 후 DB 갱신이나 커밋이 실패하면 DB 변경을 롤백하고 이번 요청에서 업로드한 Blob만 삭제한다.
- Azure Blob은 DB 트랜잭션으로 자동 롤백되지 않으므로 기존 사진 저장 방식처럼 커밋 시점 실패까지 보상 삭제를 수행한다.
- 삭제 실패로 원래 저장 오류를 숨기지 않는다. 사용자·팀 진행도·카드·Blob 식별자와 저장·정리 실패 원인을 서버 로그에 남겨 추적한다.
- 스토리지·DB·판정 실행 오류의 내부 원인은 응답에 노출하지 않고 공통 서버 오류를 반환한다.
- 기존 사진과 다른 사용자·팀의 Blob 또는 DB 기록을 삭제·변경하지 않는다.

# 협동 미션 중단 비즈니스 규칙

## 1. 요청과 처리 대상 식별

- 요청 형식과 오류 응답은 [API 명세](./API_SPEC_2.md#협동-미션-중단-api)를 따른다.
- 현재 사용자는 검증된 인증 정보로 식별한다.
- 요청의 팀 진행도 ID와 현재 사용자 ID로 본인의 참가 기록을 식별한다. 참가자 ID나 승계할 사용자 ID는 프론트에서 받지 않는다.
- 중단은 현재 사용자의 참여 해제이며 다른 참가자를 내보내거나 팀 전체를 완료하는 기능이 아니다.

## 2. 처리 순서

1. 경로와 현재 사용자를 확인한다.
2. 팀 진행도를 잠금 조회하고 연결된 미션의 활성 상태를 확인한다.
3. 해당 팀의 현재 사용자 참가 기록을 확인한다.
4. 팀이 진행 중이며 첫 단계인지 확인한다.
5. 해당 팀의 최신 참가자 목록에서 본인을 제외한 남은 참가자와 방장 승계 대상을 판단한다.
6. 팀원이면 본인의 역할 진행도와 참가 기록을 삭제한다.
7. 방장이면 승계 대상에게 방장 권한을 부여하고 나가는 기존 방장의 역할 진행도와 참가 기록을 삭제한다. 승계 대상이 없으면 대기 참가자를 포함한 팀 전체를 삭제한다.
8. 마지막 참가자가 나가는 경우 역할 진행도·참가자·팀 진행도가 남지 않도록 삭제한다.
9. 커밋이 성공하면 응답 본문 없이 처리 결과를 반환한다.

## 3. 팀 존재·활성·참가 권한과 단계 확인

- 요청한 팀 진행도가 없으면 `COOPERATIVE_MISSION_PROGRESS_NOT_FOUND`로 처리한다.
- 완료된 팀도 구분할 수 있도록 진행 중 상태만 조회하지 않는다.
- 연결된 미션이 비활성이면 `COOPERATIVE_MISSION_INACTIVE`로 처리하며 참가자·역할·팀을 삭제하지 않는다.
- 현재 사용자의 참가 기록이 해당 팀에 없으면 `COOPERATIVE_MISSION_LEAVE_ACCESS_DENIED`로 처리한다.
- 방장·팀원 모두 본인의 참가 기록이 있으면 중단할 수 있다. 대기 참가자의 호출은 본인의 참여 요청 취소로 처리한다.
- 팀이 진행 중이 아니거나 첫 단계가 아니면 `COOPERATIVE_MISSION_STEP_NOT_ALLOWED`로 처리한다.
- 수행 단계에서 완료 단계로 전환하는 작업은 기존 진행도 저장이 담당한다. 이 API에서 수행 단계의 이탈·강제 완료를 처리하지 않는다.
- 미션에 장소가 없어도 중단을 허용한다.

## 4. 팀원 중단과 역할 배정 해제

- 호출자가 팀원이면 해당 팀에 연결된 본인의 참가 기록만 삭제한다.
- 해당 참가자에 연결된 역할 진행도를 함께 삭제하여 맡았던 카드를 미배정 상태로 돌린다.
- 삭제한 역할을 방장이나 다른 참가자에게 자동 재배정하지 않는다.
- 역할 카드 원본은 삭제하지 않는다.
- 기존 방장·다른 참가자·다른 참가자의 역할 진행도와 다른 팀의 동일 사용자·동일 카드 기록은 유지한다.
- 대기 참가자의 중단도 같은 범위로 처리하며 자동 수락하지 않는다.

## 5. 방장 중단과 권한 승계

- 나가는 기존 방장을 제외한 해당 팀의 수락된 참가자만 승계 후보로 삼는다. 대기 참가자를 자동 수락하거나 방장으로 승격하지 않는다.
- 후보 중 합류 시각인 joinedAt이 가장 빠른 참가자 한 명에게 방장 권한을 승계한다.
- 합류 시각이 같으면 참가자 ID가 작은 사람을 선택하여 승계 결과를 일관되게 결정한다.
- 승계받는 참가자는 기존 참가 기록을 유지하고 참가 역할만 방장으로 변경한다. 수락 상태·합류 시각·참가자 ID·기존 역할 배정은 유지한다.
- 삭제 대상은 승계받는 참가자가 아니라 나가는 기존 방장의 참가 기록과 그에 연결된 역할 진행도이다.
- 승계 후보가 있으면 그 외의 수락·대기 참가자와 팀 진행도를 유지한다. 팀 단계·진행 상태·팀 토큰을 초기화하거나 새 팀을 만들지 않는다.

## 6. 마지막 참가자와 승계 대상 없는 팀 정리

- 현재 사용자가 마지막 참가자이면 본인의 역할 진행도·참가 기록과 해당 팀 진행도를 모두 삭제한다.
- 방장이 나간 뒤 수락된 승계 후보가 없고 대기 참가자만 남는 경우에는 남은 대기 참가자와 해당 팀 진행도도 삭제한다.
- 팀 해산 시 해당 팀의 역할 진행도와 참가 기록이 남지 않도록 함께 정리한다.
- 팀 해산 시 잠금 조회로 영속성 컨텍스트에서 관리 중인 참가자도 먼저 삭제 대상으로 전환한 뒤 팀을 삭제한다. DB 삭제 연쇄만 의존하여 삭제된 팀을 참조하는 관리 상태 참가자가 남지 않도록 한다.
- 참가자와 역할 진행도 및 팀 진행도 사이의 기존 삭제 연쇄 관계를 사용하되 다른 팀·사용자·미션 원본·역할 카드 원본은 삭제하지 않는다.
- 중단이나 팀 해산을 완료 이력으로 기록하지 않는다. 미션 보상 지급 상태를 생성·변경하거나 포인트·캐릭터·쿠폰을 지급하지 않는다.

## 7. 응답과 상태 조회 연계

- 중단·승계·필요한 팀 정리가 커밋된 후 응답하며 별도 응답 DTO나 완료 결과를 구성하지 않는다.
- 중단한 사용자는 해당 팀의 상태 조회를 계속하지 않는다. 참가 기록이 삭제되므로 기존 상태 조회의 참가자 확인을 통과하지 못한다.
- 팀이 유지되면 남은 참가자의 다음 상태 조회에 변경된 방장·참가자 목록·역할 배정이 반영된다.
- 팀이 해산되면 기존 상태 조회의 팀 진행도 없음 처리로 구분한다.
- 완료 화면이나 보상을 조회하기 위해 중단한 참가자 기록을 유지하는 처리는 하지 않는다.

## 8. 반복·동시 요청과 최신 상태 판단

- 이미 중단한 사용자가 남아 있는 팀에 다시 요청하면 참가 기록 없음에 따른 중단 권한 오류로 처리한다. 성공한 것처럼 반복 응답하지 않는다.
- 팀 진행도까지 삭제된 뒤 재요청하면 팀 진행도 없음으로 처리한다.
- 기존 참여 요청·수락/거절·역할 배정·단계 변경과 같은 팀 진행도 잠금 기준을 사용하여 중단을 순서대로 처리한다.
- 팀 잠금 뒤 현재 참가자와 승계 후보·남은 인원을 최신 커밋 데이터로 확인한다. 잠금 전에 생성된 MySQL 스냅샷으로 직전 요청의 삭제·승계를 누락하지 않는다.
- 방장과 다른 참가자가 동시에 나가도 순차 반영된 참가자 상태를 기준으로 승계·해산을 다시 판단하여 방장 없는 팀이나 중복 방장을 만들지 않는다.
- 단계 전환과 경합하면 먼저 커밋된 결과를 기준으로 판단한다. 수행 단계 전환이 먼저 완료되었으면 중단을 거부하고, 중단이 먼저 완료되었으면 단계 전환은 변경된 참가자·역할·방장 정보를 기준으로 기존 규칙을 적용한다.

## 9. 트랜잭션과 실패 시 보존

- 팀과 참가자 조회·검증부터 방장 승계·역할 삭제·참가자 삭제·팀 삭제까지 하나의 쓰기 트랜잭션으로 처리한다.
- 방장 승계나 삭제 중 하나라도 실패하면 전체 변경을 롤백하여 기존 방장·참가자·역할·팀 진행도를 유지한다.
- 검증 실패 시 삭제·승계·보상 변경을 수행하지 않는다.
- 예상하지 못한 저장·삭제 실패를 참가자 없음이나 정상 중단으로 숨기지 않고 기존 공통 서버 오류 처리와 로깅을 따른다.
