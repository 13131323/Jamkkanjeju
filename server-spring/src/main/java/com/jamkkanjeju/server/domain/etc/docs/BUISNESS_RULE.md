# 쿠폰 사용 처리 API 비즈니스 규칙

## 1. 처리 순서

1. 인증 정보에서 현재 사용자 ID를 읽는다. 클라이언트로부터 사용자 ID나 사용 시각을 받지 않는다.
2. 요청한 쿠폰이 존재하는지 확인한다. 없으면 COUPON_NOT_FOUND로 처리한다.
3. couponId와 현재 사용자 ID로 ACQUIRED_COUPON의 복합키를 구성하고 획득 기록을 조회한다. 없으면 ACQUIRED_COUPON_NOT_FOUND로 처리한다.
4. used_at이 이미 저장돼 있으면 COUPON_ALREADY_USED로 처리한다. 기존 사용 시각은 변경하지 않는다.
5. 주입받은 Clock의 현재 시각을 used_at에 저장한다.
6. 정상 종료하며 응답 본문을 반환하지 않는다.

## 2. 사용 처리와 데이터 유지

- 사용 처리 대상은 현재 사용자의 획득 기록 한 건이다. 같은 쿠폰을 다른 사용자가 보유한 기록은 변경하지 않는다.
- 획득 기록과 쿠폰 정의를 삭제하지 않으며, acquired_at·쿠폰 금액·보상 지급 기록을 변경하지 않는다.
- 재요청에서 사용 시각을 덮어쓰거나 성공으로 처리하지 않는다.
- 쿠폰 사용 여부의 기준은 ACQUIRED_COUPON.used_at이다. 클라이언트 localStorage의 사용 상태는 사용하지 않는다.
- 지도 홈은 사용 완료한 획득 쿠폰도 반환하며 사용 시각을 usedAt으로 제공한다.

## 3. 트랜잭션과 동시 요청

- 획득 기록 조회·사용 여부 확인·사용 시각 저장을 하나의 쓰기 트랜잭션에서 처리한다.
- 조회할 획득 기록에 비관적 쓰기 잠금을 적용한다. 같은 사용자·쿠폰의 동시 요청은 순서대로 확인하여 최초 요청만 성공하고 후속 요청은 이미 사용한 쿠폰으로 처리한다.
- 오류가 발생하면 사용 시각 변경을 롤백하며 기존 데이터는 유지한다.

# 점검 상태 전환 및 API 차단 비즈니스 규칙

## 1. 시간과 상태

- 현재 시각은 주입받은 Clock을 Asia/Seoul 기준으로 변환해 한 번 읽는다.
- 종료 예정 시각이 현재 시각 이하인 SCHEDULED·IN_PROGRESS를 먼저 COMPLETED로 변경한다.
- 남은 SCHEDULED 중 `starts_at <= 현재 시각 < ends_at`인 행을 IN_PROGRESS로 변경한다.
- CANCELLED·FAILED·COMPLETED는 변경하지 않는다. 조건부 UPDATE로 중복 실행과 다중 서버 실행에도 동일한 상태를 유지한다.
- 스케줄러는 1초 간격으로 DB의 일정을 확인한다. 서버가 내려가 있는 동안 지난 예약도 재기동 후 같은 조건으로 정리한다.
- API 요청 시에도 같은 전환을 별도 서비스 트랜잭션으로 적용한 후 차단 여부를 판단하여 스케줄러 간격 동안 요청이 허용되거나 홈 상태가 뒤처지는 것을 방지한다.
- 진행 중이고 유효 시간에 속한 예약이 한 건이라도 있으면 점검 중이다. 여러 예약이 겹치면 마지막 진행 중 예약이 끝날 때까지 차단한다.
- COMPLETED는 점검 시간 종료를 의미하며 장소 동기화 완료를 의미하지 않는다.

## 2. 요청 필터

- 필터는 빈으로 등록하지 않고 기존 사용자 SecurityFilterChain에서 new로 생성해 JWT 필터 앞에 배치한다.
- 예외 경로와 메서드는 API 명세를 따른다. 허용 요청도 상태를 갱신한 뒤 기존 인증·컨트롤러 검증을 그대로 거친다.
- 별도 에이전트 체인은 점검 필터를 사용하지 않는다. 기존 고정 토큰 검증과 명시한 경로·메서드 허용만 유지한다.
- 일반 서비스 API는 비로그인 요청도 점검 시 503을 우선 반환하고 컨트롤러를 실행하지 않는다.
- 점검 DB 조회·상태 반영이 실패하면 공통 500을 반환하고 정상 요청으로 우회하지 않는다.
- 이미 컨트롤러에 진입한 요청을 강제로 중단하지 않는다. 필터 진입 시각 기준으로 차단한다.

## 3. 범위

- 예약 등록·상태 전환·API 차단만 구현한다. TourAPI 조회·장소 변경·미션 진행도 및 보상 내역 초기화·에이전트 실행 요청은 수행하지 않는다.
- 장소 동기화는 사용자가 점검 중 별도로 에이전트를 실행해 진행한다.
