# 사용자 온보딩 완료 API 테스트 계획

- 상태: **실행 완료**
- 실행일: 2026-10-12
- 결과: **온보딩 28개 전부 통과, 전체 106개 전부 통과**
- 대상 API: `PATCH /api/v2/users/me`
- 기준 문서: `API_SPEC.md`, `BUISNESS_RULE.md`

## 진행 방식

| 구분 | 방법 |
| --- | --- |
| 단위 테스트 | Spring과 DB 없이 JUnit 5, AssertJ, Mockito로 요청 검증과 서비스 비즈니스 로직을 검증한다. |
| 통합 테스트 | `@SpringBootTest` + `@AutoConfigureMockMvc` + 실제 MySQL로 인증, HTTP 요청, JPA 저장, 응답까지 전체 흐름을 검증하고 테스트마다 롤백한다. |

통합 테스트에서는 `DEV_AUTH_ENABLED=false`로 고정하고 `JwtTokenProvider`로 발급한 실제 액세스 토큰을 `Authorization` 헤더에 전달한다.

## 단위 테스트 계획

### `CompleteOnboardingRequestValidationTest`

| 구분 | 검증 내용 |
| --- | --- |
| 나중에 할게요 | 모든 선택 필드가 `null`이면 유효하며 `isSkipped()`가 `true`인지 확인 |
| 일반 완료 | `expectations`, `transportation`, `travelStyle`이 모두 있으면 유효한지 확인 |
| 일부 필드 누락 | 세 필드 중 일부만 전달하면 검증에 실패하는지 확인 |
| 빈 기대 항목 | `expectations`가 빈 목록이면 검증에 실패하는지 확인 |
| null 기대 항목 | `expectations`에 `null`이 포함되면 검증에 실패하는지 확인 |
| 기대 항목 중복 | 같은 기대 항목이 두 번 포함되면 검증에 실패하는지 확인 |

### `OnboardingServiceTest`

| 구분 | 검증 내용 |
| --- | --- |
| 사용자 확인 | 인증된 사용자 ID에 해당하는 사용자가 없으면 `UNAUTHORIZED`가 발생하는지 확인 |
| 최초 일반 완료 | 기존 선택 행이 없는 사용자에게 요청한 기대 항목, 이동 수단, 여행 방식을 새로 저장하는지 확인 |
| 일반 재요청 | 기존 선택 중 제거된 값은 삭제하고 새 값은 추가하며, 이동 수단과 여행 방식은 변경하는지 확인 |
| 중복 방지 | 동일한 일반 요청을 다시 처리해도 기대 항목을 중복 저장하지 않는지 확인 |
| 기준 데이터 검증 | 요청 enum에 대응하는 기대 항목, 이동 수단 또는 여행 방식 데이터가 없으면 실패하는지 확인 |
| 일반 결과 배정 | `여행자`를 제외한 후보 중 하나를 사용자에게 배정하는지 확인 |
| 일반 결과 없음 | 배정 가능한 온보딩 결과가 없으면 실패하는지 확인 |
| 나중에 할게요 | 기존 선택값을 모두 삭제하고 `여행자` 결과를 배정하는지 확인 |
| 기본 결과 없음 | `여행자` 온보딩 결과가 없으면 실패하는지 확인 |
| 응답 구성 | 사용자 ID, 완료 여부, 최종 온보딩 결과가 서비스 처리 결과와 일치하는지 확인 |

무작위 결과 배정 테스트에서는 Repository가 후보 하나만 반환하도록 구성하여 테스트 결과를 고정한다.

## 통합 테스트 계획

### `OnboardingApiIntegrationTest`

| 구분 | 요청 및 검증 내용 |
| --- | --- |
| 일반 완료 성공 | 유효한 요청에 200을 반환하고 응답의 사용자 ID, `onboardingCompleted`, 온보딩 결과를 확인 |
| 일반 완료 DB 반영 | 사용자별 기대 항목, 이동 수단, 여행 방식, `onboarding_result_id`가 실제 DB에 저장되는지 확인 |
| 나중에 할게요 성공 | 빈 객체 `{}`에 200을 반환하고 `여행자` 결과와 `onboardingCompleted=true`를 반환하는지 확인 |
| 나중에 할게요 DB 반영 | 기존 사용자 선택값이 모두 삭제되고 기본 온보딩 결과가 저장되는지 확인 |
| 일부 필드 누락 | 선택 필드 일부만 전달하면 400 `INVALID_REQUEST`를 반환하는지 확인 |
| 빈 기대 항목 | `expectations: []`이면 400 `INVALID_REQUEST`를 반환하는지 확인 |
| 기대 항목 중복 | 같은 기대 항목을 중복 전달하면 400 `INVALID_REQUEST`를 반환하는지 확인 |
| 잘못된 enum | 정의되지 않은 enum 문자열을 전달하면 400 `INVALID_REQUEST`를 반환하는지 확인 |
| 잘못된 JSON | 파싱할 수 없는 JSON이면 400 `INVALID_REQUEST`를 반환하는지 확인 |
| 일반 재요청 | 다른 선택값으로 재요청하면 기존 선택값과 온보딩 결과가 교체되는지 확인 |
| 동일 요청 반복 | 동일한 요청을 반복해도 사용자별 기대 항목 행이 중복되지 않는지 확인 |
| 일반 완료 후 건너뛰기 | 일반 완료 후 `{}`를 요청하면 기존 선택값이 삭제되고 `여행자` 결과로 바뀌는지 확인 |
| 건너뛰기 후 일반 완료 | `{}` 처리 후 일반 요청을 보내면 새 선택값과 일반 온보딩 결과가 저장되는지 확인 |
| 트랜잭션 롤백 | 처리 중 결과 배정에 실패하면 500을 반환하고 기존 선택값과 결과가 유지되는지 확인 |

일반 완료의 온보딩 결과는 무작위이므로 특정 ID를 단정하지 않고, 결과가 존재하며 `userType`이 `여행자`가 아닌지 확인한다.

## 실행 순서

1. `CompleteOnboardingRequestValidationTest`를 작성하고 실행한다.
2. `OnboardingServiceTest`를 작성하고 실행한다.
3. `OnboardingApiIntegrationTest`를 작성하고 실행한다.
4. 온보딩 테스트와 기존 전체 테스트를 함께 실행해 회귀 오류가 없는지 확인한다.
5. 실행 후 이 문서의 상태, 실행일, 테스트 개수, 결과와 발견·수정 사항을 실제 결과로 갱신한다.

## 완료 조건

- 단위 테스트와 통합 테스트가 모두 통과한다.
- `API_SPEC.md`의 요청·응답 형식과 오류 응답이 검증된다.

## 발견하고 수정한 점

- 운영 코드에서 발견된 오류 없음
- 통합 테스트의 400 검증(일부 필드 누락, 빈 기대 항목, 기대 항목 중복, 잘못된 enum, 잘못된 JSON)은 한 테스트에서 요청 본문 목록으로 함께 검증
- 서비스 테스트의 기준 데이터 검증은 기대 항목, 이동 수단, 여행 방식 각각 실패 시 선택값이 변경되지 않는지 3개 테스트로 검증
- 트랜잭션 롤백 테스트는 테스트 트랜잭션 안에서 실제 롤백을 확인할 수 없어 트랜잭션 없이 실행하고, `@MockitoSpyBean`으로 결과 후보 조회를 빈 목록으로 바꿔 실패시킨 뒤 생성한 사용자를 직접 삭제
