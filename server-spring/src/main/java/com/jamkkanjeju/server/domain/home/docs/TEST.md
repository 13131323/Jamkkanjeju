# 홈 조회 API 테스트 계획

- 상태: **실행 완료**
- 실행일: 2026-10-28
- 결과: **기간 집계 변경 후 단위 15개·홈 통합 22개, 총 37개 통과. 실패·오류·건너뜀 0개.** 전체 회귀는 이번 변경에서 실행하지 않았으며 아래 다른 클래스의 결과는 기존 실행 기록이다.
- 대상 API: `GET /api/v2/users/me/home`
- 기준 문서: `API_SPEC.md`, `BUISNESS_RULE.md`

## 진행 방식

| 구분 | 방법 |
| --- | --- |
| 단위 테스트 | Spring과 DB 없이 JUnit 5, AssertJ, Mockito로 요청 검증, 완료 판정, 추천, 거리·시간 계산, 집계와 서비스 응답 구성을 검증한다. |
| 통합 테스트 | `@SpringBootTest` + `@AutoConfigureMockMvc` + 실제 MySQL로 인증부터 Query 바인딩, JPA 조회, JSON 응답까지 검증한다. 테스트 데이터는 테스트마다 롤백한다. |

통합 테스트에서는 `app.dev-auth.enabled=false`로 고정하고 실제 사용자에 대한 액세스 토큰을 `JwtTokenProvider`로 발급해 전달한다. 고정된 1번 사용자나 기존 데이터의 개수에 의존하지 않고 테스트별 사용자·미션·장소·진행도·방명록을 준비한다. 기존 초기 데이터가 있는 경우 테스트 후보를 격리하거나 기존 집계값과의 차이로 검증한다.

## 단위 테스트 계획

### `GetHomeRequestValidationTest`

| 구분 | 검증 내용 |
| --- | --- |
| 정상 좌표 | 유효한 위도·경도와 0을 허용하는지 확인 |
| 필수값 | 위도 또는 경도가 `null`이면 검증에 실패하는지 확인 |
| 경계값 | 위도 -90·90, 경도 -180·180을 허용하는지 확인 |
| 범위 초과 | 각 좌표의 최솟값 미만과 최댓값 초과를 거부하는지 확인 |

### `MissionCompletionCheckerTest`

| 구분 | 검증 내용 |
| --- | --- |
| 보물찾기 완료 | `COMPLETED`만 완료로 판단하고 `IN_PROGRESS`는 제외하는지 확인 |
| 협동 완료 | 참가 상태가 `ACCEPTED`이고 팀 상태가 `COMPLETED`인 경우만 완료로 판단하는지 확인 |
| 협동 미완료 | `PENDING` 참가자 또는 `IN_PROGRESS` 팀을 완료로 판단하지 않는지 확인 |
| ID 구성 | 완료한 공통 미션 ID만 반환하고 같은 미션의 여러 완료 기록은 하나로 모으는지 확인 |
| 빈 기록 | 진행 기록이 없으면 빈 집합을 반환하는지 확인 |

### `MissionRecommenderTest`

| 구분 | 검증 내용 |
| --- | --- |
| 유형별 추천 | 후보가 있으면 문화·협동·보물찾기를 각각 한 건씩 추천하는지 확인 |
| 최근접 선택 | 보물찾기와 협동 후보를 거리순이 아닌 순서로 준비하고 가장 가까운 미션을 고르는지 확인 |
| 완료 제외 | 가장 가까운 미션을 이미 완료했다면 제외하고 다음 후보를 고르는지 확인 |
| 운영 상태와 장소 | Repository에 `ACTIVE`와 장소 존재 조건으로 후보를 요청하는지 확인. 실제 필터링은 통합 테스트에서 검증 |
| 위치 변경 | 요청 위치가 바뀌면 바뀐 위치를 기준으로 최근접 미션을 선정하는지 확인 |
| 후보 없음 | 일부 유형에 후보가 없으면 해당 유형만 제외하고, 모두 없으면 빈 목록을 반환하는지 확인 |
| 문화 추천 | 후보 하나로 무작위 요소를 고정하고 문화 미션의 장소·거리·시간이 `null`인지 확인 |
| 추천 데이터 | 공통 미션 ID, 유형, 이름, 장소 정보와 계산된 거리·시간이 추천 결과에 반영되는지 확인 |

최근접 선택 테스트는 `TravelEstimator`가 서로 다른 거리를 반환하도록 Mock을 구성한다. 비공개 `findNearest()`를 직접 호출하지 않고 `recommend()`의 결과를 검증한다.

### `TravelEstimatorTest`

| 구분 | 검증 내용 |
| --- | --- |
| 동일 위치 | 같은 좌표 사이의 거리와 시간이 0인지 확인 |
| 직선거리 | 독립적으로 구한 기준 좌표의 기대 거리와 허용 오차 내에서 일치하는지 확인 |
| 거리 대칭 | 출발지와 목적지를 바꾸어도 거리가 같은지 확인 |
| 도보 시간 | 100m는 80초에 해당하고 300m는 4분으로 계산되는지 확인 |
| 정수 응답 | 거리와 시간을 각각 반올림한 정수로 구성하는지 확인 |
| 장소 없음 | 장소가 `null`이면 거리와 시간 모두 `null`인지 확인 |

계산 테스트의 기대값을 검증 대상 메서드로 다시 계산하지 않는다. 현재 임시 계산 기준을 검증하고, 추후 TODO의 계산 방식이 변경되면 해당 기대값도 함께 갱신한다.

### `HomeServiceTest`

| 구분 | 검증 내용 |
| --- | --- |
| 사용자 없음 | `UNAUTHORIZED`가 발생하고 이후 홈 정보 조회를 진행하지 않는지 확인 |
| 추천 연결 | 사용자의 완료 미션 ID와 요청 위치를 추천기에 전달하고 결과를 응답에 포함하는지 확인 |
| 문화 진행 | 퀴즈 개수를 `totalStep`, 현재 퀴즈 인덱스를 `currentStep`으로 구성하는지 확인 |
| 퀴즈별 집계 | 서로 다른 문화 미션의 퀴즈 개수가 각 미션 ID에 올바르게 연결되는지 확인 |
| 보물찾기 진행 | 전체 보물 수를 `totalStep`, 찾은 보물 수를 `currentStep`으로 구성하고 0개도 그대로 반환하는지 확인 |
| 협동 진행 | 현재 사용자의 참가 기록에 연결된 `IN_PROGRESS` 팀을 조회 결과에 포함하는지 확인. 완료 추천 제외 조건을 진행 중 조회에 적용하지 않는지 확인 |
| 협동 단계 | 팀의 현재 단계와 미션 유형의 단계 개수를 사용하고 개인 역할 진행 상태는 기준으로 사용하지 않는지 확인 |
| 완료 제외 | 완료된 보물찾기·협동 진행 기록이 진행 중 목록에 포함되지 않는지 확인 |
| 장소 없는 진행 | 장소가 없는 진행 미션의 장소명·거리·시간이 `null`인지 확인 |
| 빈 진행 목록 | 세 유형 모두 진행 중 기록이 없으면 빈 목록인지 확인 |
| 방명록 집계 | 사용자의 마지막 확인 시각을 집계 컴포넌트에 전달하고 결과를 응답에 포함하는지 확인 |
| 온보딩 이미지 | 일반·기본 온보딩 결과의 프로필 이미지를 사용하고 결과가 없으면 `null`인지 확인 |
| 실패 전파 | 조회·집계 중 예기치 않은 오류를 정상 응답으로 바꾸거나 숨기지 않는지 확인 |

## 통합 테스트 계획

### `HomeApiIntegrationTest`

| 구분 | 요청 및 검증 내용 |
| --- | --- |
| 정상 응답 | 인증된 사용자의 유효한 위치 요청에 200을 반환하고 명세의 필드명, 배열, 숫자와 `null` 형식을 확인 |
| 사용자 격리 | 다른 사용자의 완료 기록이 추천 제외에 영향을 주지 않고 다른 사용자의 진행도가 목록에 포함되지 않는지 확인 |
| 추천 후보 조건 | 실제 DB에서 비활성 미션과 장소 없는 보물찾기·협동 미션이 추천에서 제외되는지 확인 |
| 완료 추천 제외 | 사용자가 완료한 보물찾기와 수락한 참가 기록에 연결된 완료 협동 미션이 추천에서 제외되는지 확인 |
| 최근접 추천 | 거리가 명확하게 다른 장소들을 준비해 미완료 후보 중 가장 가까운 미션을 추천하는지 확인 |
| 문화 추천 | 응답 미션이 활성 문화 후보 중 하나이며 장소·거리·시간이 `null`인지 확인 |
| 후보 없음 | 유형별 후보 부재 시 해당 유형을 생략하고 전체 후보 부재 시 빈 추천 배열을 반환하는지 확인 |
| 문화 퀴즈 개수 | 서로 다른 미션에 여러 퀴즈를 저장해 실제 GROUP BY 쿼리가 미션별 퀴즈 수와 현재 인덱스를 올바르게 반환하는지 확인 |
| 보물찾기 단계 | 전체 보물 수와 사용자별 찾은 보물 수가 응답의 전체·현재 단계에 일치하는지 확인 |
| 협동 팀 조회 | 현재 사용자의 참가자 FK를 따라 진행 중 팀을 조회하고 완료 팀은 제외하는지 확인 |
| 협동 역할 중복 방지 | 참가자에게 여러 역할 진행 기록이 있어도 같은 팀 진행도가 역할 수만큼 중복되지 않는지 확인 |
| 팀 단계 사용 | 개인 역할 완료 상태와 팀 단계를 다르게 준비해 응답이 팀 단계를 사용하는지 확인 |
| 거리·시간 응답 | 장소가 있는 미션의 거리·시간과 정수 형식을 확인하고, 장소 없는 미션은 `null`인지 확인 |
| 기간별 방명록 집계 | 여러 사용자의 일반·길바닥 방명록이 마지막 확인 시각 초과·서버 현재 시각 이하에서만 집계되고, 경계·미래 기록 제외·중복 집계 없음·사용자별 확인 시각에 따른 결과를 검증한다. 홈 조회는 확인 시각을 변경하지 않는다. |
| 온보딩 이미지 | 일반 온보딩 결과, 기본 여행자 결과, 온보딩 결과 없음에 대해 이미지 URL 또는 `null`이 정확한지 확인 |
| 빈 진행 목록 | 진행 기록이 없는 사용자에게 빈 진행 배열을 반환하는지 확인 |
| Query 오류 | 위도·경도 누락, 숫자가 아닌 값, 범위 초과에 400 `INVALID_REQUEST`와 명세의 메시지를 반환하는지 확인 |
| 인증 오류 | 토큰 없음·변조·만료에 각각 명세의 401 코드와 메시지를 반환하는지 확인 |
| 사용자 없음 | 유효한 토큰의 사용자 ID가 DB에 없으면 401 `UNAUTHORIZED`를 반환하는지 확인 |
| 서버 오류 | 조회 컴포넌트의 예기치 않은 실패를 Spy로 유도해 500 공통 응답을 반환하고 내부 예외 메시지를 노출하지 않는지 확인 |
| 위치 변경 재조회 | 위치를 변경하면 추천과 거리·시간이 새 위치를 기준으로 구성되는지 확인 |
| 읽기 전용 | 반복 조회 전후 사용자·진행도·방명록·온보딩 연결 상태와 행 개수가 유지되는지 확인 |

통합 테스트의 문화 추천은 특정 미션 ID나 반복 요청 시 결과 변경을 단정하지 않는다. 후보 포함 여부를 검증한다. 목록 순서는 별도 계약이 없으므로 유형·미션 ID로 찾아 비교한다. 읽기 전용 검증은 영속성 컨텍스트를 비운 뒤 DB 상태를 다시 조회한다.

## 실행 순서

1. `GetHomeRequestValidationTest`, `MissionCompletionCheckerTest`, `TravelEstimatorTest`, `GuestbookCounterTest`를 작성하고 실행한다.
2. `MissionRecommenderTest`, `HomeServiceTest`를 작성하고 실행한다.
3. `HomeApiIntegrationTest`를 작성하고 실행한다.
4. 홈 테스트와 기존 전체 테스트를 함께 실행해 회귀 오류가 없는지 확인한다.
5. 계획 내용은 보존하고 상태, 실행일, 전체 결과, 클래스별 결과와 발견·수정 사항을 실제 실행 결과로 기록한다.

## 완료 조건

- 단위 테스트와 통합 테스트가 모두 통과한다.
- API 명세의 요청·응답 및 오류 계약이 검증된다.
- 완료 판정, 최근접 추천, 사용자별 진행 조회, 유형별 단계 구성, 방명록 집계, 온보딩 이미지와 읽기 전용 규칙이 검증된다.
- 무작위 추천과 기존 초기 데이터 때문에 테스트가 불안정해지지 않는다.
- 기존 테스트에 회귀 오류가 없다.
